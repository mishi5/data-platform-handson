データセキュリティ

DMBOK 07 ／ BigQuery 基盤での実装

「データマネジメント概論」を本編とするシリーズ。番号は DAMA-DMBOK2 の章番号（01〜17）。全体像と各章の位置づけは概論を参照。

1. この領域が扱うもの

データセキュリティは「誰が・何に・どこまで触れるか」を設計し、実施し、証明する領域。 3つ目の証明するが抜けやすい。設定しただけでは「そうなっているはず」であって、 実際にそうであることを示せる状態とは違う。

DMBOK は「4つの A」で整理する。実装を考えるときの分解として使いやすい。

要素問いBigQuery での主な担い手
Authentication（認証） 誰であるかを確かめる Google アカウント / サービスアカウント。基盤側で作り込む余地は小さい
Authorization（認可） その人に何を許すか IAM、Authorized View、列/行レベル制御。設計の主戦場
Access（アクセス） 実際にどう到達させるか VPC Service Controls、データセットの location、共有の経路
Audit（監査） 誰が何をしたかを後から示せるか Cloud Audit Logs、INFORMATION_SCHEMA.JOBS

データ基盤で設計判断が集中するのは認可で、監査は「後から効いてくる」もの。 インシデントが起きてから「ログを取っていなかった」と気づく類のものなので、 認可より先に監査の保持期間を決めておくほうが安全側に倒せる。

分類なくして制御なし

認可の設計に入る前に、何が機密かの分類が要る。 分類が無いまま権限だけ設計すると、「この列は隠すべきか」を毎回その場で判断することになり、 判断がぶれる。

分類の例扱い典型
公開可 社内なら誰でも マスタ、集計済み指標
社外秘 業務上の必要がある人まで 売上明細、原価
個人情報 目的を限定し、経路を記録 氏名、メール、住所、端末ID
要配慮個人情報 原則として基盤に入れない判断もある 健康、信条、犯罪歴

4段階を超えると運用できなくなるので、細分化したくなっても3〜4段に留める。 段階が増えるほど「どれに当たるか」の判断コストが上がり、結局は使われなくなる。

2. 認可の設計 — 何で絞るか

BigQuery の権限は「IAM でどのリソースに触れるか」と 「その内側で列・行のどこまで見せるか」の2系統に分かれている。 これを選択の順序として整理する。 上から順に検討し、足りないときだけ下へ降りるのが原則。 下へ行くほど強力だが、運用コストと事故のリスクが上がる。

「データセットを分ける」で足りる場面は多い。 個人情報を含むテーブルを専用データセットに隔離し、そこへのアクセスを限定するだけで、 列レベル制御を導入せずに済むことがある。 テーブルを分割できないかを先に考えると、権限設計は大幅に単純になる。

逆に列レベル・行レベルが本当に要るのは、同じ行を複数の立場の人が見るが、 見える範囲が違うケース。営業担当が自分の担当顧客だけ見る、 分析者はメールアドレスをハッシュでしか見ない、といった要求はテーブル分割では解けない。

3. BigQuery での実装と落とし穴

手段ごとの注意点

手段効き方踏みやすい落とし穴
IAM ロール 組織 → プロジェクト → データセット → テーブルで継承される 上位で付けた権限は下位で剥がせない。プロジェクトに bigquery.dataViewer を付けると全データセットが見える
Authorized View ビュー自体に元テーブルへの読み取り権を与える。利用者は元テーブルの権限が不要 元テーブルの構造変更でビューが壊れる。ビューが増えるとどれが誰に何を見せているか把握できなくなる
列レベル（ポリシータグ） タグの分類体系を作り、列に付与。タグへの権限で可否が決まる タグ体系の設計をやり直すのが難しい。付け替えは全テーブル横断の作業になる
行レベル CREATE ROW ACCESS POLICY でフィルタ条件を定義 ポリシーが増えるとクエリの見え方が人によって変わり、「私には0行なのですが」という問い合わせの調査が難しい
動的マスキング ポリシータグにマスキングルールを紐づけ、値を変形して返す マスク後の値で結合・集計すると結果が変わる。利用者がマスクに気づかないまま分析する事故が起きる
VPC Service Controls ネットワーク境界で持ち出しを止める 設定を誤ると正規の経路まで止まる。段階的な導入と dry-run が要る

IAM の継承が最も事故りやすい。 「開発者にプロジェクトの閲覧権を渡した」つもりが、個人情報を含むデータセットまで 見えていた、という形で起きる。プロジェクトレベルでデータ系のロールを付けない—— データセット単位で付ける、を原則にすると事故が減る。

分類の自動化 — Sensitive Data Protection（Cloud DLP）

§1 の分類は手で付けると続かない。列が増えるたびに誰かが判定する運用は、 最初の棚卸しで止まる。Google Cloud の Sensitive Data Protection（旧 Cloud DLP）は、 DMBOK が「データ分類」「マスキング／難読化」「プライバシー」として書いている活動を BigQuery 上で機械化する。名前は DMBOK に出てこないが、対応先ははっきりしている。

機能DMBOK での位置BigQuery での使い方落とし穴
Discovery（自動プロファイル） ch.7 データ分類、ch.12 メタデータ（機密度は分類メタデータ） 組織・プロジェクト単位で全テーブルを走査し、列ごとの infoType と機密度（High / Moderate / Low）を Dataplex のタグに書く。ここからポリシータグに繋ぐと §2 の列レベル制御が「分類→制御」で一本化する 採点はサンプリングで決まる。低頻度の PII 列（備考欄に稀にメール）は Low と出る。閾値だけで自動付与せず、High 以外は人が見る
Inspection（検査ジョブ） ch.7 データ分類の実施 特定テーブルに対し infoType（EMAIL_ADDRESS、JAPAN_INDIVIDUAL_NUMBER、PHONE_NUMBER 等）で値を検出。結果を BigQuery に書き戻して集計できる 日本語の氏名・住所は検出精度が低い。カスタム infoType（辞書・正規表現）を足す前提で見積もる
De-identification（非識別化） ch.7 マスキング／難読化（静的） マスク、トークン化、フォーマット保持暗号（FPE）、バケット化、日付シフト。DWH に入れる前に静的に掛けるか、§3 上表の動的マスキングで参照時に掛けるかを選ぶ 結合キーに使う列は決定的トークン化でないと結合が切れる。ハッシュだけだとレインボー攻撃に弱いので鍵付き（HMAC）にする
Risk analysis（再識別リスク） ch.7 プライバシー・機密性、ch.2 データ取扱倫理 k-匿名性・l-多様性・δ-存在性を準識別子（年齢帯・居住地・職種…）の組合せで計測。「匿名化した集計」を公開する前の定量チェック 準識別子の選び方で結果が変わる。「何を準識別子とみなすか」は分類方針（§1）側で先に決める

順序は「分類 → メタデータ → 制御」。 Discovery で機密度を Dataplex に書き、それをポリシータグに写し、タグへの権限で列を絞る—— この一本の流れにすると、分類の更新が制御に伝わる。逆に Inspection の結果を Excel に落として 手で権限を付ける運用にすると、分類と制御がすぐ乖離する。

再識別リスクはマスキングでは解けない点に注意。氏名を消しても、 「30代・福岡・データエンジニア・従業員50人未満の会社」が1人しかいなければ特定できる。 少人数の母集団を持つ属性の組合せは、集計マートの設計段階で キーを持たせない／帯に丸める判断が要る（データマート設計 DM03 の匿名性の項）。

サービスアカウントの扱い

実務では人よりサービスアカウントの権限が問題になることが多い。 パイプラインが動くために強い権限を持ち、それが放置される。

原則理由
用途ごとに分ける 1つのSAを使い回すと、何を止めてよいか分からなくなる。収集用・変換用・BI用は別にする
キーを作らない JSON キーは漏洩経路になり、失効管理も要る。Workload Identity や impersonation で代替する
権限を定期的に見直す 付けた権限は消えない。Recommender の未使用権限の提案を定期的に見る
誰が impersonate できるか管理する iam.serviceAccountTokenCreator を持つ人は、そのSAの全権限を使える。実質的な権限昇格経路

最後の項目は見落とされやすい。SA を impersonate できる権限は、 その SA が持つ全権限と等価で、直接ロールを付与していなくても同じことができる。 権限の棚卸しでは「誰がどの SA になれるか」まで見る必要がある。

監査 — 後から示せるか

知りたいこと参照先注意
誰がいつどのテーブルを読んだか Cloud Audit Logs（Data Access ログ） 既定では無効。明示的に有効化しないと記録されない。有効化すると量が多くコストがかかる
どんなクエリが実行されたか INFORMATION_SCHEMA.JOBS 保持は180日。それ以上残すなら自分でエクスポートする
権限がいつ変更されたか Cloud Audit Logs（Admin Activity ログ） こちらは既定で有効・無料。権限変更の追跡はここで足りる

Data Access ログが既定で無効な点は要注意。 「誰がこの個人情報テーブルを見たか」を後から知りたくなったときには手遅れで、 有効化した時点より前は記録が無い。 機密データを扱うデータセットだけ有効化すると、 コストを抑えつつ必要な証跡が残せる。

4. 最小構成 — 個人・小規模なら

1人で運用している基盤でも、次の3つは意味がある。 いずれも「他人から守る」より「自分の事故から守る」ための備えになる。

  • 本番と検証でプロジェクトを分ける — 権限設計の8割はこれで済む。 検証で誤って本番テーブルを消す事故が構造的に起きなくなる
  • サービスアカウントのキーを作らない — impersonation を使う。 キーファイルは作った瞬間から漏洩リスクが始まり、失効管理が必要になる
  • 個人情報を基盤に入れるかを最初に決める — 入れなければ、 それにまつわる制御・監査・保持期間の設計がすべて不要になる。 入れない判断が最も安上がりで安全

やらなくてよいのは列レベル制御の先行導入と Data Access ログの全面有効化。前者はタグ体系の設計コストが先に来て、 後者はログ費用が積み上がる。どちらも「必要になってから」で間に合う。

この基盤（news_pipeline）での実装

公開情報しか扱わないため機密の制御は薄いが、認証と権限の分離は いくつか実装されている。

Sensitive Data Protection は使っていない。扱うのは公開記事の本文と URL で、 個人情報に当たる列が無いため、分類は「全部公開可」の1段で足りる。要るとすれば favorites（本人の関心の履歴）だが、利用者が1人の基盤では保護対象にならない。 判断としては正しいが、「PII が無いことを一度も機械で確かめていない」のは弱点で、 Discovery を1回走らせて Low が並ぶことを見ておけば、それが証明になる。

対象実装評価
Cloud Run の呼び出し Scheduler 専用 SA（news-pipeline-scheduler）に run.invoker 用途ごとに SA を分けられている
Slack からの呼び出し SLACK_SIGNING_SECRET による署名検証 エンドポイントは allUsers に開いているため、署名検証が唯一の防御
API キー・シークレット Secret Manager（anthropic-api-key ほか2件） コードにも Terraform state にも平文で入らない
family-share へのアップロード IAP + SA の impersonation でIDトークンを取得 キーファイルを作らない形になっている
BigQuery への書き込み Cloud Run の既定 SA 弱点。用途別に分けておらず、権限も絞っていない
データアクセスの監査 なし（Data Access ログ未有効） 公開情報のみなので現状は妥当。個人情報を入れるなら必須になる

「公開情報しか扱わない」という判断が、セキュリティ設計の大半を省略させている。 これは手抜きではなく設計判断で、 逆に言えば個人情報を1列でも入れた瞬間に、分類・列レベル制御・監査ログ・保持期間の 検討がまとめて必要になる。入れる前に判断するのが最も安いタイミングになる。

もう1つ、この基盤で実際に効いている観点がある。 Slack のスラッシュコマンド用エンドポイントは allUsers に開いているため、 URL を知っていれば誰でも叩ける。署名検証が唯一の防御なので、 SLACK_SIGNING_SECRET が空だと事実上の無防備になる。 「開いているエンドポイントを、何が守っているか」を言えるかが この規模でのセキュリティ設計の実質になる。
