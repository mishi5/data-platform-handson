# 08 コンフォームドとドリルアクロス

- ファイル: `html/08_conformed.html`／タイトル: `コンフォームドとドリルアクロス — データマート設計 08`
- 参照: DWT ch.4（コンフォームドディメンション、ドリルアクロス）; Soul 1–2; DT#135／再解釈: ECM, Hightouch 2

## 中心の判断
複数のファクト（クチコミ・スカウト・応募・契約）を**同じ企業・同じ会員・同じ日付で横に並べる**にはどうするか。集約テーブルを何本持つか。

## 必須内容
- §1 コンフォームドディメンションの定義と CareerVoice での該当（`dim_date`, `dim_company`, `dim_member`, `dim_job_category`, `dim_agent`）。「同じ意味・同じキー・同じ属性名」の3条件
- §2 壊れ方: (a) `fct_review` と `fct_scout` で `company_key` の SCD2 版がずれる（片方が現在値）→ドリルアクロスで行が消える (b) 2つのファクトを直接 JOIN して fan-out（`C001` の 3 クチコミ × 5 スカウト = 15 行） (c) 集約テーブルを問いごとに作って 20 本になり、どれが正か分からなくなる
- §3 原典: ドリルアクロス＝「ファクトごとに同じ粒度に集約してから FULL OUTER JOIN」（Soul 2）、バスマトリクスの列がコンフォームドの正本、DT#135 のアジャイルとの関係、Soul 1 のドリルダウン=属性を足すだけ
- §4 再解釈: ECM の「エンティティ表に指標を持たせる」（`agg_company_entity`）は、ドリルアクロスを**事前に済ませたエンティティ OBT** として位置づける。指標は時間窓付き（`_30d`, `_90d`）で持ち、正本は各ファクト
- §5 実装: (a) ドリルアクロスの SQL（`fct_review`→企業×月、`fct_scout`→企業×月、`fct_application_pipeline`→企業×月 をそれぞれ集約して `FULL OUTER JOIN USING (company_key, month_key)`）(b) `agg_company_entity` の dbt モデル（各ファクトからの窓付き集約 + `dim_company` の現在値属性、`review_count_total`, `avg_overall_score_90d` は `sum/count` から算出）(c) BigQuery マテリアライズド・ビューで日次集約を自動維持する選択肢と制約（結合・非加法の制限）
- §6 判断基準: 「集約を持つ条件」の表（クエリ頻度 × 元ファクト行数 × 再集約可能性）と、「エンティティ表に指標を入れる条件」の表
- §7 演習: (a) 「クチコミ平均が上がった企業は応募率も上がるか」を答える SQL の骨格（どのファクトを何で結ぶか） (b) `agg_company_entity` に `avg_overall_score_90d` を入れるとき、04 回の原則（平均を持たない）と矛盾しないか (c) `dim_member` を中心にした `agg_member_entity` に何を持つか（匿名性の固定判断を踏まえて）

## 図
なし（ドリルアクロスは SQL と表で足りる）。
