# 07 star か One Big Table か

- ファイル: `html/07_star_vs_obt.html`／タイトル: `star か One Big Table か — データマート設計 07`
- 参照: DWT ch.1（なぜディメンショナルか）; Manifesto／再解釈: Fowler, Fivetran OBT, Hightouch 2, BQ partition

## 中心の判断
列指向 DWH（BigQuery）でスタースキーマを保つ理由は**性能ではなく意味**。何を star で持ち、何を OBT（非正規化ワイドテーブル）として配るか。**star を「正本」、OBT を「配布物」**にする層構成。

## 必須内容
- §1 3つの形（star / snowflake / OBT）の比較表（結合数 / 冗長 / 更新時の整合 / BI からの使いやすさ / パーティション・クラスタの効き方）
- §2 壊れ方: (a) OBT だけを正本にして `dim_company.name` の Type1 更新が全行の書き換えになる（`fct_page_view` 数億行） (b) OBT に `dim_member` の SCD2 属性を焼き込んだ後で「現在値で見たい」が出て再生成 (c) star のまま BI に渡して Looker Studio でアナリストが結合を間違える（fan-out）
- §3 原典: Manifesto の「理解しやすさ・性能・拡張への耐性」。DWT ch.1 の「正規化は DWH の敵」の文脈は行指向 DB の時代のもの、という前置き
- §4 再解釈: Fowler「性能のための技法は捨てる、意味のための技法は残す」を軸に、Fivetran の実測（BigQuery で OBT が 49% 速い）と Hightouch 2 の「活用側から逆算」を並べる。**BigQuery 固有**: ブロードキャスト結合（小さい dim）、パーティションプルーニングはファクト側の日付列にしか効かない、クラスタリングは `company_key` 等の高カーディナリティ列、`ARRAY<STRUCT>` のネスト
- §5 実装: (a) `fct_scout` の `config(partition_by={'field':'sent_date','data_type':'date'}, cluster_by=['scout_sender_key','member_key'])` (b) OBT `obt_scout_funnel`（`fct_scout_funnel` + `dim_member`(as-of) + `dim_scout_sender` + `dim_job_posting` を結合済み）を **marts の下流に `materialized='table'` で置く** dbt モデル (c) `require_partition_filter=true` の設定と、BI から `sent_date` で絞る前提 (d) スキャン量の見積り: `INFORMATION_SCHEMA.PARTITIONS` / dry-run の使い方
- §6 判断基準: 「利用者（アナリスト / BI ツール / 自分）× 更新頻度 × 行数 → star のまま / OBT を配布 / OBT のみ」の表
- §7 演習: (a) `fct_page_view`（数億行）を OBT 化すべきか。クラスタリング列は何か (b) `agg_company_entity` は OBT か集約か（→ 08 回） (c) `obt_scout_funnel` の `member` 属性は as-of（送信時点）か現在値か、両方持つか

## 図（1枚）
**star と OBT のスキャン範囲**（比較図型）: 左=star（`fct_scout` を `sent_date` でプルーニング + 小さい dim をブロードキャスト結合）、右=OBT（ワイド1表を同じ日付で切る）。「読む列数」と「読むパーティション」の差だけ accent。ノード ≤9、矢印 ≤6。
