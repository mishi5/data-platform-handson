# 09 増分・遅延到着・冪等性

- ファイル: `html/09_incremental.html`／タイトル: `増分・遅延到着・冪等性 — データマート設計 09`
- 参照: DWT ch.19–20（ETL、遅延到着ファクト/ディメンション）; ETL Subsystems／再解釈: FDE（不変パーティション・冪等）, dbt incremental BQ

## 中心の判断
ファクトをどう増分で作り、遅れて届いたデータをどう吸収し、**同じ日を2回流しても同じ結果**にするか。

## 必須内容
- §1 増分の3方式の表（`append` / `merge` / `insert_overwrite`）× BigQuery での挙動（DML 制限、パーティション置換、コスト）。CareerVoice の各ファクトへの割当（`fct_page_view`=insert_overwrite 日次、`fct_scout`=insert_overwrite、`fct_application_pipeline`=merge（行が更新される累積型）、`fct_contract_monthly`=月パーティション置換）
- §2 壊れ方: (a) `WHERE sent_at > (SELECT MAX(sent_at) FROM {{ this }})` で、6/20 に遅れて 6/18 分が届き永久欠損 (b) 累積スナップショット `fct_application_pipeline` を `append` にして `P001` が7行になる (c) **遅延到着ディメンション**: `C002` の規模変更（5/1）が DWH に届くのが 5/3 で、5/1–5/2 のファクトが旧版 `company_key` に紐づいたまま (d) 冪等でない処理を再実行して二重計上
- §3 原典: ETL Toolkit の遅延到着ファクト（過去日付のサロゲートキーを当時の版で解決）と遅延到着ディメンション（仮キー→後で更新）。監査ディメンションによる追跡
- §4 再解釈: FDE「パーティションを不変の単位にして丸ごと上書き」「タスクは純関数」。dbt の `insert_overwrite` + `partitions` 引数がこれをそのまま実装する。ルックバック窓の考え方（遅延の分布から決める。ここでは 3 日）
- §5 実装: (a) `fct_scout` の dbt モデル: `materialized='incremental'`, `incremental_strategy='insert_overwrite'`, `partition_by`, `partitions = dbt.partition_range(...)` または `{% if is_incremental() %} WHERE sent_date >= DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 3 DAY)` の形。**ルックバック内は全パーティション置換**で冪等 (b) `fct_application_pipeline` の `merge`（`unique_key='application_id'`）と、対象を「ルックバック内に `selection_events` があった `application_id`」に絞る CTE (c) 遅延到着ディメンションの修復: `dim_company` の版が後から届いた時に `fct_review` の `company_key` を再解決する `MERGE` 文（対象パーティションだけ） (d) 冪等性の検証: 同じ `--vars run_date` で2回 `dbt run` して `SELECT COUNT(*), SUM(...)` を比較する手順
- §6 判断基準: 「ファクトの型 × 遅延の有無 × 行数 → 方式とルックバック」の表
- §7 演習: (a) `fct_page_view` のルックバックを何日にするか、決めるために何を測るか (b) `fct_job_posting_daily`（定期スナップショット）を増分で作る時の単位は「日」か「求人」か (c) `dim_member` の日次スナップショット（05 回）が1日欠けた時、as-of join はどう壊れ、どう埋めるか
