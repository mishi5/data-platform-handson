# 02 ファクトの3型とファクトレス

- ファイル: `html/02_fact_types.html`／タイトル: `ファクトの3型とファクトレス — データマート設計 02`
- 参照: DWT ch.4（トランザクション / 定期スナップショット / 累積スナップショット）; Fact Tables; DT#50（ファクトレス）#95（ヘッダ/明細）

## 中心の判断
同じソースイベントからどの型のファクトを作るか。**型は問いで決まり、ソースの形では決まらない**。

## 必須内容
- §1 3型 + ファクトレスの比較表（粒度 / 行の増え方 / 更新の有無 / 日付キーの数 / 典型の問い）。CareerVoice の10ファクトを型に分類（domain.md §3）
- §2 壊れ方: (a) `fct_job_posting_daily`（定期スナップショット）を作らず `job_postings` の `posted_at`/`closed_at` だけで「4/15 時点の掲載中求人数」を出そうとして、`closed_at` が後から埋まる問題 (b) `fct_application_pipeline` を UPDATE で更新する運用で、BigQuery のストリーミングバッファ/DML 制約に当たる話（→ 09 回へ送る） (c) `selection_events` の `rejected` と `withdrawn` を同じ「終了」に丸めて歩留まりが読めなくなる
- §3 原典: 累積スナップショットの「複数日付キー・ラグ計測・行の再訪」、定期スナップショットの半加法性、ファクトレス・ファクト（イベント記録型 / カバレッジ型）。`fct_page_view` はイベント型ファクトレス、「スカウト枠の付与」はカバレッジ型として例示
- §5 実装: `fct_application_pipeline` を **`selection_events` から PIVOT 的に組む dbt モデル**（`MIN(IF(stage='document', occurred_at, NULL))` 形式）。`-1` 日付キーの埋め方（`COALESCE(..., -1)`）。`P001` の1行がどう埋まるかを表で。`fct_job_posting_daily` を `dim_date` との範囲結合で日次展開する SQL（`J001` の 4/1〜）
- §6 判断基準: 「問い → 型」の表（例: 「今日の掲載中件数」→定期、「応募から内定までの日数分布」→累積、「日別の応募数」→トランザクション）
- §7 演習: (a) 「スカウト枠の消化」を定期スナップショットで持つべきか、`fct_scout` を集計すれば済むか (b) `S002`（未開封）は `fct_scout_funnel` でどの列がどう入るか (c) `page_views` の `is_unlocked` はメジャーかディメンションか

## 図（1枚）
