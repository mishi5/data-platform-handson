# 03 ディメンションの設計

- ファイル: `html/03_dimensions.html`／タイトル: `ディメンションの設計 — データマート設計 03`
- 参照: DWT ch.3, ch.6（サロゲートキー、退化、ロールプレイング、ジャンク、ミニディメンション、NULL）; SK; DT#5 #43 #46 #83 #100 #127／再解釈: dbt Kimball（`generate_surrogate_key`）, ECM

## 中心の判断
サロゲートキーは BigQuery + dbt で本当に要るか（**要る条件は SCD2 だけ**、それ以外は自然キーでよい）。属性をどのディメンションに置くか。

## 必須内容
- §1 技法の一覧表（技法 / 定義 / CareerVoice での適用先）: サロゲートキー、自然キー、退化（`review_id`, `scout_id`, `application_id`）、ロールプレイング（`dim_date` の 7 役割 in `fct_application_pipeline`）、ジャンク（`dim_review_attributes` 30行、`dim_page_context` 72行）、ミニディメンション（`dim_member_profile_mini` 15行）、監査（`dim_audit`）、`-1` 行
- §2 壊れ方: (a) `dim_member` に `annual_income_band` を Type2 で持って、変化のたびに行が増え `fct_page_view` の結合が肥大する→ミニディメンションへ (b) `dim_date` を作らず `DATE` 列で済ませて「営業日」「年度」がファクトごとにバラける (c) 未達日付を NULL にして `LEFT JOIN` と `COUNT` がずれる（DT#43）
- §3 原典: SK の理由（ソースキーの再利用・SCD2・性能・未知値）。DT#100 の「キーは単純に」。ミニディメンションの設計（属性の帯化、行数＝組合せ数）。ECM は「ディメンションに指標を持たせてよい」と拡張する点を §4 で
- §5 実装: (a) `dim_date` 生成（`GENERATE_DATE_ARRAY` + `-1` 行 UNION）(b) `dim_review_attributes` を `CROSS JOIN` で生成 (c) `dim_member_profile_mini` (d) サロゲートキー: `FARM_FINGERPRINT(CONCAT(member_id, '|', CAST(valid_from AS STRING)))` と dbt_utils `generate_surrogate_key` の比較表（型 / 衝突 / 可読性 / 結合コスト）。**結論: SCD2 の `dim_member`/`dim_company`/`dim_agent`/`dim_scout_sender` だけサロゲートキー、Type0/1 は自然キーをそのまま `_key` にする** を判断基準の表で (e) `dim_audit` の列と、dbt の `invocation_id` を入れるマクロ
- §6 判断基準: 「属性の変化速度 × カーディナリティ → 置き場所（本体 / ミニ / ジャンク / 退化）」の表
- §7 演習: (a) `scouts.template_id` は退化かディメンションか（テンプレ名や種別が要るなら後者） (b) `dim_page_context` に `is_unlocked` を入れるべきか、`fct_page_view` のメジャーにすべきか (c) `M001` の 6/15 の変化で `dim_member` と `dim_member_profile_mini` それぞれに何が起きるか
