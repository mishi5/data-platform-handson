# 10 レイヤ・命名・契約・テスト・監査

- ファイル: `html/10_layers_tests.html`／タイトル: `レイヤ・命名・契約・テスト・監査 — データマート設計 10`
- 参照: DWT ch.19（ETL サブシステム）; ETL Subsystems; Data Quality; DT#108 #164／再解釈: dbt Kimball, dbt structure, dbt contracts

## 中心の判断
モデルをどの層に置き、どう名付け、何をテストし、どう改版するか。**テストは粒度・参照整合性・加法性の3種を層ごとに置く**。

## 必須内容
- §1 層の表（staging / intermediate / marts(dim, fct, agg, br, obt) / snapshots）× 役割 × マテリアライズ × テストの種類。命名規約（domain.md §4）を正本として転載
- §2 壊れ方: (a) `mart_scout_v2` のようにバージョンをモデル名に入れて両方が本番参照される（改版の手順が無い） (b) staging に集約が入る／marts に型変換が入る (c) `not_null` だけで粒度が保証されず `fct_review` に `R001` が2行 (d) `dim_audit` が無く、どの実行が壊れた行を入れたか追えない
- §3 原典: ETL 34 サブシステムのうち、マート設計に直接効くもの（データプロファイリング、SCD マネージャ、サロゲートキー生成、遅延到着処理、監査ディメンション、集約ビルダー）を表で。DT#108 の「設計完了の条件」（ビジネスユーザーのレビュー、バスマトリクス更新）。Data Quality の「スクリーン」概念
- §4 再解釈: dbt structure（`stg_` は1ソース1モデル・型変換のみ、`int_` は結合・ピボット、marts は公開面）、dbt Kimball 記事の dim/fct 分離、model contracts（`enforced: true`, `data_type`, `constraints`）で列契約を BI へ保証、`versions:` による改版と `deprecation_date`
- §5 実装: (a) `schema.yml`: `fct_scout` の contract（列・型）、粒度テスト `dbt_utils.unique_combination_of_columns`、参照整合性 `relationships`（`member_key → dim_member`, `-1` の扱い: `where: "member_key != -1"`）、加法性チェック（`dbt_utils.expression_is_true`: `scouts_remaining = scout_quota - scouts_sent`）、`accepted_values` for `sender_type` (b) `dim_audit` を全ファクトに付けるマクロ `audit_key()`（`invocation_id` + `run_started_at`）(c) 改版: `fct_scout` を v2 にする時の `versions:` 設定と、`latest_version`、`ref('fct_scout', v=1)` (d) `dbt source freshness`（`loaded_at_field: updated_at`）(e) `exposures` で BI ダッシュボードを依存に登録
- §6 判断基準: 「テストを置く層と種類」の表（staging: not_null/accepted_values、intermediate: 粒度、marts: 粒度・relationships・加法性・contract）と「改版 vs 上書き」の表
- §7 演習: (a) `fct_application_pipeline` に置くべきテストを列挙し、それぞれがどの壊れ方を捕まえるか (b) `dim_company` に `industry` の分類を1階層足す変更は改版か上書きか (c) `int_review_member_link`（アクセス制限）をどの層・どのデータセットに置き、テストで何を保証するか
