# 06 多対多・不揃い階層・異種ディメンション

- ファイル: `html/06_bridges.html`／タイトル: `多対多・不揃い階層・異種ディメンション — データマート設計 06`
- 参照: DWT ch.6（supertype/subtype）, ch.7（不揃い階層）, ch.8（多値・ブリッジ）; DT#142／再解釈: BQ nested（`ARRAY<STRUCT>`）

## 中心の判断
1つのファクト行に複数のディメンション値が対応するとき、ブリッジ表・重み付け・BigQuery の `ARRAY` のどれで持つか。異種のディメンション（企業 or エージェント）をどう1つの FK に畳むか。

## 必須内容
- §1 3つの問題と手段の表: 多値（会員の希望職種）→ブリッジ + `weighting_factor` / `ARRAY`；不揃い階層（企業グループ、職種）→階層ブリッジ / 固定深さ平坦化；異種（スカウト送信主体）→supertype ディメンション / 2本の FK + `-1`
- §2 壊れ方: (a) `br_member_desired_job_category` を重みなしで `fct_scout` に結合して `M002`（希望2件）のスカウトが2倍に数えられる (b) `dim_job_category` を level3 固定にして `ENG-DATA`（level2 終端）が NULL で落ちる (c) `fct_scout.sender_company_key` と `sender_agent_key` の両方を持って、どちらかが常に `-1`、BI で「送信主体別」が UNION になる
- §3 原典: ブリッジの重み（合計=1）、「impact report」と「weighted report」の使い分け、階層ブリッジ（祖先-子孫 + depth）、supertype/subtype（共通属性を supertype、固有を subtype 表）
- §4 再解釈: BigQuery では `desired_job_categories ARRAY<STRUCT<code STRING, priority INT64, weight FLOAT64>>` を `dim_member` に持つ選択肢。`UNNEST` のコスト、BI（Looker Studio / Looker）からの見え方（UNNEST が要る＝セルフサービスに不向き）、Google の公式ガイドの位置づけ
- §5 実装: (a) `br_member_desired_job_category` 生成（`weighting_factor = 1 / COUNT(*) OVER (PARTITION BY member_id)`）と weighted report の SQL (b) `br_company_hierarchy`（`C001`→`C003` を depth 1、自己を depth 0）を再帰 CTE（`WITH RECURSIVE`）で作る SQL と、「`C001` グループのクチコミ数」を出す結合 (c) `dim_scout_sender`（supertype）の生成 SQL（`companies` と `agents` の UNION、`sender_type` + 固有属性は NULL 許容）(d) `ARRAY` 版の `dim_member` と `UNNEST` クエリ
- §6 判断基準: 「多値の個数の分布 × BI の UNNEST 可否 × 更新頻度 → ブリッジ / ARRAY」、「階層の深さの分布 × 問いの形 → 平坦化 / ブリッジ」、「異種の共通属性の割合 → supertype / 分離」の3表
- §7 演習: (a) `reviews` に将来「タグ（複数）」が付いたら、`fct_review` にどう持つか (b) `C003` が `C001` から離脱した時 `br_company_hierarchy` はどう変わるか（SCD の観点） (c) `fct_placement.agent_key` が `-1`（直接応募）のとき `dim_agent` に `-1` 行を持つべきか、`dim_scout_sender` で統一すべきか
