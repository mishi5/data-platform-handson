## 5. 判断に迷った箇所

1. **§7(b) の SQL コメントに残る「潰す」**
   地の文は「足せない軸を先に1つの値へまとめる」に直したが、直前の SQL ブロック内コメントは「先に潰してから」のまま。規約 §3「SQL は変えない」と §4「SQL コメントは検査対象外」に従って残した。地の文とコメントで表現が割れているので、SQL 変更を許容するなら `-- 足せない軸（日）を先に1つの値へまとめてから、足せる軸（求人）で足す` に揃えるのが望ましい。

2. **h2「4. 現代の再解釈 — MetricFlow の ratio metric」と `p.meta` の「再解釈: MetricFlow（ratio metric）」を英語のまま残した**
   ブリーフの手順4が「h2 は 1 と 2 だけ変える（他の h2 はそのまま）」と明示しているため見出しは不変にし、本文の初出側にだけ「比率メトリクス（ratio metric）」の訳を入れた。`ratio` は MetricFlow の YAML で実際に書く値（`type: ratio`）でもあるため、見出しの英語は API 名として通ると判断した。訳語を見出しにも入れるなら「4. 現代の再解釈 — MetricFlow の比率メトリクス（ratio metric）」。

3. **`AG01` / `AG02` を「転職エージェントの担当者」と書いた**
   題材定義では `A01`/`AG01` が「キャリアブリッジ（gold）/ 担当 佐藤」と1行にまとまっており、`A01` がエージェント会社・`AG01` が担当者という対応。この資料には `A01`/`A02` が出ないので、ID 表には `AG01`/`AG02` を担当者として載せ、所属会社名と `agency_tier` を事実欄に併記した。

4. **`M001` の事実を「2026-06-16 と 06-20 にスカウトを受け取る」にした**
   本文 §2(c) が「`M001` が `S001` に加えて 6/16 にもスカウトを受けたとする」という**この資料だけの仮定**を置いている。ID 表に 6/16 を書かないと日次3行の表が読めないため、仮定を含めた形で書いた。題材定義にある 6/15 の属性変化・8/1 の入社は、この資料では一度も使わないので省いた（ブリーフの「この資料で使わない事実は省いてよい」に従う）。

5. **`J001` の「4月中は掲載中」**
   題材定義には掲載終了日が無く、§7(b) の解答例が「4月の `SUM(is_open) = 30`」を前提にしている。ID 表には本文の前提どおり「4月中は掲載中（`open`）」と書いた（新しい設計判断や数値は足していない）。

6. **`§2a` 表記の揺れ**
