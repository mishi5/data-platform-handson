1. この資料で決めること

この資料で決めることは1つだけである。そのメジャーは再集約できるかを判定する。日次の行を月次に、企業の行を企業グループに足し上げたとき、同じ列に同じ意味が残るかどうかで、マートに持つ形が決まる。

結論は率・平均・ユニーク数はマートに持たず、分子・分母・和・件数を持つで、この題材の集約テーブル全てに適用する。半加法メジャー（残高・在庫）は「どの軸で足せないか」をモデル側で宣言する。

メジャーの3分類（DWT ch.1–2）

分類定義足せる軸集約表に持つ形
加法（additive） ファクトに紐づくすべてのディメンションで合計できる 全部 そのまま SUM
半加法（semi-additive） 一部の軸では合計できるが、少なくとも1軸では合計が無意味。残高・在庫・枠残が典型で、足せないのはたいてい時間軸 時間以外 値はそのまま。時間で足すなという宣言を付ける。時間方向は期末値か期中平均で1つの値にまとめる
非加法（non-additive） どの軸でも合計が無意味。率・平均・比・パーセンタイル・ユニーク数 なし 持たない。加法な構成要素（分子・分母、和・件数）に分解して持つ

2. よくある失敗

(a) 平均の平均 — agg_company_rating_daily に avg_overall_score を持つ

C002（ネクスト技研）の3日分を例にする。日次の集約表が件数と一緒に平均も持っていて、月次レポートがその平均をさらに AVG する。

date_keyreview_countsum_overall_score日次の avg_overall_score
2026031013.53.5
2026031115.05.0
202603121025.02.5
合計1233.5—
  • 平均の平均: (3.5 + 5.0 + 2.5) / 3 = 11.0 / 3 = 3.67
  • 正しい平均: 33.5 / 12 = 2.79

0.88 ポイントずれる。ずれの向きは常に「件数の少ない日を過大評価する側」。3/12 に炎上して 10 件の低評価が入ったのに、レポートは 3.67 という良い値を返す。

この表が四半期に上がると、月次の 3.67 がさらにもう1段平均される。ずれは粒度を上げるたびに累積する。

(b) 半加法を足す — scouts_remaining を四半期で SUM

契約 K001（C001 アオゾラ商事、premium、枠 200/月）。fct_contract_monthly は 1契約 × 1月の定期スナップショットなので、行は素直に3行ある。

month_date_keyscout_quotascouts_sentscouts_remaining
2026010120020180
2026020120060140
2026030120080120
SUM600160440

3列のうち2列は足してよい。SUM(scouts_sent) = 160 は「1〜3月に送った総数」、SUM(scout_quota) = 600 は「1〜3月に付与された総枠」で、どちらも加法なフローの量。

誤りなのは SUM(scouts_remaining) = 440 だけである。この 440 は存在しない枠で、上限まで積んでも 200 × 3 = 600 にしかならない量を「残枠」として報告している。実在するのは 3月末の 120 だけである。

企業軸では足せる。C001 と C003 の同月の残枠を足した「グループ全体の残枠」は意味がある。足せない軸が時間だけ、というのが半加法の定義そのもの。

(c) ユニーク数を足す — 日次の COUNT(DISTINCT member_key)

fct_scout から「日次のスカウト受信ユニーク会員数」を集約表に事前計算して保存し、週次レポートがその値を SUM する。週は dim_date.iso_week（月曜始まり）で切る。ここで見るのは 2026-06-15 〜 06-21 の ISO 週。

この週に入るサンプルは S003（AG02 → M002、6/18）と S001（C001 → M001、6/20）の2件。S002（AG01 → M003、6/25）は翌 ISO 週なのでこの窓に入らない。M001 が S001 に加えて 6/16 にもスカウトを受けたとする（同じ会員が週内の複数日に受け取るのは普通に起きる）。

sent_date受信会員日次のユニーク会員数
2026-06-16M0011
2026-06-18M002（S003）1
2026-06-20M001（S001）1
SUM—3
  • 日次ユニークの合計: 3
  • ISO 週 2026-06-15 の実ユニーク数: 2（M001, M002）

膨らみ方は会員1人あたりの受信日数に比例する。会員 N 人が平均 d 日受け取れば合計は N × d、つまり d 倍になる。日次を月次に上げれば d は 10 を超える。

(a) と違うのは、和と件数に分解しても直らないことである。ユニーク数は加法な構成要素を持たないので、集計済みの数値からは復元できない。原子ファクトを残すか、集約可能な概算用スケッチ（HyperLogLog。ユニーク数を近似する、足し合わせられる中間データ）を持つかの二択になる。

3. Kimball の原則

技法定義使う条件
加法・半加法・非加法の分類（DWT ch.2） ファクトの数値メジャーは3種に分かれる。全軸で足せる／一部の軸だけ足せる／どの軸でも足せない ファクト設計のたびに全メジャーへ適用する。1行が何を表すかを定める粒度宣言（DM01『粒度を宣言する』）の直後の作業
非加法メジャーの分解 非加法メジャーは、可能な限り加法な構成要素を格納し、集計後に最後の計算をする 率・平均・比のすべて。最後の割り算は BI 層／OLAP キューブで行う
定期スナップショット（DWT ch.4） 1行が「期間」を要約する。粒度は期間であってトランザクションではない。外部キーは密（活動が無くても行が立つ） 残高・在庫・枠残。fct_contract_monthly, fct_job_posting_daily
残高の扱い 残高は時間以外の全軸で加法。時間方向は期末値か期中平均で1つの値にまとめる 半加法メジャーを期間集計するとき。どちらを出すかを指標定義として決めておく
集約ファクト（aggregate fact table） 原子ファクトの単純な数値ロールアップ。クエリ性能のためだけに作り、原子ファクトと同時に BI へ公開する 「性能のため」なので、原子から出る答えと一致しなければならない。平均を事前計算して列に持つと一致しなくなる
サマリーだけを持たない（DT#77） 詳細データは予測不能な形にロールアップできるが、逆は不可能。サマリーを構成要素へ「爆発」させることはできない パーセンタイル・中央値・ユニーク数のように、そもそも分解して持てないメジャーの置き場所を決めるとき

DWT / Kimball Dimensional Modeling Techniques（加法性）

“Semi-additive measures can be summed across some dimensions, but not all; balance amounts are common semi-additive facts because they are additive across all dimensions except time. Finally, some measures are completely non-additive, such as ratios. A good approach for non-additive facts is, where possible, to store the fully additive components of the non-additive measure and sum these components into the final answer set before calculating the final non-additive fact. This final calculation is often done in the BI layer or OLAP cube.”

この資料の判断（avg_* を持たず sum_* + count を持つ）は、この一文をそのままテーブル設計規約にしたものである。

Design Tip #77（Margy Ross, 2006）

“While you can roll up detailed data in unpredictable ways, the converse is not true – you can’t magically explode summary data into its underlying components.”

“Summary data naturally pre-supposes the typical business questions. When the business requirements change, as they inevitably will, then both the data model and ETL system must change to accommodate new data.”

加法性の議論は突き詰めると DT#77 に行き着く。集約表は原子ファクトの代替ではなく高速化の手段で、原子が残っている限り「持つ形を間違えた」は後から直せる。中央値やユニーク数を集約表に事前計算して保存し、原子を捨てた瞬間に直せなくなる。

パーセンタイルが再集約できないのは、原典の定義から出る帰結である。分位点は「値の分布」に対する関数で、分位点どうしの和にも平均にも分布の情報は残らない。日次 p95 を7日ぶん平均した数字は、週次 p95 とは別物であり、対応する定義が存在しない。

4. 現代の再解釈 — MetricFlow の ratio metric

dbt Semantic Layer（MetricFlow）は、この資料の判断をテーブルの外側で表現する道具である。メトリクスを YAML で宣言すると、クエリのたびに「その粒度で分子と分母を集計してから割る」SQL が生成される。比率メトリクス（ratio metric）は numerator（分子）/ denominator（分母）をメトリクス名で受け取るので、率そのものを列として持つ場所がどこにも無い。

YAML は dbt v1.12 以降の仕様で書く。セマンティックモデルは models: の中に入り、エンティティ（entity）とディメンション（dimension）は columns: で宣言する（旧仕様のトップレベルにあった semantic_models: と measures: は置き換えられた）。

# models/marts/_marts__models.yml — dbt v1.12+ の spec
# セマンティックモデルはモデル定義の中に入り、entity / dimension は columns で宣言する
models:
  - name: fct_scout_funnel
    description: "1行 = 1スカウトの送信→開封→返信→応募"
    semantic_model:
      enabled: true
      agg_time_dimension: sent_date
    columns:
      - name: scout_id
        entity:
          type: primary
          name: scout
      - name: member_key
        entity:
          type: foreign
          name: member
      - name: scout_sender_key
        entity:
          type: foreign
          name: scout_sender
      - name: sent_date
        granularity: day
        dimension:
          type: time
    metrics:
      - name: scouts_sent
        label: スカウト送信数
        type: simple
        agg: count_distinct
        expr: scout_id
      - name: scouts_replied
        label: スカウト返信数
        type: simple
        agg: sum
        expr: is_replied

# 複数モデルにまたがる metric（ratio を含む）はトップレベルの metrics に置く
metrics:
  - name: reply_rate
    label: スカウト返信率
    description: "返信数 ÷ 送信数。どの粒度で切っても分子分母を先に集計してから割る"
    type: ratio
    numerator: scouts_replied
    denominator: scouts_sent

メトリクス名はプロジェクト内で一意でなければならない。fct_scout_funnel 由来の scouts_sent（送ったスカウトの本数）と fct_contract_monthly 由来の contract_scouts_sent（契約枠の消化数）は数え方も分母も違う指標なので、名前を分ける。§6 の「名前を分ける」がそのままメトリクス層の制約になっている。

粒度宣言（1行が何を表すかの宣言。DM01『粒度を宣言する』で扱う）と entity の宣言は一致していなければならない。fct_contract_monthly の粒度は 1契約 × 1月なので、contract_id は月数ぶん重複する。type: primary と書くと「この列が行を一意に識別する」という嘘の宣言になり、contract エンティティ経由の結合で行が増幅する。

一意なのは (contract_id, month_date) の組である。MetricFlow のエンティティは複合キーを取らないので、primary を宣言したいならモデル側に連結した代理列（contract_month_id のような1列）を足す。足さないなら type: foreign のままでよく、simple / ratio metric はそれで作れる。

半加法も宣言できる。non_additive_dimension は「このメジャーはこの時間ディメンションでは集約するな」という指定で、window_agg: max が期末値、min が期首値にあたる（旧 spec ではこのキーが window_choice）。Kimball が運用ルールとして書いていた「残高は期末の値だけを採る」が、そのままメタデータになった。

models:
  - name: fct_contract_monthly
    description: "1行 = 1契約 × 1月"
    semantic_model:
      enabled: true
      agg_time_dimension: month_date
    columns:
      # 粒度は 1契約 × 1月。contract_id 単独では行を一意にできないので primary にしない
      - name: contract_id
        entity:
          type: foreign
          name: contract
      - name: company_key
        entity:
          type: foreign
          name: company
      - name: month_date
        granularity: month
        dimension:
          type: time
    metrics:
      - name: scouts_remaining
        label: スカウト残枠（期末）
        type: simple
        agg: sum
        expr: scouts_remaining
        non_additive_dimension:
          name: month_date
          window_agg: max         # 期間内の最終月の値だけを採る（min なら期首値）
      - name: contract_scouts_sent
        label: 契約枠の消化数
        type: simple
        agg: sum
        expr: scouts_sent         # こちらは素直に加法

何が変わり、何が残るか

  • 残る: 「率と平均をテーブルに事前計算して持たない」という判断そのものである。MetricFlow は分子分母が列として存在することを前提にしており、fct_scout_funnel に is_replied が無ければ比率メトリクスは定義できない。物理設計の要求は変わらない
  • 変わる: 割り算のロジックの置き場所。かつては BI ツール／ダッシュボードごとに散っていた「SUM してから割る」が、リポジトリ内の1定義に集まる。「返信率」の定義が2つに割れる事故（複数のファクトで共有する同一定義のディメンション＝コンフォームドディメンションと同じ構図の問題で、DM08『コンフォームドとドリルアクロス』で扱う）が減る
  • 変わる: 半加法の宣言が実行可能になった。テーブルのコメントや Wiki に書いてあった「時間で足すな」が、集計エンジンが従う指定になる
  • 変わらない危険: Semantic Layer を通らない経路（アドホック SQL、直接 BigQuery を参照する BI、DWH から業務システムへ書き戻す Reverse ETL）が1本でもあるなら、メトリクス定義は守ってくれない。テーブル側で和と件数を持つ規律は依然として必要で、Semantic Layer はその上の層

5. BigQuery + dbt での実装

集約ファクト（DWT ch.2 の aggregate fact table）: 平均を持たず和と件数を持つ

-- models/marts/agg_company_rating_daily.sql
{{ config(
    materialized='table',
    partition_by={'field': 'rating_date', 'data_type': 'date'},
    cluster_by=['company_key']
) }}

WITH review AS (
    SELECT * FROM {{ ref('fct_review') }}
)

SELECT
    submitted_date_key AS date_key,
    submitted_date     AS rating_date,
    company_key,
    COUNT(*) AS review_count,
    SUM(score_compensation)   AS sum_score_compensation,
    SUM(score_morale)         AS sum_score_morale,
    SUM(score_openness)       AS sum_score_openness,
    SUM(score_respect)        AS sum_score_respect,
    SUM(score_growth_20s)     AS sum_score_growth_20s,
    SUM(score_long_term_dev)  AS sum_score_long_term_dev,
    SUM(score_compliance)     AS sum_score_compliance,
    SUM(score_eval_fairness)  AS sum_score_eval_fairness,
    SUM(overall_score)        AS sum_overall_score
FROM review
GROUP BY date_key, rating_date, company_key

この表には avg_ で始まる列が1つも無い。review_count と sum_* だけが並ぶ。列名の規約を「集約表に avg_・rate_・pct_・unique_ を出さない」とすると、レビューで機械的に弾ける。

# models/marts/schema.yml
models:
  - name: agg_company_rating_daily
    description: |
      1行 = 1企業 × 1日。fct_review の単純ロールアップ（性能のための集約ファクト）。
      平均・率は列に持たない。avg は SAFE_DIVIDE(SUM(sum_*), SUM(review_count)) で都度計算する。
    data_tests:
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [date_key, company_key]
    columns:
      - name: date_key
        data_tests: [not_null]
      - name: rating_date
        description: "パーティション列。date_key と同じ日を DATE で持つ"
        data_tests: [not_null]
      - name: company_key
        data_tests: [not_null]
      - name: review_count
        data_tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 1
              inclusive: true
      - name: sum_overall_score
        data_tests: [not_null]

月次へ再集約する

SELECT
    d.year,
    d.month,
    c.company_id,                          -- SCD2 版ではなく自然キーで束ねる
    SUM(a.review_count)      AS review_count,
    SUM(a.sum_overall_score) AS sum_overall_score,
    SAFE_DIVIDE(SUM(a.sum_overall_score), SUM(a.review_count)) AS avg_overall_score
FROM {{ ref('agg_company_rating_daily') }} AS a
JOIN {{ ref('dim_company') }} AS c
    ON a.company_key = c.company_key       -- 投稿時点の版から自然キーを引く
JOIN {{ ref('dim_date') }} AS d
    ON a.date_key = d.date_key
-- 絞り込みはパーティション列（rating_date）で。date_key で書くと全パーティションを読む
WHERE a.rating_date BETWEEN DATE '2026-03-01' AND DATE '2026-03-31'
GROUP BY d.year, d.month, c.company_id

C002 の3日分に対しては 33.5 / 12 = 2.79 が返る。a.company_key でグループ化しないのは、C002 が 2026-05-01 に employee_size_band を変えて2版になるためである。SCD2 版で束ねると年内の集計がその境で2行に割れる（足し上げの単位は企業という実体）。

SAFE_DIVIDE は素の集計では出番が無い（この表は 0 件の日に行を立てないので review_count >= 1 が保証される）。有効になるのは後段で dim_date 側から 0 件月を LEFT JOIN で埋めたときで、分母 0 をエラーではなく NULL にして通す保険である。

企業グループへ再集約する（br_company_hierarchy 経由）

SELECT
    anc.company_id AS group_company_id,    -- SCD2 版ではなく自然キーで束ねる
    d.year,
    SUM(a.review_count)      AS review_count,
    SAFE_DIVIDE(SUM(a.sum_overall_score), SUM(a.review_count)) AS avg_overall_score
FROM {{ ref('agg_company_rating_daily') }} AS a
JOIN {{ ref('br_company_hierarchy') }} AS b
    ON a.company_key = b.descendant_company_key   -- 子孫側は全 SCD2 版を持つ
JOIN {{ ref('dim_company') }} AS anc
    ON b.ancestor_company_key = anc.company_key
   AND anc.is_current                             -- 祖先側は現行版だけ
JOIN {{ ref('dim_date') }} AS d
    ON a.date_key = d.date_key
WHERE a.rating_date BETWEEN DATE '2026-01-01' AND DATE '2026-12-31'
GROUP BY group_company_id, d.year

C001（アオゾラ商事）を ancestor とする行には、自分自身（depth = 0）と子会社 C003（ヒノデ物流、depth = 1）が入る。集計式（SUM と SAFE_DIVIDE）が月次のときと1文字も変わらないのが、和と件数で持つことの実利である。

ただしキーの扱いには前提が要る。agg_company_rating_daily.company_key は投稿時点の SCD2 版なので、br_company_hierarchy の子孫側は dim_company の全 SCD2 版に展開して作る（br_member_desired_job_category と同じ理由）。現行版のキーしか持たないブリッジだと、C002 のように年内に属性が変わった企業の投稿が、結合で静かに除外される。

祖先側も同じく全 SCD2 版で持ち、クエリ側で anc.is_current の1版に絞ってから company_id（自然キー）でグループ化する。この is_current が無いと、祖先 C001 の版の数だけ同じ子孫行が複製され、結合による行の増幅が起きる。足し上げの単位は企業という実体であって、SCD2 の版ではない。

もし日次に平均を持っていたら、時間方向とグループ方向で別々の重み付けロジックを書くことになり、片方を必ず間違える。

半加法を期末値にまとめる

-- 四半期末（3月）時点の残枠。QUALIFY で行を絞る
SELECT
    company_key,
    contract_id,
    month_date,
    scouts_remaining AS scouts_remaining_month_end
FROM {{ ref('fct_contract_monthly') }}
WHERE month_date BETWEEN DATE '2026-01-01' AND DATE '2026-03-01'   -- パーティション列で絞る
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY contract_id
    ORDER BY month_date DESC
) = 1

K001 について scouts_remaining = 120（3月の行）が返る。SUM の 440 ではない。期中平均が欲しいなら同じ窓で AVG(scouts_remaining) を使う（= 440 / 3 = 146.67）。

どちらを「残枠」と呼ぶかは指標定義であって、SQL の都合ではない。決めて名前を分ける（scouts_remaining_month_end と avg_scouts_remaining）。

SELECT
    contract_id,
    AVG(scouts_remaining) AS avg_scouts_remaining,   -- 期中平均残枠
    SUM(scouts_sent)      AS scouts_sent             -- こちらは素直に加法
FROM {{ ref('fct_contract_monthly') }}
WHERE month_date BETWEEN DATE '2026-01-01' AND DATE '2026-03-01'
GROUP BY contract_id

パーセンタイルは原子ファクトから直接（DT#77）

SELECT
    r.company_key,
    d.year,
    COUNT(*) AS review_count,
    APPROX_QUANTILES(r.overall_score, 100)[OFFSET(50)] AS p50_overall_score,
    APPROX_QUANTILES(r.overall_score, 100)[OFFSET(90)] AS p90_overall_score
FROM {{ ref('fct_review') }} AS r
JOIN {{ ref('dim_date') }} AS d
    ON r.submitted_date_key = d.date_key
GROUP BY r.company_key, d.year

指針: パーセンタイルを集約表に列として事前計算して保存するのは、その粒度でしか使わないと確定している場合だけである。事前計算した p50 は上位粒度へ持ち上げられないので、年次が要るなら年次でもう一度原子から計算する。fct_review は 1行 = 1クチコミなので、企業 × 年程度の集計ならスキャン量は問題にならない。

ユニーク数はスケッチで持つ

-- HLL スケッチなら「日次で作って週次でマージ」ができる
WITH daily AS (
    SELECT
        sent_date,
        HLL_COUNT.INIT(member_key) AS member_sketch
    FROM {{ ref('fct_scout') }}
    WHERE sent_date BETWEEN DATE '2026-06-15' AND DATE '2026-06-21'
    GROUP BY sent_date
)

SELECT
    DATE_TRUNC(sent_date, ISOWEEK) AS iso_week_start,
    HLL_COUNT.MERGE(member_sketch) AS weekly_unique_members
FROM daily
GROUP BY iso_week_start

§2(c) と同じ ISO 週（6/15〜6/21）を読むので、返るのは weekly_unique_members = 2 である。日次ユニークを足した 3 ではない。

HLL_COUNT.INIT が返す BYTES のスケッチはマージ可能で、これが「ユニーク数の加法な構成要素」にあたる。誤差は数 % 入るので、正確な値が要る監査系の数字には使わない。厳密さが要るなら原子ファクトから COUNT(DISTINCT ...) を都度実行する。

6. 判断基準

メジャー分類マートに持つ形BI / クエリ側で計算する形
review_count, scout_count, view_count, fee_amount 加法 そのまま1列 SUM(x)
平均スコア（overall_score, score_*） 非加法 sum_overall_score + review_count SAFE_DIVIDE(SUM(sum_overall_score), SUM(review_count))
率（返信率・応募率・公開率） 非加法 分子 is_replied の和 と 分母の件数 SAFE_DIVIDE(SUM(is_replied), COUNT(*)) / MetricFlow の ratio metric
加重比率（fee_rate） 非加法 fee_amount と annual_income SAFE_DIVIDE(SUM(fee_amount), SUM(annual_income))。AVG(fee_rate) ではない
平均リードタイム（days_applied_to_offer） 非加法 原子は素の値。集約するなら和と件数 SAFE_DIVIDE(SUM(days), COUNT(*))。NULL（未達）を分母に含めるかを定義で決める
残高（scouts_remaining） 半加法（時間 ✗） スナップショットの値のまま。non_additive_dimension で時間軸を宣言 期末値 = QUALIFY ROW_NUMBER() ... ORDER BY 期 DESC = 1／期中平均 = AVG
状態フラグ（is_open, is_active） 半加法（時間 ✗） 0/1 のまま 時点数 = 期末行の SUM／延べ日数 = 期間の SUM。名前を分ける
中央値・p95 非加法・分解不能 持たない（原子ファクトを残す） APPROX_QUANTILES(x, 100)[OFFSET(50)] を原子から都度
ユニーク数 非加法・分解不能 持たない。必要なら HLL_COUNT.INIT のスケッチ列 COUNT(DISTINCT x) を原子から／HLL_COUNT.MERGE
1エンティティ1行の終端テーブル（agg_company_entity） — 平均・率を持ってよい（再集約しない契約） そのまま表示する。この表を足し上げる分析を書かないのが条件（終端テーブルの設計は DM08『コンフォームドとドリルアクロス』で扱う）

運用上の着地点を1つ挙げる。集約表の列名から avg_ / rate_ / pct_ / median_ / unique_ を禁止する。分類の議論は設計時にしかできないが、列名の検査は CI でできる。

例外を作るのは「終端テーブル」だと宣言した agg_company_entity だけである。

7. 演習

(a) fct_review.overall_score の「企業別・年別の中央値」を出すために何を持つか

解答例

何も新しく持たない。fct_review（1行 = 1クチコミ）を残しておくことが答えになる。agg_company_rating_daily の sum_overall_score と review_count からは中央値を復元できない（和と件数は分布の情報を持たない）。

判断基準表の「中央値・p95 → 分解不能 → 持たない」の行にあたる。

SELECT
    r.company_key,
    d.year,
    APPROX_QUANTILES(r.overall_score, 100)[OFFSET(50)] AS median_overall_score
FROM {{ ref('fct_review') }} AS r
JOIN {{ ref('dim_date') }} AS d
    ON r.submitted_date_key = d.date_key
GROUP BY r.company_key, d.year

「毎朝ダッシュボードで見るので事前計算して保存したい」なら、企業 × 年の粒度で専用の集約表を作る。ただしその表の中央値は四半期にも全期間にも持ち上げられない、と明記する。粒度ごとに別テーブルが増えるのを避けたいなら、原子から都度計算する方を選ぶ（DT#77）。

(b) fct_job_posting_daily.is_open を月で SUM したら何を意味するか。「月末時点の掲載数」はどう出すか

解答例

SUM(is_open) は延べ掲載日数（posting-days）にあたる。求人 J001（C001 のデータエンジニア、2026-04-01 掲載、4月中は open）なら 4月の SUM(is_open) = 30。

この 30 は「30 件の求人」ではなく、1件の求人 × 30 日を表す。

延べ日数それ自体は意味のあるメジャー（掲載枠の消化量、掲載単価の分母）なので、間違いなのは値ではなく名前である。open_posting_days のように別名にすれば加法なメジャーとして扱える。

-- 月末時点の掲載数: 足せない軸（日）を先に潰してから、足せる軸（求人）で足す
WITH month_end AS (
    SELECT
        f.company_key,
        f.is_open,
        d.year,
        d.month
    FROM {{ ref('fct_job_posting_daily') }} AS f
    JOIN {{ ref('dim_date') }} AS d
        ON f.snapshot_date_key = d.date_key
    -- パーティション列（snapshot_date）で絞る。dim_date は年月のラベル取得だけに使う
    WHERE f.snapshot_date BETWEEN DATE '2026-04-01' AND DATE '2026-04-30'
    -- QUALIFY は GROUP BY / HAVING の後に評価される。同じ SELECT に GROUP BY を置くと
    -- snapshot_date_key（非グループ列）を QUALIFY で参照できないので、絞り込みを CTE に分ける
    QUALIFY f.snapshot_date_key = MAX(f.snapshot_date_key) OVER (PARTITION BY d.year, d.month)
)

SELECT
    company_key,
    year,
    month,
    SUM(is_open) AS open_postings_month_end
FROM month_end
GROUP BY company_key, year, month

J001 だけなら open_postings_month_end = 1。QUALIFY で行を 4/30 に絞ってから求人をまたいで足す＝足せる軸（求人）でだけ足している。半加法の扱いは「足せない軸を先に1つの値へまとめる」で常に同じ形になる。

(c) 返信率を「スカウト送信主体別」に見るとき、分子分母をどの粒度で持つか

解答例

分子分母は同じ行から出すのが原則である。fct_scout_funnel（1行 = 1スカウトの送信→開封→返信→応募）は scout_sender_key を外部キーに持ち、is_replied を 0/1 で持つので、分母 = 行数、分子 = SUM(is_replied) で足りる。

集約表を作るなら粒度は sent_date_key × scout_sender_key、列は「送信件数」と「返信件数」の2つだけにする。率の列は作らない。

SELECT
    s.sender_type,
    COUNT(*)                                  AS scouts_sent,
    SUM(f.is_replied)                         AS scouts_replied,
    SAFE_DIVIDE(SUM(f.is_replied), COUNT(*))  AS reply_rate
FROM {{ ref('fct_scout_funnel') }} AS f
JOIN {{ ref('dim_scout_sender') }} AS s
    ON f.scout_sender_key = s.scout_sender_key
GROUP BY s.sender_type

注意点が2つある。

  • 返信日ではなく送信日で数える。分子を replied_date_key 基準、分母を sent_date_key 基準にすると、月をまたいだ返信の分だけ率がずれる（月末に送ったスカウトの返信は翌月に入る）。累積スナップショットは送信の行が更新されていく形なので、両方を送信日で数えれば整合する。
  • 送信主体別の率を平均しない。C001（企業としての送信）が 100 通送って 12 返信 = 12%、AG01（エージェントとしての送信）が 50 通送って 12 返信 = 24%。この2つを平均すると 18% だが、全体の返信率は 24 / 150 = 16% である。§2(a) と同じ誤りが、時間軸ではなく送信主体軸で起きる。

なお dim_scout_sender は SCD2 なので、scout_sender_key は送信時点の版を指す。「エージェント AG01 の agency_tier が gold だった期間の返信率」はそのまま出る。現在の階級（agency_tier）で束ねたいなら is_current の行へ自然キーで再結合する（属性の版をどう持ち、どの版に結ぶかは DM05『履歴を持つ：SCD とスナップショット』で扱う）。

8. 参考: 手元の基盤ではどうか

  • mart_url_performance は url_path × date 粒度で avg_response_time・error_rate_percent・unique_visitors（COUNT(DISTINCT client_ip)）を持つ。週次に上げると §2 の (a)(b)(c) が3つとも同時に起きる形になっている。
  • この資料の基準なら、error_rate_percent は分子（client_error_count + server_error_count）も分母（total_requests）も既に列にあるので、率の列を削っても情報は 1 ビットも失われない。avg_response_time は sum(response_time_sec) を並べて初めて同じ状態になる。
  • percentile() マクロの APPROX_QUANTILES(x, 100)[OFFSET(p)] を日次テーブルに事前計算して保存すると、その p95 は週次へ持ち上げられない。原子（stg_access_logs）から都度計算する経路を残しておくかどうかが、この資料の判断が分かれる点である。
  • 種: unique_visitors を HLL_COUNT.INIT(client_ip) のスケッチ列に置き換え、HLL_COUNT.MERGE で週次・月次を出して COUNT(DISTINCT) の実測値と誤差を比べてみる。
