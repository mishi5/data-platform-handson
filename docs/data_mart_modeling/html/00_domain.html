2. 題材: CareerVoice

架空のサービス CareerVoice。社員・元社員の企業クチコミを軸に、求人掲載・直接スカウト・エージェントスカウト・応募選考を1つのプラットフォームで提供する。収益源が4種類あり、それぞれ別のビジネスプロセスから発生する点が設計上の要になる。

機能概要収益
クチコミ会員が在籍/退職した企業を8軸で採点しテキストを書く。審査を通ると公開閲覧権限（投稿するか課金するか）で会員を集める
求人企業（またはエージェント）が求人を掲載掲載プラン月額
直接スカウト企業の採用担当が会員へ直接スカウト契約プランの月次スカウト枠
エージェントスカウト転職エージェントの担当者が会員へスカウト入社時の成果報酬（年収 × 料率）
応募・選考検索/スカウト経由で応募、書類→面接→内定→入社—
Kimball（DWT ch.18 / Techniques「Gather Business Requirements and Data Realities」）: 設計に入る前に、業務側の要求とソースデータの現実を同時に掴めと言う。要求は業務代表との対話で KPI・意思決定プロセス・分析ニーズとして引き出し、データの現実はソース側の担当者への聞き取りと高レベルのプロファイリングで確かめる。片側だけで進めると、実装できないモデルか、誰も使わないモデルのどちらかになる。
以下の5つが CareerVoice での「要求」側、§3 が「現実」側にあたる。

分析側が答えたい問い

  • クチコミ数・評価スコアの推移と、求人応募率・スカウト返信率への影響
  • スカウト送信主体（企業 vs エージェント）別の開封→返信→応募→入社ファネル
  • 応募から入社までのリードタイムと歩留まり（職種・企業規模・チャネル別）
  • 契約枠の消化率、MRR、成果報酬売上
  • 会員属性（年収帯・転職意欲）の変化前後での行動差

この5つは全回の演習の種になる。5つ目だけが他と質的に違い、「今の属性」ではなく「そのイベントが起きた時点の属性」を要求する。これが 05回（SCD と as-of join）の存在理由で、サンプル値の M001 が 2026-06-15 に job_change_intent を passive → active へ変え、06-20 に S001 を受け取り、06-23 に応募する、という並びで検証する。

3. ソースシステムの簡易モデル

OLTP は BigQuery の src_careervoice データセットに Datastream（CDC）で複製されている前提。行が更新されるテーブル（members, member_desired_job_categories, companies, agencies, agents, reviews, job_postings, contracts）だけが updated_at を持ち、論理削除 deleted_at を持つのは members だけである。残る9表（job_categories, industries, prefectures, review_moderation_events, scouts, applications, selection_events, placements, page_views）は追記型で更新列を持たない。

scouts の opened_at / replied_at / reply_type だけが例外で、更新列を持たないまま後から値が埋まる。列は以下が全てで、以降の回もこれ以外を持ち出さない。

ER 図（主要9テーブル）

図に出していない外部キーが4本ある。members.current_company_id → companies、companies.parent_company_id → companies（自己参照、C003 の親が C001）、agents.agency_id → agencies、job_postings.agency_id → agencies（J002 が A01 経由であることの根拠）。仲介会社そのもの（agencies）、参照マスタ（job_categories, industries, prefectures）、多値の member_desired_job_categories、審査ログの review_moderation_events、成果報酬の placements、イベントログの page_views も図からは省いた。

塗ったテーブルも reviews.status や scouts.opened_at のように後から列が更新される。追記と更新が混ざる点が 02回（ファクトの型）と 05回（履歴の持ち方）の論点になる。

OLTP としての設計意図

この形はアプリケーションの都合で正しい。job_categories は parent_code による自己参照で階層を持ち、industries や prefectures はコード表に切り出されている。重複を消して更新を1箇所に閉じる、正規化の教科書どおりの形だ。

状態は列で持つ。reviews.status、job_postings.status、contracts.status、scouts.opened_at/replied_at はいずれも行を上書きして遷移する。members の削除も deleted_at を立てるだけで、行は消えない。

つまり OLTP を素直に読むと「今」しか分からない。C002 の employee_size_band が 2026-05-01 に 50_299 から 300_999 へ変わったとき、その前に投稿された R001 を「当時の規模」で集計する手段はソース側に無い。

Kimball（Manifesto, 1997）: ER モデリングはトランザクション処理には適切で、そこでは最高のトランザクション性能とデータ整合性が得られる。しかしデータがエンドユーザーに届く前に、理解しやすさと性能の両方のために次元モデルへ変換しなければならない、と主張する。
Manifesto が次元モデルの強みとして挙げるのは5つ — 予測可能な枠組み、対称性（どのディメンションからでも等しく入れる）、優雅な拡張性（行や列を足すだけで既存クエリを壊さない）、緩やかに変化するディメンションやファクトレスファクトのような定型の対処法が揃っていること、そして集約を管理するユーティリティ群。このシリーズが扱うのは4つ目の「定型」の中身で、5つ目の集約は 04回・08回で扱う。

4. ビジネスプロセスの棚卸し

次元モデルの行はビジネスプロセスであって部門ではない（DT#3）。CareerVoice の場合、「マーケ部のマート」「エージェント事業部のマート」を作ると、スカウトも応募も両方に複製されて数字が食い違う。

Kimball（Design Tip #3）: 「データマートは部門で定義される」は業界で最も広く流布した誤りの一つだと断じている。マーケのマートにも受注が入り、セールスのマートにも受注が入れば、同じ情報が複数箇所に存在し、真実のバージョンが割れる。開発も保守もストレージも重複する。
プロセス単位で一度だけ公開し、コンフォームドディメンションで各部門から参照させる。 バスマトリクスの行がプロセスであってレポート名でも部門名でもないのはこのためだ。

プロセスの見つけ方は2方向から挟む。業務側が口にするパフォーマンス指標を聞き（「返信率」「歩留まり」「枠消化率」）、ソースシステムの側でそれを生む操作を探す（scouts の insert、selection_events の insert、contracts の月次判定）。CareerVoice では10個に棚卸しした。

5. 概念 → 論理 → 物理

再解釈（Joe Reis, Practical Data Modeling ch.14）: 概念モデル（CDM）は業務側と共有する「町の計画（Town Plan）」で、名詞（エンティティ）と動詞（関係）だけを置き、実装の詳細を持たない。論理モデル（LDM）は属性・主キー・外部キー・多重度まで書くがストレージ技術は選ばない。物理モデルで初めて具体的な技術に落とす。
Reis はこの順を飛ばすと、部門ごとに「顧客」の定義が食い違ったまま業務と IT が合意できない状態になると言い、CDM を最も価値のある成果物と位置づける。

Kimball の4ステップは、この階層のうち概念と論理にまたがる。ステップ1が概念、ステップ2〜4が論理で、物理は4ステップの後に来る。

粒度宣言は設計に対する拘束力のある契約であり、異なる粒度は同じファクトテーブルに混ぜてはならない。

1行目だけが Kimball の原則と正面から衝突する。10 Rules の Rule #1 は「原子の詳細を入れよ」、Rule #5 は「多対多はファクトテーブルで解決し、その外部キーを NULL にしてはならない」と言うが、fct_review から member_key を落とすのは原子性を意図的に下げる判断だ。理由は性能でも簡潔さでもなく、少人数企業では「30代・男性・在籍3〜5年・エンジニア」だけで投稿者が特定できてしまう点にある。

原子ファクトが要る分析は int_review_member_link に隔離し、公開マートには出さない。この衝突の扱いは 01回と 03回で詰める。

7. 演習

(a) プロセスの棚卸し

自分の担当システムでビジネスプロセスを5つ挙げよ。挙げたそれぞれについて、(1) 部門名・チーム名・レポート名になっていないか、(2) ソース側でそれを生む具体的な操作（どのテーブルへの insert / update）を1つ書けるか、(3) 業務側が口にするパフォーマンス指標を1つ書けるか、を確認する。3つとも満たせないものはプロセスではない。

解答例（CareerVoice）
プロセスソース側の操作業務側の指標部門名になっていないか
スカウト送信scouts へ insert送信数、枠消化率OK（「エージェント事業部」は不可）
スカウト反応scouts.opened_at / replied_at を update開封率、返信率OK
クチコミ審査review_moderation_events へ insert審査リードタイム、却下率OK（「モデレーションチーム」は不可）
選考イベントselection_events へ insertステージ間歩留まりOK
契約・枠消化contracts を月次で評価MRR、枠消化率OK（「営業ダッシュボード」は不可）

落とした候補: 「カスタマーサクセス」（部門名）、「月次経営レポート」（レポート名）、「会員」（プロセスではなくエンティティ＝ディメンション候補）。scouts の insert と update を別プロセスに分けたのは、前者がトランザクション、後者が累積スナップショットになり粒度も更新頻度も違うため（fct_scout と fct_scout_funnel）。

(b) reviews.status の遷移を分類する

reviews.status は submitted / screening / published / rejected の4値をとる。遷移を列挙し、それぞれの情報がファクト側（メジャーまたは日付キー）に行くのか、ディメンション側に行くのかを分類せよ。サンプル値は R001（M001 → C002、2026-03-10 投稿、03-12 公開）と R002（M002 → C001、2026-04-02 投稿、却下 defamation）。

解答例

submitted → screeningファクト（日付キー）fct_review_moderation.screening_date_key時点を持つ測定イベント。マイルストーン列になる
screening → publishedファクト（日付キー + メジャー）published_date_key, is_published(0/1)同上。到達したか否かは 0/1 の加法メジャー
screening → rejectedファクト（日付キー + メジャー）rejected_date_key, is_rejected同上

R001 は submitted_date_key=20260310, published_date_key=20260312, rejected_date_key=-1, moderation_reason_key='-1'（dim_moderation_reason の自然キー reason_code は STRING なのでセンチネルも STRING）, is_published=1。R002 は rejected_date_key に却下日、published_date_key=-1, moderation_reason_key=defamation の代理キー、is_rejected=1。未達マイルストーンを NULL ではなく -1 にするのは §6 の固定判断（DT#43）で、dim_date 側に full_date = NULL・表示名「未到達」の行を1本置く。

8. 参考: 手元の基盤ではどうか

dbt_logs_analysis はマートをデータソース起点で切っている。mart_url_performance はプロセス名ではなくソーステーブル（アクセスログ）に対する集計軸の名前で、DT#3 の基準では行が「プロセス」ではなく「レポートの見出し」になっている状態にあたる。
news_pipeline は逆で、収集（raw_articles）・要約と採点（summaries）・通知（notified_at）・お気に入り（favorites）がそれぞれ別プロセスに対応する。アプリの処理境界がプロセス境界と一致していると、マートの行も自然に揃う。
チュートリアルの種: アクセスログを「ページ表示」という1プロセスとして粒度宣言し直すと、01回の粒度テストと 08回のドリルアクロスがそのまま試せる。
