増分・遅延到着・冪等性

データマート設計 09 ／ 参照: DWT ch.19–20, ETL サブシステム #2 #6 #13 #14 #16 #24, Design Tip #43 #164 ／ 再解釈: Functional Data Engineering, dbt の増分戦略（BigQuery configs / incremental strategies / microbatch）

この資料で使う題材。 CareerVoice は、社員・元社員の企業クチコミを軸に、求人掲載・企業からの直接スカウト・転職エージェントからのスカウト・応募から入社までの選考を1つのプラットフォームで扱う架空のサービスである。業務データベースは CDC（変更データキャプチャ）で BigQuery に複製され、dbt で、業務イベントを1行ずつ記録するファクトテーブル（fct_*）と、その相手方の属性を説明するディメンションテーブル（dim_*）へ組み替えられる。

1. この資料で決めること

「増分で作る」とは、毎回どこを消してどこを書き直すかを決めることに尽きる。CareerVoice のファクトは、行が追加されるだけのもの（fct_scout）と、既存行が更新され続けるもの（fct_application_pipeline）で書き戻し方が違う。この資料ではファクトごとに「方式 × ルックバック窓（毎回さかのぼって作り直す日数の範囲）」を決め、同じ run_date で2回流しても結果が1バイトも変わらない形＝冪等（同じ入力で何度実行しても同じ結果）にする。

1.1 BigQuery で選べる方式

dbt-bigquery が受け付ける incremental_strategy は merge / insert_overwrite / microbatch の3つ。他アダプタにある append という戦略名は無く、追記は「unique_key を指定しない merge」として現れる（一致条件が常に偽の MERGE ＝ INSERT のみ）。

方式dbt の書き方BigQuery が実行する DML同じ日を2回流すと課金スキャン使う条件
追記（append 相当） incremental_strategy='merge' ＋ unique_key 無し 一致条件が常に偽の MERGE（実質 INSERT のみ） 行が二重になる（冪等でない） ソース側の WHERE 分 再実行が原理的に起きないログ取り込みのみ。マートでは使わない
merge（既定） unique_key='application_id' MERGE … WHEN MATCHED THEN UPDATE / WHEN NOT MATCHED THEN INSERT キー一致行を上書き（冪等） ターゲット全体。incremental_predicates とパーティション列条件で絞る 行が更新される累積スナップショット
insert_overwrite partition_by 必須。partitions を渡すと静的、渡さないと動的 対象パーティションを丸ごと削除して挿入する MERGE（copy_partitions=true なら copy API） パーティション単位で同じ結果（冪等） 置換対象パーティションのみ 行が更新されないトランザクション／定期スナップショット
microbatch event_time / batch_size / begin / lookback（既定 1） BigQuery では内部的に insert_overwrite（partition_by 必須） バッチ＝パーティション単位で冪等 バッチ単位 dbt 1.9 以降。窓の宣言を dbt に任せたいとき

2. よくある失敗

(a) > MAX(sent_at) の境界と、永久欠損

-- 壊れている増分境界
{% if is_incremental() %}
where s.sent_at > (select max(sent_at) from {{ this }})
{% endif %}

6/19 の実行が終わった時点で MAX(sent_at) は 6/19 の最終送信時刻を指している。6/20 の実行の直前に、6/18 09:12 送信の S003（AG02 → M002）が CDC の遅れで届く。境界条件は S003 を読まず、翌日以降は境界がさらに前進するので、S003 は永久に fct_scout に載らない。

この欠損はテストに出ない。unique も not_null も「存在しない行」を見つけられないからだ。気づくのはエージェント経由の送信数が実績と合わないと言われたときで、そのとき境界はもう何百日も先にある。

(b) 累積スナップショットを追記にすると P001 が7行になる

P001（M001 → J001）は 6/23 応募 → 7/1 書類 → 7/8 一次 → 7/15 最終 → 7/20 内定 → 7/22 承諾 → 8/1 入社と7回状態が変わる。fct_application_pipeline を unique_key 無しの merge（＝追記）で作ると、状態が動いた日の実行ごとに1行増えて7行になる。粒度宣言「1行 = 1応募のパイプライン」が成立しなくなり、COUNT(*) は応募数 1 ではなく 7 を返す。

COUNT(*) と COUNT(DISTINCT application_id) の乖離が、そのまま二重計上の量になる。一方 SUM(is_hired) は 1 のまま（入社を観測できた最後の1行しか is_hired = 1 にならない）で、AVG(days_applied_to_offer) も内定前の4行が NULL で平均から外れるため P001 単独では正しい値を返す。行が二重になっていても正しい値を返す指標があることが、この失敗を見つけにくくしている。

(c) 遅延到着ディメンション: C002 の規模変更

C002（ネクスト技研）の employee_size_band は 5/1 に 50_299 から 300_999 へ変わったが、CDC が DWH に届いたのは 5/3 だった。dim_company 側は valid_from を 5/1 に遡って新版を挿入できるので正しくなる。しかし 5/1–5/2 に投稿されたクチコミの fct_review.company_key は、その時点で唯一存在した旧版のキーを指したまま残る。

結果、「企業規模別の平均 overall_score」は2日分だけ旧規模帯に載る。ディメンションは正しく、ファクトの外部キーだけが古い、という誤り方になる。§5(c) で修復するのは、この 5/1–5/2 の fct_review.company_key である。

(d) 冪等でない処理の再実行

fct_contract_monthly を「当月分を INSERT」で作り、途中で失敗したあと素直に再実行すると、K001（C001 の premium、枠 200/月）の6月行が2本になる。scouts_sent は二重計上され、半加法の scout_quota も 400 として合計される。MERGE かパーティション置換なら、この再実行は何度やっても同じ1行に収束する。

3. Kimball の原則

ETL は34のサブシステムに分解できる（The Data Warehouse ETL Toolkit、要約は Subsystems of ETL Revisited, 2007）。増分と遅延到着はそのうち5〜6個の担当範囲であって、モデル設計の問題ではなくロードの問題として整理されている。

3.1 遅延到着ファクトと遅延到着ディメンション（DWT ch.19–20）

状況原典の処理CareerVoice に当てると
遅延到着ファクト: 過去日付のファクト行が今日届く 今日の現行版ではなく、そのイベント時点で有効だったディメンション版のサロゲートキーを割り当てる。SCD2 の有効期間で解決する S003（AG02 → M002、6/18 送信）が 6/20 に届いても、member_key は 6/18 時点の M002 の版に結ぶ。sent_at >= valid_from AND sent_at < valid_to という時点結合（イベント時点の版に結ぶ結合。DM05『履歴を持つ：SCD とスナップショット』で扱う）で解決する
遅延到着ディメンション: ディメンションの新版が遅れて届く 新版を valid_from 遡及で挿入し、その区間に既に入っているファクトの外部キーを貼り替える §2(c) がこの状況にあたる。5/1–5/2 の fct_review.company_key を新版へ更新する（§5c）
ディメンション行が無いままファクトが来る 自然キーだけを埋めた仮の行を立て、属性が届いたら更新する この題材では、参照先が未知のときも外部キーを NULL にせず -1 の行で受ける（DT#43）。仮行を立てるなら dim_company に company_id だけの行を作り、属性到着時に Type1 で埋める

遅延到着ディメンションの修復で触るのは外部キーだけにする。原典はファクトの誤り訂正に「該当行の更新」「削除して再ロード」「相殺行の追加」の3方式を挙げるが（DWT ch.19–20 のロード処理）、ここで直したいのは「ディメンションの版が後から来た」ことであってメジャーの誤りではない。この区別が §5(c) の MERGE を company_key と audit_key に限る理由になっている。

4. 現代の再解釈

Functional Data Engineering（Beauchemin）は、バッチ処理を関数型プログラミングの語彙で捉え直す。タスクは副作用を持たない純関数であり、再実行は追記ではなく上書きで行う。状態の最小単位はパーティションで、「1タスク → 1テーブル、1タスク実行 → 1パーティション」を守ると系譜とデバッグが単純になる。

この主張のうち増分にそのまま当てはまるのは2点である。パーティションを不変の単位として扱うことと、行単位の更新をやめて丸ごと置換することだ。

3点目として Functional Data Engineering（以下 FDE）は「過去への依存を持たず、処理時刻でパーティションを切る」ことを挙げ、それでバックフィル（過去分をまとめて作り直す処理）が並列化でき、遅れて届くファクトも素直に扱えるとする。CareerVoice はそこを採らず、run_date を与えた実行が sent_date（イベント時刻）のパーティションを置換し、遅延分はルックバック窓で吸収する形にした。イベント時刻を基準にする選択は dbt の microbatch が event_time として持っている側で、代わりに「窓の外は自動では入らない」という穴を自分で塞ぐ必要がある（§5c）。

dbt の insert_overwrite に静的な partitions を渡す形は、この「1タスク実行 → 指定したパーティションを丸ごと置換」をそのまま実装する。ディメンションを日次スナップショットで持つ設計（dim_member_daily。DM05『履歴を持つ』で扱う）も、同じ不変パーティションの発想の適用にすぎない。

論点Kimball（原典）FDE / dbtこの題材の決定
遅延ファクトの吸収遅延到着ハンドラ（#16）で行を挿入し、キーを当時の版で解決該当パーティションを作り直す。窓の中なら遅延分は自動で入るルックバック3日の insert_overwrite。窓の外は §5(c) の修復に回す
ディメンションの版SCD2（valid_from / valid_to）日次スナップショットで置き換える両方持つ（DM05『履歴を持つ』）。ファクトのキー解決は時刻の精度が要るので SCD2 の時点結合を使う
再実行Recovery and Restart（#24）＝安全に再開できること冪等＝何回流しても同じ。再実行は上書き静的 partitions と unique_key 付き merge で担保し、指紋クエリで検証（§5d）
実行の追跡監査ディメンション（#6, DT#164）invocation id をタスク出力に埋めるdim_audit に dbt_invocation_id と loaded_at。遅延の実測にも使う（§7a）

4.1 ルックバック窓をどう決めるか

窓は勘ではなく遅延の分布から決める。dim_audit.loaded_at とファクトの <role>_date の差を分位点で見て、p99 を覆う最小の日数を採る。CareerVoice では3日（＝当日 + 過去3日の4パーティション）を既定にし、それを超える裾は窓を広げるのではなく修復ジョブに回す。

窓を広げ続けない理由は課金だけではない。窓が広いほど「毎日書き換わるパーティション」が増え、下流のキャッシュ・抽出・エクスポートが毎日作り直しになる。dbt の microbatch がこの考え方を lookback（既定 1）という config 名で製品側に持っているのも、窓が設計上の宣言であって実装の副産物ではないという整理による。

5. BigQuery + dbt での実装

(a) fct_scout: 静的パーティション置換

-- models/marts/fct_scout.sql
{% set lookback_days = 3 %}
{% set run_date = var('run_date', run_started_at.strftime('%Y-%m-%d')) %}
{% set partitions_to_replace = [] %}
{% for i in range(lookback_days + 1) %}
  {% do partitions_to_replace.append(
       "date_sub(date '" ~ run_date ~ "', interval " ~ i ~ " day)") %}
{% endfor %}

{{ config(
    materialized = 'incremental',
    incremental_strategy = 'insert_overwrite',
    partition_by = {'field': 'sent_date', 'data_type': 'date', 'granularity': 'day'},
    cluster_by = ['scout_sender_key', 'member_key'],
    partitions = partitions_to_replace,
    on_schema_change = 'append_new_columns'
) }}

with sent as (

    select
        s.scout_id,
        s.template_id,
        s.member_id,
        s.job_posting_id,
        s.sender_type,
        coalesce(s.sender_company_id, s.sender_agent_id) as sender_id,
        s.sent_at,
        date(s.sent_at, 'Asia/Tokyo') as sent_date
    from {{ ref('stg_careervoice__scouts') }} as s
    {% if is_incremental() %}
    -- config の partitions と同じ集合で絞る（置換対象とソース範囲を一致させる）
    where date(s.sent_at, 'Asia/Tokyo') in ({{ partitions_to_replace | join(', ') }})
    {% endif %}

),

member_snapshot as (

    -- require_partition_filter = true なので結合条件ではなく WHERE で絞る
    select snapshot_date, member_id, member_profile_mini_key
    from {{ ref('dim_member_daily') }}
    {% if is_incremental() %}
    where snapshot_date in ({{ partitions_to_replace | join(', ') }})
    {% else %}
    where snapshot_date >= date '2026-01-01'
    {% endif %}

)

select
    cast(format_date('%Y%m%d', t.sent_date) as int64) as sent_date_key,
    t.sent_date,
    coalesce(m.member_key, -1)                as member_key,
    coalesce(d.member_profile_mini_key, -1)   as member_profile_mini_key,
    coalesce(snd.scout_sender_key, -1)        as scout_sender_key,
    coalesce(jp.job_posting_key, '-1')        as job_posting_key,
    {{ audit_key() }}                         as audit_key,
    t.scout_id,
    t.template_id,
    1 as scout_count
from sent as t
left join {{ ref('dim_member') }} as m
    on t.member_id = m.member_id
   and t.sent_at >= m.valid_from
   and t.sent_at <  m.valid_to
left join member_snapshot as d
    on t.member_id = d.member_id
   and t.sent_date = d.snapshot_date
left join {{ ref('dim_scout_sender') }} as snd
    on t.sender_type = snd.sender_type
   and t.sender_id  = snd.sender_id
   and t.sent_at >= snd.valid_from
   and t.sent_at <  snd.valid_to
left join {{ ref('dim_job_posting') }} as jp
    on t.job_posting_id = jp.job_posting_id

{{ audit_key() }} は、その実行に対応する dim_audit の行のキーを返すマクロで、定義は DM10『レイヤ・命名・契約・テスト・監査』で扱う。この資料の範囲では -1 を返すものとして読めばよい。member_key はイベント時刻の時点結合で解決するので、6/18 送信の S003 が 6/20 に届いても 6/18 時点の版に結ばれる（§3.1 の遅延到着ファクト）。

member_profile_mini_key のほうは dim_member_daily（その日の終わり時点）で解決するので、同日中の属性変化は当日ぶんが変化後の版になる。M001 の 6/15 の active・600_800 化がまさにこの型で、時刻の精度が要るならミニディメンション dim_member_profile_mini の履歴側（DM05『履歴を持つ』）に切り替える。

partitionsdbt が生成するもの置換されるパーティション向く場面
指定あり（静的）列挙した集合に対する WHEN NOT MATCHED BY SOURCE … THEN DELETE ＋ INSERT列挙したもの全部。その日のソース行が0件になれば空で置換される窓を宣言で固定したいとき。行が消える訂正（クチコミの削除、スカウトの取消）がある表
指定なし（動的）一時表を作り、その中の distinct なパーティションを検出して置換。_dbt_max_partition が使えるモデルが出力したパーティションのみ。出力が0行の日は古い行が残る出力範囲が実行時にしか決まらないとき
copy_partitions=true（partition_by の中に書く）MERGE ではなく copy API（パーティションデコレータ）動的置換のみfct_page_view のような大きい表。挿入の課金が無い代わりに追跡は粗い

(b) fct_application_pipeline: merge と対象の絞り込み

-- models/marts/fct_application_pipeline.sql
{% set lookback_days = 3 %}
{% set run_date = var('run_date', run_started_at.strftime('%Y-%m-%d')) %}

{{ config(
    materialized = 'incremental',
    incremental_strategy = 'merge',
    unique_key = 'application_id',
    partition_by = {'field': 'applied_date', 'data_type': 'date', 'granularity': 'day'},
    cluster_by = ['company_key'],
    incremental_predicates = [
      "DBT_INTERNAL_DEST.applied_date >= date_sub(date '" ~ run_date ~ "', interval 180 day)"
    ],
    on_schema_change = 'append_new_columns'
) }}

with touched as (

    -- ルックバック窓の中で動いた応募だけを作り直す
    select e.application_id
    from {{ ref('stg_careervoice__selection_events') }} as e
    where date(e.occurred_at, 'Asia/Tokyo')
          >= date_sub(date '{{ run_date }}', interval {{ lookback_days }} day)

    union distinct

    select a.application_id
    from {{ ref('stg_careervoice__applications') }} as a
    where date(a.applied_at, 'Asia/Tokyo')
          >= date_sub(date '{{ run_date }}', interval {{ lookback_days }} day)

),

applications as (

    select a.*
    from {{ ref('stg_careervoice__applications') }} as a
    {% if is_incremental() %}
    where a.application_id in (select application_id from touched)
    {% endif %}

),

milestones as (

    select
        e.application_id,
        min(if(e.stage = 'document',        e.occurred_at, null)) as document_at,
        min(if(e.stage = 'first_interview', e.occurred_at, null)) as first_interview_at,
        min(if(e.stage = 'final_interview', e.occurred_at, null)) as final_interview_at,
        min(if(e.stage = 'offer',           e.occurred_at, null)) as offer_at,
        min(if(e.stage = 'accepted',        e.occurred_at, null)) as accepted_at,
        min(if(e.stage = 'hired',           e.occurred_at, null)) as hired_at,
        max(e.occurred_at)                                        as last_event_at
    from {{ ref('stg_careervoice__selection_events') }} as e
    where e.application_id in (select application_id from applications)
    group by e.application_id

)

select
    a.application_id,
    date(a.applied_at, 'Asia/Tokyo') as applied_date,
    cast(format_date('%Y%m%d', date(a.applied_at, 'Asia/Tokyo')) as int64) as applied_date_key,
    coalesce(cast(format_date('%Y%m%d', date(ms.offer_at, 'Asia/Tokyo')) as int64), -1) as offer_date_key,
    coalesce(cast(format_date('%Y%m%d', date(ms.hired_at, 'Asia/Tokyo')) as int64), -1) as hired_date_key,
    date_diff(date(ms.offer_at, 'Asia/Tokyo'), date(a.applied_at, 'Asia/Tokyo'), day) as days_applied_to_offer,
    if(ms.hired_at is not null, 1, 0) as is_hired,
    {{ audit_key() }} as audit_key
    -- 残りのマイルストーン date_key・FK・current_stage は 02 回の定義どおり
from applications as a
left join milestones as ms
    on a.application_id = ms.application_id

merge はキー一致行を丸ごと置換するので、touched に入らなかった応募の行はそのまま残る。危険なのは incremental_predicates の窓で、6か月前に応募した P001 が今日 withdrawn になったのに 180 日の窓から外れていると、一致行が見つからず同じ application_id が2行になる。窓は「開いたままになりうる最長のパイプライン」以上に取り、実測で確かめる。

-- incremental_predicates の窓の下限を測る
select
    approx_quantiles(open_days, 100)[offset(99)] as p99_open_days,
    max(open_days)                               as max_open_days
from (
    select
        p.application_id,
        date_diff(max(e.event_date), p.applied_date, day) as open_days
    from `marts.fct_application_pipeline` as p
    join `marts.fct_selection_event`      as e
      on p.application_id = e.application_id
    group by p.application_id, p.applied_date
)

(c) 遅延到着ディメンションの修復

-- macros/repair_late_company_key.sql
{% macro repair_late_company_key(from_date, to_date) %}

  {% set repair_sql %}
    merge into {{ ref('fct_review') }} as t
    using (
        select
            r.review_id,
            c.company_key as resolved_company_key
        from {{ ref('stg_careervoice__reviews') }} as r
        join {{ ref('dim_company') }} as c
          on r.company_id = c.company_id
         and r.submitted_at >= c.valid_from
         and r.submitted_at <  c.valid_to
        where date(r.submitted_at, 'Asia/Tokyo')
              between date '{{ from_date }}' and date '{{ to_date }}'
    ) as s
    on  t.review_id = s.review_id
    -- ターゲット側にもパーティション条件を置く（置かないと全期間をスキャンする）
    and t.submitted_date between date '{{ from_date }}' and date '{{ to_date }}'
    when matched and t.company_key <> s.resolved_company_key then update set
        company_key = s.resolved_company_key,
        audit_key   = {{ audit_key() }}
  {% endset %}

  {% do run_query(repair_sql) %}
  {% do log('repaired fct_review.company_key: ' ~ from_date ~ ' .. ' ~ to_date, info=true) %}

{% endmacro %}
dbt run-operation repair_late_company_key \
  --args '{from_date: "2026-05-01", to_date: "2026-05-02"}'

更新するのは company_key と audit_key だけで、メジャーには触れない（§3.1）。audit_key を差し替えるので、あとから「どのバッチが貼り替えた行か」を dim_audit 経由で数えられる。

ただし insert_overwrite のファクトなら、この MERGE より該当パーティションを流し直す方が安い。reviews は CDC で submitted_at を保持しているので再構築できる（dbt run --select fct_review --vars '{"run_date": "2026-05-02"}'）。修復 MERGE を選ぶのは、再構築のコストが跳ねる大きい表か、貼り替え範囲が数十パーティションに散っている場合に限る。

(d) 冪等性の検証

# 1回目
dbt run --select fct_scout --vars '{"run_date": "2026-06-20"}'
-- 指紋を取る（行の順序に依存しない集約）
create or replace table `marts.fct_scout__fingerprint` as
select
    t.sent_date,
    count(*)            as row_count,
    sum(t.scout_count)  as scout_count,
    -- audit_key は実行ごとに変わるので指紋から外す
    bit_xor(farm_fingerprint(to_json_string(
        (select as struct t.* except (audit_key))
    ))) as row_fingerprint
from `marts.fct_scout` as t
where t.sent_date between date '2026-06-17' and date '2026-06-20'
group by t.sent_date;
# 2回目（同じ run_date）
dbt run --select fct_scout --vars '{"run_date": "2026-06-20"}'
-- 差分が0行なら冪等
with after_run as (
    select
        t.sent_date,
        count(*)            as row_count,
        sum(t.scout_count)  as scout_count,
        bit_xor(farm_fingerprint(to_json_string(
            (select as struct t.* except (audit_key))
        ))) as row_fingerprint
    from `marts.fct_scout` as t
    where t.sent_date between date '2026-06-17' and date '2026-06-20'
    group by t.sent_date
),

before_run as (select * from `marts.fct_scout__fingerprint`)

select 'before のみ' as side, * from (select * from before_run except distinct select * from after_run)
union all
select 'after のみ',  * from (select * from after_run  except distinct select * from before_run);

EXCEPT DISTINCT は片方向なので両向きを取る。audit_key は実行ごとに変わるので SELECT AS STRUCT t.* EXCEPT (audit_key) で除いてから指紋を取る。「同じ入力なら同じ出力」を守る対象はメジャーとキーであって、実行の記録ではない。

# models/marts/schema.yml（一部）
version: 2

models:
  - name: fct_scout
    description: "1行 = 送信された1スカウト。sent_date で日次パーティション"
    columns:
      - name: scout_id
        data_tests: [not_null, unique]
      - name: sent_date
        data_tests: [not_null]
      - name: member_key
        data_tests: [not_null]
    data_tests:
      - dbt_utils.expression_is_true:
          expression: "sent_date <= current_date('Asia/Tokyo')"

unique は §2(b) の二重行を捕まえる。捕まえられないのは §2(a) の欠損なので、そちらは「ソースの件数とマートの件数をルックバック窓で突き合わせる」テストを別に置く。

6. 判断基準

ファクトの型遅延行数の規模方式ルックバックこの題材の例
トランザクションp99 ≤ 3日日次で数万〜数百万insert_overwrite（静的 partitions）3日fct_scout, fct_selection_event, fct_review
トランザクションp99 ≤ 3日日次で数千万以上insert_overwrite（動的 ＋ copy_partitions）3日fct_page_view
トランザクション裾が長い（p99 > 7日）—insert_overwrite ＋ 定期の広窓リビルド日次3日 ＋ 週次30日モバイルからの page_views のように到着が遅れる経路
累積スナップショット行が更新され続ける—merge（unique_key）＋ incremental_predicatesイベント側3日。predicate は最長パイプライン以上fct_application_pipeline, fct_scout_funnel, fct_review_moderation
定期スナップショット（日）ソースが現在値のみ＝過去日は再現不能—insert_overwrite（当日パーティションのみ）0日（過去は不変）fct_job_posting_daily（同じ扱いで dim_member_daily も）
定期スナップショット（月）月内は動き続ける—insert_overwrite（granularity: 'month'）当月 ＋ 前月fct_contract_monthly
小さいファクト—全量再構築が数十秒以内増分にしない（materialized='table'）—fct_placement

順序としては、まず増分にしない。全量再構築の課金と所要時間が運用上の制約に触れてから、上の表で方式を選ぶ。増分は正しさの担保を1つ増やす選択で、行数が小さいうちに払う理由がない。

6.1 ルックバック日数の決め方

  1. dim_audit.loaded_at とファクトの <role>_date の差を分位点で測る（§7a）。
  2. p99 を覆う最小日数 × 1パーティションの再ビルド課金 × 1日の実行回数を出し、許容内かを見る。
  3. 許容外なら窓は広げず、裾は修復ジョブ（週次の広窓リビルド、または §5c の MERGE）へ分ける。

7. 演習

(a) fct_page_view のルックバックを何日にするか。決めるために何を測るか

解答例

測るのは3つある。遅延の分布、再ビルドの課金、そして窓の外に外れた行が指標を動かす量である。

-- 1. 遅延の分布（監査ディメンションを使う）
select
    approx_quantiles(lag_days, 100)[offset(50)] as p50,
    approx_quantiles(lag_days, 100)[offset(99)] as p99,
    max(lag_days)                               as max_lag,
    safe_divide(countif(lag_days > 3), count(*)) as over_3d_ratio
from (
    select date_diff(date(a.loaded_at, 'Asia/Tokyo'), f.view_date, day) as lag_days
    from `marts.fct_page_view` as f
    join `marts.dim_audit`     as a using (audit_key)
    where f.view_date between date '2026-05-01' and date '2026-06-30'
);

-- 2. 1パーティションの再ビルド規模
select partition_id, total_rows, total_logical_bytes
from `marts.INFORMATION_SCHEMA.PARTITIONS`
where table_name = 'fct_page_view'
order by partition_id desc
limit 10;

決め方: p99 を覆う最小日数を採る。課金が許容外なら窓は3日のままにし、over_3d_ratio の行は週次の広窓リビルドで回収する（判断基準の表の3行目）。fct_page_view は最大の表なので、窓を1日広げる判断は他のどのファクトより高くつく。

(b) fct_job_posting_daily を増分で作る時の単位は「日」か「求人」か

解答例

単位は「日」にする。理由は3つある。

  • 粒度が「1行 = 1求人 × 掲載中の1日」で、パーティション列が snapshot_date。置換単位と粒度の日次側が一致し、FDE の「1タスク実行 → 1パーティション」に収まる。
  • 「求人」単位にすると1回の実行が J001 の全掲載日パーティションに書き込むことになり、insert_overwrite が使えず merge（unique_key=['job_posting_id','snapshot_date']）になる。冪等ではあるがターゲット全体が更新対象になり、パーティションの絞り込みを自前で設計することになる。
  • ソース（job_postings の現在値）は過去日の status を再現できない。過去パーティションは不変にし、当日ぶんだけ作る＝ルックバック0日（判断基準の表の5行目）。掲載終了の反映が1日遅れる経路があるなら、前日ぶんの再生成だけを許す。

ただし application_count_cum / scout_count_cum は累計なので、過去日を作り直さない代わりに「その日の時点で観測できた累計」を持つことになる。この定義を description に書いておかないと、あとから遡って数えた累計と一致しないという問い合わせになる。

(c) dim_member_daily（DM05『履歴を持つ』）が1日欠けたとき、時点結合に何が起きるか。どう埋めるか

解答例

起きること: 6/19 の snapshot_date が無いと、snapshot_date = <role>_date で結ぶモデル（§5(a) の member_snapshot は sent_date、fct_page_view なら view_date）は 6/19 だけ一致行を失う。inner join なら 6/19 の行が丸ごと消え、left join なら member_profile_mini_key が NULL になる。-1 すら付かないので DT#43 の「NULL 外部キー禁止」に違反し、年収帯別の集計から6/19 だけが抜ける。

しかも require_partition_filter=true なので、欠損しているのか単にそのパーティションを読んでいないだけなのかがクエリ結果からは区別できない。

埋め方1（再生成できる場合）: members.updated_at があるので 6/19 終了時点の版を作り直せる。1パーティションだけ流す。

dbt run --select dim_member_daily --vars '{"run_date": "2026-06-19"}'

埋め方2（再生成できない場合）: 前日の行をそのまま複製して埋める（carry-forward）。

insert into `marts.dim_member_daily`
    (snapshot_date, member_id, member_key, member_profile_mini_key,
     current_company_id, current_job_category_code, annual_income_band, job_change_intent)
select
    date '2026-06-19',
    member_id, member_key, member_profile_mini_key,
    current_company_id, current_job_category_code, annual_income_band, job_change_intent
from `marts.dim_member_daily`
where snapshot_date = date '2026-06-18';

これは属性変化を1日遅らせる近似で、M001 の 6/15 のような変化がちょうど欠損日に起きていれば取りこぼす。時点精度が要る結合なら、そもそも dim_member の時点結合（event_ts >= valid_from AND event_ts < valid_to）に切り替える。SCD2 と日次スナップショットを両方持つ（DM05『履歴を持つ』）判断が役に立つのはこの場面で、片方の欠損がもう片方で埋まる。

8. 参考: 手元の基盤ではどうか

  • mart_url_performance_incremental は unique_key=['url_path','date']（BigQuery 既定の merge）だが、増分境界が DATE(request_timestamp) > (SELECT MAX(date) FROM {{ this }}) で、§2(a) の形そのもの。ログが1日でも遅れて届くとその日は永久に埋まらない。
  • partition_by は date（DATE）で張ってあるので、この資料の基準なら insert_overwrite ＋ 静的 partitions（当日 + 3日）にすれば、境界を持たずに冪等になる。unique_key も不要になる。
  • news_pipeline の summaries はパーティション無しで insert_rows_json（ストリーミング挿入）。再実行の冪等性をテーブル側に置けないので、収集時の URL 全件突合で重複を防いでいる。冪等性をパーティションに預けられない典型例。
  • 試せる種: mart_url_performance_incremental を --vars run_date 付きの静的 partitions に書き換え、同じ run_date で2回流して §5(d) の指紋クエリが一致するかを見る。
