star か One Big Table か

データマート設計 07 ／ 参照: DWT ch.1, A Dimensional Modeling Manifesto (1997) ／ 再解釈: Fowler (Coalesce 2020), Fivetran Star Schema vs. OBT, Hightouch Modelling Part 2, BigQuery パーティション分割テーブル

1. この回が決めること

列指向 DWH でスタースキーマを保つ理由は性能ではなく意味である。BigQuery では OBT（非正規化ワイドテーブル）の方が実測で速いことが分かっており、性能を根拠にした star の擁護はもう成立しない。それでも star を残すのは、dim_company の属性がどの時点の値かを 1 箇所で決められること、fct_scout と fct_placement を同じ company_key で横断できること、この 2 点のためである。

この回で固定する判断

論点決定
正本はどれかstar が正本。fct_scout_funnel + dim_member / dim_scout_sender / dim_job_posting をマートの中心に置く
OBT の位置づけ配布物。star の下流に materialized='table' の obt_scout_funnel を置き、BI と逆 ETL はここだけを見る
OBT を正本にする条件§6 の判断基準表の 1 行目に当たるときだけ（単発の分析・PoC・star をまだ持っていない・1000 万行未満）。閾値の定義は 6 節に一本化する
雪片化しない（正典の固定判断）。OBT の議論は star ↔ OBT の 2 極で行い、snowflake は比較対象としてのみ扱う
パーティションstar 側も OBT 側も同じ sent_date（DATE）に張る。OBT だけ require_partition_filter=true

2. どこで壊れるか

(a) Type1 上書きが全行の書き換えになる

C002 ネクスト技研が社名を変更した。正典では dim_company は Type 6 相当で、name だけが Type1（履歴を残さず上書き）である。star なら dim_company の C002 の行を上書きするだけで終わる。

Type1 属性は履歴を持たないので、is_current で絞らずその自然キーの全 SCD2 版を揃えて上書きする（Type 6, DT#15）。C002 は 2026-05-01 に employee_size_band が変わっているので現時点で 2 行あり、更新対象はその 2 行である。

-- star: C002 の SCD2 版すべて（現時点で 2 行）
UPDATE marts.dim_company
SET name = 'ネクスト技研ホールディングス'
WHERE company_id = 'C002';

-- OBT を正本にした場合: 全パーティションを触る
-- （marts.obt_page_view は正典に無い。fct_page_view を企業属性込みで
--   非正規化したと仮定した、この節だけの「やってはいけない設計」の例）
UPDATE marts.obt_page_view
SET company_name = 'ネクスト技研ホールディングス'
WHERE company_id = 'C002';   -- 全期間のパーティションが対象

2 行と数億行の差である。後者は require_partition_filter=true を付けていると実行すらできない（パーティション列 view_date の条件が無いため）。付けていなければ全期間を書き換える DML が走る。

どちらにしても「Type1 の属性を数億行に焼き込む」時点で設計が誤っている。

(b) as-of で焼いた後に「現在値で見たい」が来る

M001 は 2026-06-15 に job_change_intent が passive → active、annual_income_band が 400_600 → 600_800 に変わり、2026-08-01 に C001 へ入社した。S001（2026-06-20 送信）の member_key は送信時点の SCD2 行を指す。OBT に dim_member の属性を焼き込むと、そこに固定されるのは送信時点の値である。

ここに「転職意欲が今 active の会員に、過去半年で何通スカウトが届いたか」という問いが来る。star なら member_id で is_current 行へ再結合すれば答えられる（正典の固定判断）。

OBT だけを持っていると、現在値の列を足して全期間を再生成するしかない。しかも再生成した瞬間、過去の分析結果と数字が合わなくなる。

(c) star を BI に直接渡して fan-out する

M002 は希望職種を 2 件（ENG-BE, ENG-DATA）持つ。br_member_desired_job_category は多値ブリッジなので M002 について 2 行ある。Looker Studio でアナリストが fct_scout にこのブリッジを結合して職種別に集計すると、M002 宛のスカウトが 2 回数えられる。

-- 誤: scout_count が希望職種数だけ膨らむ
SELECT
    b.job_category_key,
    SUM(f.scout_count) AS scout_count   -- M002 宛は 2 倍
FROM marts.fct_scout AS f
JOIN marts.br_member_desired_job_category AS b
    ON f.member_key = b.member_key
GROUP BY b.job_category_key;

-- 正: weighting_factor を掛ける（DT#142 の配分）
SELECT
    b.job_category_key,
    SUM(f.scout_count * b.weighting_factor) AS scout_count_allocated
FROM marts.fct_scout AS f
JOIN marts.br_member_desired_job_category AS b
    ON f.member_key = b.member_key
GROUP BY b.job_category_key;

この誤りは SQL を書ける人でも踏む。BI ツールに star を露出させるということは、結合の正しさをアナリスト全員に委ねるということである。

OBT を配布物として置く動機の本体はここにある。性能ではない。

3. Kimball の原則

Manifesto（1997）が挙げる強みのうち、この回で使うのは 3 点。理解しやすさ（"End users cannot understand or remember an ER model. End users cannot navigate an ER model."）、性能（star の "predictable, standard framework" が、オプティマイザの推測に頼らず "evaluate arbitrary n-way joins to a fact table in a single pass" を可能にする）、拡張への耐性（新しいファクト・新しいディメンション・新しい属性・粒度の変更の 4 種類が、既存のロードやレポートを壊さずに載る）。

同記事はほかに対称性（すべてのディメンションが等しく対等な入口になる）、標準技法（SCD・異種製品・ファクトレスファクト）、集約ナビゲーションも挙げる。そのどれもが意味の側の主張で、性能を根拠にしているのは上の 2 番目だけである。

ここで前置きが要る。DWT ch.1 が「正規化は DWH の敵」と書くとき、その敵対関係は行指向 RDBMS の物理特性に由来している。行指向では 1 行を読むと全列がディスクから上がってくるので、テーブルを分けるほど I/O が増える。

列指向の BigQuery では、テーブルが何本あろうと読まれるのは参照した列だけである。つまり Manifesto の主張のうち「性能」の根拠だけが、列指向 DWH が標準になった時点で失効した。残りは全て意味の側の主張なので、そのまま効いている。

技法定義使う条件（2026 年の BigQuery で）
スタースキーマ1 つのファクトを中心に、非正規化されたディメンションを 1 段で囲む常に。ただし理由は結合コストではなく「属性の時点を 1 箇所で決める」ため
ディメンションの非正規化（雪片化しない）dim_agent に agency_name / agency_tier を平坦化して持つ常に。正典の固定判断。列指向では結合コストは理由にならないが、可読性の理由は残る
コンフォームドディメンション同じ company_key を fct_review / fct_scout / fct_placement が共有する常に。OBT はこの技法を破壊する（表ごとに企業属性のコピーが分岐する）
粒度の宣言1 行が何を意味するかをモデル定義の最初に固定する常に。OBT でも宣言は必要で、宣言できない OBT は作らない
拡張への耐性属性追加・ディメンション追加を既存レポートを壊さずに行えるstar では列追加のみ。OBT では属性追加が全行の再生成になる

4. 現代の再解釈

軸: 性能のための技法か、意味のための技法か

Dave Fowler（Chartio）の Coalesce 2020 講演「Kimball in the context of the modern data warehouse: what's worth keeping, and what's not」は、star schema を捨てて結合可能な列を全て結合した大きな非正規化テーブルを 1 本作り、その上にビューでマートを切って利用者へ出すことを提案した。根拠は、Kimball が star schema を採った動機の 1 つがストレージコストであり、クラウド DWH ではそのコストがもう当時ほど高くない、という点にある。

この提案が有効なのは、star schema の技法のうち性能とコストを根拠に導入されたものに限られる。粒度の宣言・コンフォームドディメンション・SCD のような意味を根拠に導入された技法は、ストレージが安くなっても何も変わらない。

この回はこの区別を 1 本の軸として使う。性能を根拠に導入された技法は捨てる。意味を根拠に導入された技法は残す。

Fowler の提案のうち「ビューでマートを切る」は BigQuery ではそのまま採れない。ビューは実行のたびに下のテーブルをスキャンするので、ワイドテーブルの上にビューを重ねてもスキャン量は減らない。この回が OBT を materialized='table' で置くのは、そのためである（マテリアライズド・ビューという選択肢もあるが、外部結合や一部の集計に制約がある）。

関連議論: dbt Discourse のスレッド「Is Kimball dimensional modeling still relevant in a modern data warehouse?」（Fowler の講演より前の別議論）にも同じ対立が出ている。Ernesto は失効した前提として "Databases are slow and expensive"、"SQL language is limited"、"You can never join fact tables" の 3 つを挙げる。levelworm は "Columnar database welcomes wide table and hate a lot of joins. Kimball naturally needs a lot of joins for one analysis." と書く。

一方 Josh は残るものを挙げる。コンフォームドディメンション（"if you are slicing a bunch of facts by, say, customer, it needs to be the same, common list"）、粒度の一貫性（"when we add new data it doesn't break existing reports"）、そして "a consistent conceptual way to get people to think about events we analyze (facts) versus the things we are analyzing them by"。軸の両側がそのまま揃っている。

この題材への適用は下表になる。

技法元の根拠この題材での扱い
ファクトを細く保つ（属性をディメンションへ追い出す）性能（行指向の I/O）＋ 意味（属性の時点管理）残す。根拠は意味の方だけ
雪片化を避ける性能（結合段数）捨ててよいはずだが残す。理由を可読性に差し替える（正典の固定判断）
結合を減らす性能捨てる。BigQuery では小さいディメンションはブロードキャストされ、シャッフルが起きない
コンフォームドディメンション意味（横断可能性）残す。OBT を増やしても star 側を正本に保つ
SCD2 / 粒度宣言意味残す（05 回・01 回）

実測: BigQuery では OBT が 49% 速い

Fivetran の "Star Schema vs. OBT for Data Warehouse Performance"（2022）は TPC-DS の scale 100 データ（store_sales, date_dim, store, household_demographics, customer_address）で star と非正規化 1 表を比較した。BigQuery では "the average improvement in query response time is 49%, with the denormalized table outperforming the star schema in every category"。Redshift は 25〜30%、Snowflake は約 25% で、Snowflake では単純なクエリで star が勝つこともあった。

ただし同記事はコストも書いている。非正規化表は 60,250 MB、ファクト store_sales 単体は 29,778 MB（4 つのディメンションを足した star 全体でも 29,905 MB）でストレージは約 2 倍。そして "OBT is good for small teams and small projects that are focused on tracking a specific item"、"The star schema promotes better ELT / ETL code conceptualization and organization" と結んでいる。

この 49% はクエリ応答時間の改善であって、スキャンされるバイト数の削減ではない。列指向ではスキャン量は「読んだ列 × 行数」で決まるので、同じ集計をするなら OBT の方が読むバイトは多いことすらある（文字列属性が行ごとに複製されるため）。速いのは結合とシャッフルの段が消えるからである。

BigQuery のオンデマンド課金はスキャンバイト数に対して発生する。つまり OBT にすると速くなるが安くはならない。

層構成: star を正本、OBT を配布物に

Hightouch の "A Guide to Modern Data Warehouse Modelling — Part 2" は両方を採る層構成を推す。"To get the best of both worlds, we can still utilize Kimball's Star Schema as an intermediate step after the staging layer, then materialize Wide Tables out of it." つまり staging → Kimball の star → そこからマテリアライズしたワイドテーブル、の 3 層。同記事は "cloud data warehouses are different now. Storage, for instance, does not cost as much" として非正規化のコストが下がったことを認めつつ、立ち上げ段階のチームにはこの複合構成を勧めていない（staging から直接ワイドテーブルへ行き、複雑さが増えてから star を挟め、という順序）。

BigQuery 固有の 4 点

機構挙動この題材での帰結
ブロードキャスト結合片側が十分小さければ全スロットに配布され、シャッフルが起きない。ヒントは指定できずオプティマイザが選ぶdim_scout_sender（送信主体、数千行）や dim_date との結合は実質ただ。「結合が多いから OBT」という理由は成り立たない
パーティションプルーニングDATE / TIMESTAMP / DATETIME 列に hour / day / month / year 単位で張る。境界は UTC。"filter the partitioning column using a constant expression, rather than a dynamic expression"ファクト側の日付列にしか効かない。dim_member.valid_from でどれだけ絞ってもファクトのパーティションは減らない
クラスタリング複数列の絞り込み、高カーディナリティ列に効く。"Partitioning results in a small amount of data per partition (approximately less than 10 GB)" ならパーティションよりクラスタを選ぶscout_sender_key, member_key のような高カーディナリティ列に張る。sender_type（2 値）に張っても無駄
ARRAY<STRUCT> のネスト1 対多を行に展開せず 1 行に畳む。展開しないかぎりスキャンされないOBT に多値属性（希望職種）を載せる唯一の安全な形。fan-out を起こさずに持てる。詳細は 06 回

プルーニングが効かない書き方は明示的に列挙されている。サブクエリを使った動的な値との比較（WHERE t1.ts = (SELECT timestamp FROM table3 WHERE key = 2)）、非対応関数での加工（FORMAT_DATE('%Y-%m-%d %H', ts)、EXTRACT(MONTH FROM ts)）、パーティション列への算術（WHERE ts + INTERVAL 1 DAY > CURRENT_TIMESTAMP()）、そして AND ではなく OR でつないだ述語。BI ツールが生成する SQL がこの形になっていないかは、実際に生成された SQL を見るまで分からない。

5. BigQuery + dbt での実装

(a) star 側: fct_scout のパーティションとクラスタ

下の int_scout_keyed は stg_careervoice__scouts にキー解決（as-of join によるディメンション版の割り当て）を済ませた intermediate モデルである（正典 §4 の命名規則 int_<entity>_<verb>。正典にモデル登録は無い）。この回の主題は物理設計なので、キー解決の中身は 05回を見る。

-- models/marts/fct_scout.sql
-- 増分化（materialized='incremental' + insert_overwrite）は 09回・10回で扱う。
-- この回の論点は物理設計（パーティションとクラスタ）だけなので table のまま示す。
{{ config(
    materialized='table',
    partition_by={
        'field': 'sent_date',
        'data_type': 'date',
        'granularity': 'day'
    },
    cluster_by=['scout_sender_key', 'member_key']
) }}

SELECT
    s.sent_date_key,
    s.sent_date,
    s.member_key,
    s.member_profile_mini_key,
    s.scout_sender_key,
    s.job_posting_key,
    s.audit_key,
    s.scout_id,
    s.template_id,
    1 AS scout_count
FROM {{ ref('int_scout_keyed') }} AS s

パーティションは sent_date_key（INT64 の YYYYMMDD）ではなく sent_date（DATE）に張る。正典が両方を持たせているのはこのためである。sent_date_key に整数レンジパーティションを張ることもできるが、DATE_SUB 系の関数がそのまま使えず BI の生成 SQL がプルーニングを外しやすい。

クラスタ列は正典どおり scout_sender_key, member_key の順。順序に意味があり、前方の列ほど絞り込みが効く。「送信主体別の分析が主で、会員別は従」という利用実態を順序が表している。

sender_type（company / agent の 2 値）をクラスタ列に入れないのは、カーディナリティが低く 1 ブロックも落とせないため。

(b) 配布物: obt_scout_funnel

-- models/marts/obt_scout_funnel.sql
{{ config(
    materialized='table',
    partition_by={
        'field': 'sent_date',
        'data_type': 'date',
        'granularity': 'day'
    },
    cluster_by=['scout_sender_key', 'member_key'],
    require_partition_filter=true
) }}

SELECT
    -- 退化ディメンションと粒度
    f.scout_id,
    f.sent_date,
    f.sent_date_key,
    d.iso_week      AS sent_iso_week,
    d.fiscal_year   AS sent_fiscal_year,

    -- 送信主体（異種ディメンション・送信時点）
    f.scout_sender_key,
    sd.sender_type,
    sd.sender_name,
    sd.company_industry AS sender_company_industry,
    sd.agency_tier      AS sender_agency_tier,

    -- 会員（as-of = 送信時点）
    f.member_key,
    m.birth_year   AS member_birth_year_asof,
    m.prefecture   AS member_prefecture_asof,
    m.region       AS member_region_asof,

    -- 求人
    f.job_posting_key,
    j.title            AS job_title,
    j.salary_min,
    j.salary_max,
    j.prefecture       AS job_prefecture,
    j.employment_type,
    j.is_agency_posting,

    -- メジャー
    f.hours_to_open,
    f.hours_to_reply,
    f.is_opened,
    f.is_replied,
    f.is_interested,
    f.is_applied
FROM {{ ref('fct_scout_funnel') }} AS f
LEFT JOIN {{ ref('dim_scout_sender') }} AS sd
    ON f.scout_sender_key = sd.scout_sender_key
LEFT JOIN {{ ref('dim_member') }} AS m
    ON f.member_key = m.member_key
LEFT JOIN {{ ref('dim_job_posting') }} AS j
    ON f.job_posting_key = j.job_posting_key
LEFT JOIN {{ ref('dim_date') }} AS d
    ON f.sent_date_key = d.date_key

結合条件が valid_from / valid_to の範囲比較になっていないことに注意する。f.member_key はすでに送信時点の SCD2 行を指すサロゲートキーなので、等値結合でそのまま as-of になる。時点解決はファクトのビルド時に済ませる（05 回）。

OBT 側で範囲結合をやり直すと、そこが 2 つ目の時点解決ロジックになり、star と数字がずれる原因になる。

LEFT JOIN にしているのは、キーが -1（未知）でも行を落とさないため。dim_* 側に -1 行がある前提なので実際には INNER でも同じ結果になるが、ディメンションのロード漏れが起きたときにOBT の行が黙って消えるのを防ぐ。

(c) require_partition_filter と BI の前提

# models/marts/schema.yml
version: 2

models:
  - name: obt_scout_funnel
    description: |
      配布用の非正規化テーブル。正本は fct_scout_funnel と dim_*。
      粒度: 1 行 = 1 スカウトの送信→開封→返信→応募。
      member_* / sender_* は送信時点の値（as-of）。現在値が要る分析は star 側で組む。
      sent_date による絞り込みが必須（require_partition_filter=true）。
    columns:
      - name: scout_id
        data_tests: [unique, not_null]
      - name: sent_date
        data_tests: [not_null]
      - name: scout_sender_key
        data_tests:
          - relationships:
              to: ref('dim_scout_sender')
              field: scout_sender_key

-- BI から: 通る
SELECT sender_type, SAFE_DIVIDE(SUM(is_replied), COUNT(*)) AS reply_rate
FROM marts.obt_scout_funnel
WHERE sent_date BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
GROUP BY sender_type;

-- BI から: エラーになる（パーティションフィルタが無い）
-- Cannot query over table 'marts.obt_scout_funnel' without a filter
-- over column(s) 'sent_date' that can be used for partition elimination
SELECT sender_type, COUNT(*) FROM marts.obt_scout_funnel GROUP BY sender_type;

require_partition_filter=true は「うっかり全期間スキャン」を型で止める唯一の手段である。副作用が 2 つある。

第 1 に、この OBT を参照する下流モデルも必ず sent_date で絞る必要がある。第 2 に、生成 SQL にパーティション列の述語が入らない dbt テストが落ちる。上の schema.yml では unique と relationships がこれに当たり、そのままでは通らない。

落ちるテストそれぞれの config: に where を書いて、直近パーティションに限定する。

    columns:
      - name: scout_id
        data_tests:
          - unique:
              config:
                where: "sent_date >= DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY)"
      - name: scout_sender_key
        data_tests:
          - relationships:
              to: ref('dim_scout_sender')
              field: scout_sender_key
              config:
                where: "sent_date >= DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY)"

モデル単位でまとめて掛ける方法は dbt に無い。where はデータテストの config なので、モデルの config: に書いても、そのモデルに付いた generic test には伝播しない。テスト単位に書くか、dbt_project.yml の data_tests: 配下でディレクトリ単位に掛けるかの二択である。

# dbt_project.yml — ディレクトリ単位でまとめる場合
data_tests:
  careervoice:
    marts:
      +where: "sent_date >= DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY)"

ただしこちらは配下のテスト全部に効くので、sent_date を持たない dim_member や fct_review のテストまで壊す。+ 前置が使えるのは dbt_project.yml だけで、プロパティ yml の config: では使わない。

not_null は生成 SQL が where sent_date is null のようにパーティション列そのものへの述語になるので、unique / relationships とは挙動が違う可能性がある。実際に dbt test を回して、どのテストが落ちるかを自分の環境で確かめる。

star 側の fct_scout / fct_scout_funnel には require_partition_filter を付けない。正本は全期間の再集計・バックフィル・整合テストの対象になるからである。フィルタ強制は配布物側にだけ掛けるのが、star = 正本 / OBT = 配布物という層構成の物理的な表現になる。

(d) スキャン量の見積り

-- パーティションあたりの実サイズ。10 GB を大きく下回るならクラスタ優先を検討する
SELECT
    table_name,
    COUNT(*)                                            AS partition_count,
    SUM(total_rows)                                     AS total_rows,
    ROUND(SUM(total_logical_bytes) / POW(1024, 3), 2)   AS total_gib,
    ROUND(AVG(total_logical_bytes) / POW(1024, 2), 1)   AS avg_partition_mib,
    MAX(last_modified_time)                             AS last_modified_time
FROM marts.INFORMATION_SCHEMA.PARTITIONS
WHERE table_name IN ('fct_scout_funnel', 'obt_scout_funnel')
  AND partition_id NOT IN ('__NULL__', '__UNPARTITIONED__')
GROUP BY table_name;

INFORMATION_SCHEMA.PARTITIONS はデータセット修飾が必須で、日次パーティションの partition_id は '20260620' の形。__NULL__ と __UNPARTITIONED__ の擬似パーティションを除かないと平均が歪む。

このビュー自体も課金対象である。オンデマンド課金では処理バイトが 10 MB 未満でも 1 回あたり最低 10 MB が課金され、しかも INFORMATION_SCHEMA へのクエリは結果がキャッシュされないので、同じクエリでも回すたびに課金される。

クエリ 1 本ぶんの見積りは dry-run で取る。star と OBT を同じ問いで比べるときに使う。

bq query --use_legacy_sql=false --dry_run \
  "SELECT sd.sender_type, SUM(f.is_replied) AS replied
   FROM marts.fct_scout_funnel AS f
   JOIN marts.dim_scout_sender AS sd USING (scout_sender_key)
   WHERE f.sent_date = DATE '2026-06-20'
   GROUP BY sd.sender_type"

bq query --use_legacy_sql=false --dry_run \
  "SELECT sender_type, SUM(is_replied) AS replied
   FROM marts.obt_scout_funnel
   WHERE sent_date = DATE '2026-06-20'
   GROUP BY sender_type"

dry-run は Query successfully validated. ... this query will process N bytes of data. を返す。この N を 2 本で比べるのが、OBT を作る前に必ずやる作業である。N が star より増えるなら、OBT の正当化は「速い」ではなく「BI が結合を間違えない」でなければならない。

日付条件を WHERE EXTRACT(MONTH FROM f.sent_date) = 6 のような形に書き換えて N を見ると、プルーニングが外れたときのバイト数が分かる。

4BI ツール問わない1 億以上star のまま + 集約を配布Type1 の 1 回の上書きが全行の書き換えになる。ファクト粒度の OBT ではなく集約テーブルを配る（08 回）
5BI ツール日次以上問わないstar のまま + 集約を配布全行の再生成が毎日走る
6アナリスト（SQL を書く・少人数）月数回以下1 億未満star + OBT を配布OBT はビューではなくテーブル。再生成は日次で足りる
7複数ファクトの横断（返信率 × 入社率）問わない問わないstar のままOBT ではコンフォームドディメンションが失われ、横断（drill across）ができない
8自分（SQL を書く）問わない問わないstar のまま結合を間違えない利用者に OBT を配る意味がない。維持コストだけが増える。star をまだ持っていなくても、1 行目の規模を超えるなら先に star を作ってから判断する

読み方: 上から順に当てはめ、最初に一致した行を採る。行は具体的なものから一般的なものへ並べてあり、1 行目は「小さく始めるとき何を作るか」、8 行目はそこから漏れた全ての場合を受ける。

「OBT のみ」に落ちるのは 1 行目だけで、それ以外は star が必ず存在する。

7. 演習

(a) fct_page_view（数億行）を OBT 化すべきか。クラスタリング列は何か

解答例

OBT 化しない。§6 の表の 4 行目（BI ツール × 更新頻度を問わず × 1 億以上）に当たる。

dim_company.name は Type1 なので、企業名を焼き込むと社名変更のたびに全期間の書き換えが要る（§2a）。月に 1 度の社名変更でも数億行が動く。

配布するなら、agg_company_rating_daily と同じ形の「企業 × 日粒度の閲覧集約」か、直近 90 日だけの期間限定 OBT にする（どちらも正典には無いので、作るなら正典への追加が要る）。

クラスタ列は正典どおり company_key を先頭に置く。パーティションは view_date。

-- models/marts/fct_page_view.sql（OBT ではなくファクト本体の config）
{{ config(
    materialized='incremental',
    partition_by={'field': 'view_date', 'data_type': 'date', 'granularity': 'day'},
    cluster_by=['company_key', 'page_context_key']
) }}

2 列目は用途で決まる。「企業ページの中で求人詳細だけ見たい」が主なら page_context_key（72 行のジャンク＝カーディナリティは低いが、企業内での絞り込みには効く）。「会員単位の行動を追う」が主なら member_key。

ただし member_key は匿名 -1 に大きく偏るので、先頭には置かない。

(b) agg_company_entity は OBT か集約か

解答例

どちらでもなく「ディメンション粒度の集約」。粒度が 1 行 = 1 企業（company_key）で、ファクト粒度ではない。OBT は「ファクト 1 行に全ディメンション属性を付けた表」なので定義が違う。

粒度行数再集計
obt_scout_funnel1 スカウトファクト行数と同じできる（メジャーが原子粒度）
agg_company_entity1 企業企業数できない（avg_overall_score_90d は窓が固定）

正典の固定判断どおり、集約は avg_* を持たず sum_* + count を持つべきだが、agg_company_entity の avg_overall_score_90d は窓が 90 日に固定された指標なのでこの例外になる。エンティティ中心の集約としての扱いは 08 回。

(c) obt_scout_funnel の member 属性は as-of か現在値か、両方持つか

解答例

as-of（送信時点）を既定にする。正典の固定判断「ファクトにはイベント時点の SCD2 キーを持つ」に従う。S001（2026-06-20 送信）で M001 の属性を引くと、6/15 の変化後・8/1 の入社前の行が返る。

現在値は OBT に載せない。載せると 2 つの問題が同時に起きる。(1) M001 の属性が変わるたびに、その会員宛の全スカウト行（全期間・全パーティション）を書き換える必要がある。(2) 同じ表の中に時点の違う 2 系統の列が並び、アナリストが member_region_asof と現在値の列のどちらで切ったのかを追えなくなる。

現在値で見たい問いは star 側で組む。

SELECT
    m_now.region,
    COUNT(*) AS scouts_received
FROM marts.fct_scout_funnel AS f
JOIN marts.dim_member AS m_asof
    ON f.member_key = m_asof.member_key
JOIN marts.dim_member AS m_now
    ON m_asof.member_id = m_now.member_id
   AND m_now.is_current
WHERE f.sent_date BETWEEN DATE '2026-03-01' AND DATE '2026-08-31'
GROUP BY m_now.region;

例外は 1 つだけ。現在値での絞り込みが BI の常用パターンになり、かつ会員数が十分小さいなら、OBT ではなく「member_id と現在値属性だけの薄い表」を別に配る。BI 側の結合は 1 本で済み、更新は会員数ぶんの行に閉じる。

8. 参考: 手元の基盤ではどうか

mart_url_performance は url_path × date 粒度の集約マートで、OBT ではない（ファクト 1 行に属性を付けた表ではない）。上流に star を持たない形は §6 の表の 1 行目に当たり、この規模では正しい。

mart_url_performance_incremental は date に partition_by を持つ（cluster_by は無い）。それでも増分境界 DATE(request_timestamp) > (SELECT MAX(date) FROM {{ this }}) が §4 の「サブクエリによる動的式」そのもので、上流 stg_access_logs（view）は毎回全スキャンされる。境界を変数に取って定数リテラルで渡す形に書き換え、§5(d) の dry-run を前後で比べるのが最小のチュートリアル。

news_pipeline の summaries はスコアを再採点で上書きする（Type1）ので、本文と要約を 1 表に非正規化していたら /recalculate のたびに §2(a) と同じ全行書き換えが起きていた。
