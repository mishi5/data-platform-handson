用語の確認。ディメンション（dim_*）は集計の切り口となる属性の表、ファクト（fct_*）は出来事と数値の表、サロゲートキー（*_key）はソースの ID とは別に DWH 側で振る代理キーを指す。SCD（Slowly Changing Dimension）はディメンションの属性が時間とともに変わったときの持ち方で、Type 0〜7 の番号で呼び分ける。縮約ディメンションは、あるディメンションの属性の一部だけを持つ粗い版（担当者に対するエージェンシーなど）である。

1. この資料で決めること

ディメンションの属性が変わったとき、古い値をどう残すか。残し方は Type 0〜7 の 8 通りあり、それぞれ「行が増えるか」「ファクトから見えるのは版か現在値か」が違う。この資料はその選択と、選んだ結果として必ず必要になる 時点結合（as-of join。イベント時点の版でファクトのキーを解決する結合） の実装を決める。

2. よくある失敗

(a) dim_company を Type1 にする — 過去のレポートが翌月には別の数字になる

C002（ネクスト技研）は 2026-05-01 に employee_size_band が 50_299 から 300_999 へ変わった。R001 は 2026-03-10 投稿、当時の C002 は 50_299 である。Type1 で上書きすると R001 は 300_999 帯のクチコミとして集計され、「規模帯別のクチコミ平均スコア」が過去に遡って動く。

設計2026-04 に出したレポート2026-06 に同じ SQL を流した結果
Type1（上書き）50_299 の平均に R001（3.5）が入る300_999 の平均に R001 が移る。両方の帯の数字が変わる
Type2（版を追加）50_299 の平均に R001 が入る同じ。fct_review.company_key が 3 月版を指しているので動かない

Kimball はこれを「Type 1 destroys the history of a particular field」と書く。事前計算した集約についても「Precomputed aggregates (including materialized views and automatic summary tables) that depend on the Home City field must be taken offline at the moment of the overwrite and must be recomputed before being brought back online」と付け加えている。CareerVoice では agg_company_rating_daily がそれに当たる。

(b) fct_scout を現在の member_key で結ぶ — スカウトの宛先が入社後の姿になる

M001 は 2026-06-15 に job_change_intent が passive → active、annual_income_band が 400_600 → 600_800 に変わり、2026-08-01 に C001 へ入社した（current_company_id が C002 → C001）。S001 は C001 が 2026-06-20 に送ったスカウトである。

現在の版で結ぶと、S001 は送信当時の版（current_company_id = C002、区間 [2026-01-05, 2026-08-01)）ではなく 8/1 入社後の版に紐づく。すると「C001 が自社に在籍している会員へスカウトを送った」ように見える。

企業別スカウト返信率の分母から自社社員を除く運用ルールがあれば S001 は消え、無ければ返信率が不当に高く出る。どちらにせよ、そのスカウトが受け入れられた理由（当時 C002 在籍で、6/15 から active になっていた）が読み取れなくなる。

fct_scout は会員について 2 本のキーを時点結合で解決する。この 2 本は区間の切れ目が違う。

解決するキー参照先S001（6/20）が当たる区間そこから読める属性
member_keydim_member（Type 2）[2026-01-05, 2026-08-01)current_company_id = C002
member_profile_mini_keydim_member_profile_mini への割当（Type 4）[2026-06-15 09:12, 2026-08-01)600_800 / active

6/15 の変化は dim_member の版を切らない。切り出し先が dim_member_profile_mini（Type 4）だからである。dim_member に「6/15 始まりの版」は存在しない——この点がこの資料で最も間違えやすく、§7-b で改めて問う。

(c) valid_to を NULL にする — 8 月以降のイベントだけが気づかれずに除外される

dbt snapshot の既定では現行行の dbt_valid_to は NULL である。この列をそのまま valid_to にすると、範囲述語が NULL との比較になって UNKNOWN を返し、その行が結果から除外される。

-- 現行行が valid_to = NULL の場合
where s.sent_at between dm.valid_from and dm.valid_to   -- 現行行に当たるはずの行が落ちる

問題は気づきにくさにある。S001（6/20）が当たるのは dim_member の [2026-01-05, 2026-08-01) の版で、この行は 8/1 に既に閉じている（valid_to が入っている）。誤りが出るのは 8/1 以降のイベントだけなので、テストデータでは再現しない。

内部結合なら行が消え、外部結合なら member_key が NULL になって -1（未知）に置き換わる。

もう 1 つ、BETWEEN そのものが注意点になる。Kimball は「The end-effective-datetime of a Type 2 dimension record must be exactly equal to the begin-effective-datetime of the next change」と規定し、dbt snapshot もこの規約に従う。境界時刻ちょうどのイベントは BETWEEN だと 2 つの版に当たり、ファクトが 2 行に増える。

-- 正しい形: valid_to に 9999-12-31 を入れ、範囲は半開区間にする
where s.sent_at >= dm.valid_from
  and s.sent_at <  dm.valid_to

3. Kimball の原則

技法定義（Design Tip #152 / SCD Part 1–2）使う条件
Type 0「the dimension attribute value never changes, so facts are always grouped by this original value」版をまたいで変わらない識別子（durable key）と、日付ディメンションの属性
Type 1既存の値を新しい値で上書きする(1) 誤りの訂正 (2) 履歴を追わないと明示的に決めた属性。ただし規制対象の環境では「Type 1 changes may be outlawed」
Type 2新しいサロゲートキーの行を追加する。有効開始（effective）と有効終了（expiration）の日時、変更理由、現行行フラグ（current flag）を持つ履歴を完全に残す必要があり、行の増加が許容できる規模
Type 3「alternate reality（もう一つの現実）」を表す列を追加し、旧値をそこへ退避して主列を上書きする属性が視点によって正当に複数の値を持つとき（商品分類の付け替えなど）
Type 4「A group of dimension attributes are split off into a separate mini-dimension.」ファクトが元のディメンションとミニディメンションの両方のサロゲートキーを持つ速く変わり、かつ値の組合せ数が小さい属性群
Type 5Type 4 に加え、元のディメンション側に「current profile（現在のプロファイル）」を指すミニディメンションのキーを Type1 属性として埋め込むファクトを経由せずに現在のプロファイル値へ辿りたいとき
Type 6「Fact rows can be filtered or grouped by either the type 2 value in effect when the measurement occurred or the attribute's current value.」現在値は、版をまたいで変わらない同じ識別子（durable key）を持つ全ての過去行へ上書きされる版と現在値の両方で同じ属性を切りたいとき
Type 7「the fact table contains dual foreign keys for a given dimension: a surrogate key linked to the dimension table where type 2 attributes are tracked, plus the dimension's durable supernatural key linked to the current row in the type 2 dimension to present current attribute values」Type 6 と同じ効果を、物理的な上書きなしに得たいとき

Design Tip #15 — Type 6 は 2+3+1 である。 Margy Ross は Type 2 を土台に置いた上で、「For all prior dimension rows for a given product, the current roll-up attribute will be overwritten to reflect the current state of the world」と書き、この組合せの呼び名を「As a student recently suggested, perhaps we should refer to this as Type 6 (2+3+1)」——受講生の提案として——書き留めている。Type 2 の効果については「the fact table rows will reference the new surrogate key with the new roll-up thereby perfectly partitioning history」。履歴を分割するのはディメンションではなく、ファクトが指すキーである。

ファクトはロード時点でサロゲートキーを解決する。 Kimball は「With a dimension undergoing Type 2 processing, great care must be taken to use the correct contemporary surrogate keys from this dimension in every affected fact table. This assures that the correct dimension profiles are associated with fact table activity」と書き、この処理を「The extract, transform and load (ETL) process for aligning the dimension tables with fact tables at load time is called the surrogate key pipeline」と名付けた。

この原則の実務上の意味は 2 つある。

  • 時点解決のロジックは ETL に 1 か所だけ置き、クエリには持ち込まない。
  • 一度書いたファクト行のキーは後から書き換えない。ディメンション側に新しい版が増えても、既存のファクト行は古い版を指し続ける。

4. 現代の再解釈

ディメンションの日次スナップショット（Functional Data Engineering）

Beauchemin の主張は「パーティション（行ではなく）が状態の最小単位である」ことに尽きる。the partition (not the row) is the atomic unit of state; always overwrite whole partitions instead of UPDATE/DELETE/APPEND。ディメンションについてはさらに直接的で、SCD2 の代わりに append a full snapshot per run; trade cheap storage for clarity and reproducibility と書く。毎日、ディメンション全体を snapshot_date パーティションに丸ごと書く。

観点SCD2日次スナップショット
時点結合の書き方event_at >= valid_from AND event_at < valid_to（境界と NULL の扱いを毎回間違える）snapshot_date = DATE(event_at) の 1 述語
冪等性MERGE で既存行を UPDATE する。再実行すると valid_to の状態に依存するパーティション単位の全置換。何度流しても同じ
バックフィル日次逐次。11 月を直すには 11/01 から 30 本を順番に流す日ごとに独立。30 日ぶんを並列で流せる
コードの本数日次用とバックフィル用で別ロジックになりがち1 本
行数会員数 + 変化回数会員数 × 日数
時間精度ソースの updated_at の精度そのまま（秒）日単位に切り捨てられる。日の途中の変化は次のスナップショットまで見えない
「その日の母集団」の問い毎回、時点結合の述語を書く必要があるWHERE snapshot_date = '2026-06-20' で終わる

Zach Wilson「SCD-2 considered harmful」の核心は運用コストである。 彼が挙げるのは主に次の 3 つである。

  • バックフィルの直列性 —「To fix November 15th, you'd need to... Rerun November 1st... wait for it to finish... Rerun November 2nd...」
  • クエリの複雑さ —「To get user data 'as of 3 months ago', you need... WHERE valid_from <= '2024-10-01' AND (valid_to > '2024-10-01'...」
  • 日次用とバックフィル用の 2 系統のコードを同期し続ける負担

代替は「all 30 days kick off in parallel... The whole month finishes in the time it takes to run one day」。

ただし記事のコメント欄で Chris Gambill が反論している。人手で編集される業務データ（Salesforce / NetSuite / HubSpot）は「Those records flip after the fact, and auditors expect an immutable trail tied to who changed what and when」であり、日次スナップショット単体では監査に耐えない。

だが彼の結論は SCD2 への回帰ではない。「So the choice isn't "SCD2 vs datestamps." It's immutable facts at the base, with snapshots or SCD2 as views that match the model and the risk」——CDC またはイベントログを基盤に置き、スナップショットも SCD2 もその上のビューにする、である。Wilson はこれに答えていない。

CareerVoice はこの前提を既に満たしている。ソースは Datastream（CDC）で src_careervoice に複製されており、snap_companies も dim_member_daily も、その不変ログの上に載るビューにすぎない。

何が変わり、何が残るか

変わるのは実装手段だけである。「イベント時点の属性でファクトを集計する」という要求そのものは Kimball の時代から変わっていない。SCD2 も日次スナップショットも、その要求を満たすための 2 通りの物理設計にすぎない。

残るのは「ファクトはロード時点で時点属性を確定する」という原則の方である。これはスナップショット方式でも同じで、WHERE snapshot_date = DATE(sent_at) をロード時に 1 回だけ書く。

会員数百万高（意欲・年収帯は月単位で動く）日次スナップショット dim_member_daily。dim_member（Type2）は member_key の発行と変化の遅い属性に限定(1) 数百万 × 変化頻度の Type2 は、valid_from/to の境界がソースの updated_at の精度に左右され、誤った版に結ばれやすい (2) 「6/20 時点で active な会員は何人」という母集団の問いが多く、これはスナップショットの得意形 (3) 行数 300 万 × 365 日は BigQuery のパーティション + クラスタリングで吸収できる。クエリは常に 1〜2 パーティションに閉じる
企業数万低（employee_size_band は年 1 回程度）SCD2（name は Type1 ＝ Type 6）(1) 行の増加が問題にならない (2) 日次にすると「変化の無い日の行」が 99.9% を占め、dim_company を参照する全ファクトに日付結合を強いる (3) name の Type1 上書きは 1 テーブルに閉じている方が自然
エージェント担当者・エージェンシー数千 / 数十中（移籍・ティア変更）SCD2（dim_agent と、その縮約 dim_agency）成果報酬の帰属が移籍前後で変わる。1 件ごとの帰属が金額に直結するので、日単位に切り捨てず秒精度で持つ。縮約ディメンションは元と同じ SCD 型でなければならない（片方だけ Type1 にすると §7-a の食い違いが起きる）

会員について両方持つのは冗長に見えるが、役割が違う。dim_member（Type2）はファクトが指すキーの発行元で、変化の遅い属性しか持たないので版は増えない。dim_member_daily は母集団と時点属性の参照先で、こちらは日次で全件を持つ。

速く変わる annual_income_band / job_change_intent は、§1 の判断どおり dim_member_profile_mini（Type 4）へ切り出してある。したがって dim_member の版が増えるのは current_company_id のような転職イベントだけである。

5. BigQuery + dbt での実装

時点結合が何をしているか

(a) dbt snapshot で snap_companies → dim_company を組む

スナップショットはソースの生の形のまま取る。加工は下流のモデルで行う（スナップショットの定義に SELECT を書くと、後からロジックを直したときに過去の版を作り直せなくなる）。

# snapshots/snap_companies.yml
snapshots:
  - name: snap_companies
    relation: source('src_careervoice', 'companies')
    config:
      schema: snapshots
      unique_key: company_id
      strategy: timestamp
      updated_at: updated_at
      dbt_valid_to_current: "cast('9999-12-31' as timestamp)"

  - name: snap_members
    relation: source('src_careervoice', 'members')
    config:
      schema: snapshots
      unique_key: member_id
      strategy: timestamp
      updated_at: updated_at
      dbt_valid_to_current: "cast('9999-12-31' as timestamp)"

dbt_valid_to_current を指定すると現行行の dbt_valid_to が NULL ではなく 9999-12-31 になる（§2-c）。既に NULL で運用しているスナップショットには COALESCE を挟む。なお dbt_valid_to_current と、この YAML 形式のスナップショット定義自体が dbt Core 1.9 以降である（1.8 以下は snapshots/*.sql のブロック形式で、dbt_valid_to_current が無いぶん COALESCE 側で吸収する）。

strategy: timestamp は updated_at の前進で変化を検知する。companies / members はどちらも CDC で updated_at が入るのでこれで足りる。updated_at 相当の列が無いソースだけ strategy: check + check_cols にする。

スナップショットは、実行を始めた日より前の履歴を作れない。 dbt snapshot が見るのは実行時点のソースの現在値だけである。snap_members の初回実行が 2026-07 なら、M001 の第 1 版の dbt_valid_from は 2026-01-05 ではなく 7 月の値になり、6/15 の変化は永久に取れない。

この資料の結果表はすべて「2026-01-05 以前からスナップショットが毎日実行されている」ことを前提にしている。前提が崩れるなら、ソース側に履歴があるうち（Datastream の CDC ログ）に初期版を投入するか、「この日から履歴がある」を下流へ明示する。実行間隔より短い変化を取りこぼすのも同じ理由で、timestamp と check のどちらでも起きる。

ここで §4 の主張の範囲を確認しておく。日次スナップショット方式が有利なのは捕捉済みの期間を作り直せる点で、各日のパーティションを独立に・並列に再計算できる。SCD2 のテーブルは MERGE の結果として状態を持つため、同じ日を流し直しても元に戻らない。

一方、捕捉していない履歴はどちらの方式でも復元できない。 dim_member_daily も snap_members の上に載っているので、snap_members が持っていない 1〜6 月のパーティションは作れない。遡って作れるのは、ソース側に updated_at 付きの履歴（Datastream の CDC ログ）が残っている場合だけである（1 パーティションを作り直す手順は DM09『増分・遅延到着・冪等性』の演習で扱う。1〜6 月をまとめて作り直す話はそこには無い）。

# models/marts/schema.yml（抜粋）
models:
  - name: dim_company
    data_tests:
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [company_id, valid_from]
      # 各版の区間が空でないことだけを見る（重なり・隙間は下の singular test）
      - dbt_utils.expression_is_true:
          expression: "valid_from < valid_to"
    columns:
      - name: company_key

      - name: is_current

          - not_null

expression_is_true は 1 行の区間が空でないことしか見ない。重なりも隙間も検出しない。 この資料で最も検証したい 2 つがそれなので、singular test（SQL を 1 本書き、行が返らないことを確かめる形式の dbt のテスト）を 1 本立てる。

-- tests/assert_dim_company_no_gap_or_overlap.sql
-- 隣り合う版が「前の valid_to = 次の valid_from」で連続していない行を返す
select company_id, valid_from, valid_to, next_valid_from
from (
    select
        company_id, valid_from, valid_to,
        lead(valid_from) over (
            partition by company_id order by valid_from
        ) as next_valid_from
    from {{ ref('dim_company') }}
)
where next_valid_from is not null
  and next_valid_from != valid_to

corporate_number は Type 2 のディメンションの中に置かれた Type 0 属性である。版をまたいで変わらないことが同一性の保証になるので、変わったら別法人だと分かる。この Type 0 の性質も 1 本のテストで押さえられる。

-- tests/assert_dim_company_corporate_number_is_type0.sql
-- 同じ company_id の版で corporate_number が変わっている（= 別法人の使い回し）行を返す
select company_id
from {{ ref('dim_company') }}
group by company_id
having count(distinct corporate_number) > 1

1 つのディメンションに複数の Type が同居するのはこの資料の主題そのもので、dim_company は corporate_number=0 / name=1 / それ以外=2 の 3 種類を 1 テーブルに載せている。

上の expression_is_true のテストは §2-c で引いた Kimball の規約（旧行の valid_to = 新行の valid_from）をそのままテストにした形である。隙間があるとキーが解決できずに -1 になり、重なりがあるとファクトの行が増える。relationships テストはどちらも検出しない（NULL 行を無視し、行数の増加も見ない）。

この資料の dim_company は name を Type1 のみで持つ。Design Tip #15 の完全な Type 6 は「当時の社名」と「現在の社名」を両方列として持つ形だが、CareerVoice では社名を集計軸にしないので現在値だけにした。企業の同一性は company_id と corporate_number（法人番号）が担保する。監査で「当時のレポートの社名」を再現する要求が出たら Type 6 に格上げする（§7-c）。

(b) 時点結合で fct_scout の member_key を解決する

まず dim_member を作る。snap_members は members のどの列が変わっても版を切るので、dim_member の属性だけを見ると同じ内容の版が連続する。連続する同内容の版を 1 行にまとめないと、member_key が意味なく増える。

-- models/marts/dim_member.sql
{{ config(materialized='table', cluster_by=['member_id']) }}

with versions as (

    select
        member_id,
        birth_year,
        gender,
        prefecture_code,
        current_company_id,
        current_job_category_code,
        registered_at,
        dbt_valid_from as valid_from,
        coalesce(dbt_valid_to, timestamp '9999-12-31') as valid_to
    from {{ ref('snap_members') }}
    where deleted_at is null

),

-- dim_member の属性が実際に変わった版だけにフラグを立てる
flagged as (

    select
        *,
        case
            when to_json_string(struct(
                     birth_year, gender, prefecture_code,
                     current_company_id, current_job_category_code))
                 = lag(to_json_string(struct(
                     birth_year, gender, prefecture_code,
                     current_company_id, current_job_category_code)))
                   over (partition by member_id order by valid_from)
            then 0 else 1
        end as is_change
    from versions

),

collapsed as (

    select
        *,
        sum(is_change) over (
            partition by member_id order by valid_from
            rows between unbounded preceding and current row
        ) as version_no
    from flagged

)

select
    farm_fingerprint(concat(v.member_id, '|', cast(min(v.valid_from) as string))) as member_key,
    v.member_id,
    any_value(v.birth_year)                as birth_year,
    any_value(v.gender)                    as gender,
    any_value(pf.name)                     as prefecture,
    any_value(pf.region)                   as region,
    any_value(v.current_company_id)        as current_company_id,
    any_value(v.current_job_category_code) as current_job_category,
    date(any_value(v.registered_at), 'Asia/Tokyo') as registered_date,
    min(v.valid_from) as valid_from,
    max(v.valid_to)   as valid_to,
    max(v.valid_to) = timestamp '9999-12-31' as is_current
from collapsed as v
left join {{ ref('stg_careervoice__prefectures') }} as pf
    on pf.prefecture_code = v.prefecture_code
group by v.member_id, v.version_no

スナップショットは「変化しなかった日」も書く。 会員 300 万人なら 1 日 300 万行、1 年で約 11 億行になる。これが成立するのは次の 3 つが揃うからである。

  • パーティションが snapshot_date で切れていて、クエリが 1〜2 パーティションに閉じる
  • 列指向で、同じ値が続く列は圧縮が有効に働く
  • require_partition_filter: true が全走査を禁じる

BigQuery で require_partition_filter を外したままこの設計にすると、1 クエリで年間全走査が起きる。

(d) 「現在値で見たい」ときは自然キーで再結合する

ファクトが指しているのはイベント時点の版である。現在値で切りたい要求は、同じ dim_company をもう一度、company_id（版をまたいで変わらない自然キー）で結んで満たす。ファクトに二重の外部キーを持たせる Type 7 は採らない。

select
    at_review.employee_size_band as size_band_at_review,   -- 投稿当時の規模
    now.employee_size_band       as size_band_current,     -- 現在の規模
    count(*)                        as review_count,
    sum(f.overall_score)            as sum_overall_score,
    safe_divide(sum(f.overall_score), count(*)) as avg_overall_score
from {{ ref('fct_review') }} as f
inner join {{ ref('dim_company') }} as at_review
    on at_review.company_key = f.company_key
inner join {{ ref('dim_company') }} as now
    on  now.company_id = at_review.company_id
    and now.is_current
group by 1, 2
order by 1, 2
C002 のクチコミがどこに載るか（R001 = 2026-03-10 投稿、C002 は 2026-05-01 に規模帯が変化）
切り口行意味
size_band_at_review50_299「50〜299 人の会社に対するクチコミの平均は 3.5」— 投稿当時の実感
size_band_current300_999「いま 300〜999 人の会社が過去に受けたクチコミの平均は 3.5」— 現在の企業群での比較

どちらも正しく、問いが違う。Type 1 だけの設計は前者を、Type 2 だけの設計は後者を答えられない。この 2 段結合で両方を返せることが、§1 で「ファクトはイベント時点の company_key を持ち、現在値は company_id で再結合する」と決めた理由である。

7. 演習

(a) 担当者の移籍と成果報酬の帰属

エージェント担当者 AG01（佐藤）が、エージェンシー A01（キャリアブリッジ、gold）から A02（ワークリンク、standard）へ移籍した。移籍前に AG01 が成立させた fct_placement の fee_amount は、どちらのエージェンシーに計上されるべきか。fct_placement は agency_key と agent_key の両方を持つことに注意する。

解答例

既定では「移籍前の A01」に計上される。 placements.agency_id はソースが持っている「契約したエージェンシー」なので、移籍しても過去の行の値は A01 のままである。agency_key はそれを hired_at 時点で dim_agency の版へ時点結合するだけで、正しい答えが出る。

agent_key（scouts.sender_agent_id 経由、無ければ -1）も hired_at 時点の dim_agent の版を指し、そこには平坦化された agency_name = キャリアブリッジ、agency_tier = gold が入っている。2 つの経路が同じ答えを返すのが正しい状態である。

この一致が失われるのは、片方だけ Type1 にしたときである。 dim_agent を Type1 にすると agent_key は変わらないまま agency_name / agency_tier だけが A02 / standard に上書きされる。すると同じ fct_placement の 1 行から、agency_key 経由では A01、agent_key 経由では A02 という 2 つの答えが出る。縮約ディメンションは元のディメンションと同じ SCD 型に揃えなければならない、というのがこの演習の結論である。

その上で「どちらのエージェンシーに計上すべきか」は業務ルールで決まる。判断基準の表の行の使い分けは次のとおり。

業務上の問い正しい帰属適用する行
成果報酬の請求先はどこか（会計）A01（契約したのは移籍前のエージェンシー）「〜数千 × 月単位 × 秒 → Type 2」。既定の時点結合がそのまま答えになる
いまワークリンクにいる担当者は累計いくら決めたか（人事評価）A02「版と現在値の両方が要る → 自然キー再結合」。agent_id で dim_agent の is_current 行へ再結合する（§5-d と同じ 2 段結合）
A01 が A02 に吸収合併されたA02（過去分も遡って移す）これは移籍ではなく法人格の承継である。dim_agent / dim_agency の SCD ではなく、エージェンシーの承継関係を別に持つ問題（企業側の br_company_hierarchy と同型。DM06『多対多・不揃い階層・異種ディメンション』で扱う）

設計としては 時点結合を既定にしておくのが安全である。後から「現在の所属で見たい」は再結合で足せるが、Type1 で上書きしてしまうと請求先を復元できない。

(b) M001 の dim_member は何行になるか

M001 は 2026-06-15 09:12 に job_change_intent が passive → active、annual_income_band が 400_600 → 600_800 に変わり、2026-08-01 00:00 に C001 へ入社して current_company_id が C002 → C001 になった。dim_member は何行になり、各行の valid_from / valid_to はどうなるか。

解答例

2 行になる。

member_keycurrent_company_idvalid_fromvalid_tois_current
(v1)C0022026-01-05 00:00:00（登録時点）2026-08-01 00:00:00false
(v2)C0012026-08-01 00:00:009999-12-31 00:00:00true

6/15 の変化は annual_income_band と job_change_intent だけで、この 2 列は §1 の判断で dim_member_profile_mini（Type 4）に切り出してある。dim_member の属性は 1 つも動いていないので版は増えない。snap_members には 3 版できるので、§5-b の flagged / collapsed の CTE で、連続する同内容の版を 1 行にまとめる必要がある。

まとめないと何が起きるか。dim_member が 3 行になり、fct_scout の member_key の distinct 数が「会員の実質的な状態数」とずれる。COUNT(DISTINCT member_key) を会員数の近似に使っている集計（agg_*）が水増しされる。

member_id で数え直せば直るが、そもそも member_key は「区別すべき状態が変わったところ」で切るべきものである。

参考: S001（6/20）と P001（6/23）はどちらも (v1) に当たる。属性の違いは member_profile_mini_key = (600_800, active) 側で表現される。

(c) dim_company.name を Type1 にして困る分析はあるか

§1 の判断では dim_company.name は Type1（現在の社名で全版を上書き）である。この判断で困る分析があるか。あるなら、それは Type1 の問題か別の問題か。

解答例

通常の分析では困らない。 企業の同一性は company_id が担保し、社名は表示用ラベルである。「旧社名で GROUP BY したい」という問いは存在せず、判断基準の表の「変化は誤りの訂正だけ／履歴を追わないと決めた属性 → Type 1」の行がそのまま当てはまる。

困るのは次の 2 つの場面である。

場面何が起きるかType1 の問題か
監査・突合。2026-03 に配信したレポートや公開したクチコミページと、いま同じ SQL を流した結果を突き合わせる社名が変わっていて一致しない。「当時のレポートに載っていた社名」を DWH から復元できないType1 の問題。 再現性が要件なら Type 6 に格上げする（name を版ごとに残し、current_name を Type1 で併置。Design Tip #15 の完全形）
社名変更が合併を伴う。corporate_number も変わる旧法人に対する R001 のようなクチコミが、新法人の評価に混ざるType1 の問題ではない。 別法人なのに company_id を使い回したことが原因。corporate_number の変化を検知したら新しい company_id を発行し、承継関係は br_company_hierarchy で表す（DM06『多対多・不揃い階層・異種ディメンション』で扱う）

後者は SCD の型をいくら変えても直らない。「同一性をどのキーで判定するか」の問題であり、SCD はその前提の上に乗る技法だからである。

8. 参考: 手元の基盤ではどうか

  • news_pipeline の summaries は /recalculate でスコアを上書きする。この上書きは Type 1 である。scoring_version で「どの採点ロジック版か」は分かるが、「ある記事が 0.72 から 0.61 に下がったのはいつか」は残らない。プロンプトを変えた前後で通知ランキングがどう動いたかを検証できない。
  • この資料の基準を当てると、行数は数千、変化頻度は再採点のたび、必要な時間精度は日 —「数百万以上」に当たらないので Type 2 も現実的だが、summaries には updated_at 相当の列が無い（日時列は raw_articles 側にしかない）。strategy: timestamp が使えず strategy: check + check_cols になる、という制約がそのまま設計を決める。
  • dbt_logs_analysis には SCD の対象になるディメンションが 1 つも無い。mart_url_performance も mart_error_analysis もファクトの集約で、url_path や HTTP ステータスは Type 0 の世界である。属性を持つマスタが無い基盤では、この資料の論点そのものが発生しない。
  • 試せる種: snapshots/snap_summaries.yml を strategy: check, check_cols: ['importance_score', 'relevance_score'] で置き、/recalculate の前後で dbt_valid_from がどう切れるかを見る。スナップショットが「実行間隔より短い変化を取りこぼす」ことも同時に確認できる（これは check 固有ではなく、timestamp でも同じ）。
