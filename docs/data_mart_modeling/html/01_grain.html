用語の確認。粒度はファクト表の1行が意味するものの水準。ディメンション（dim_*）は切り口となる属性の表、ファクト（fct_*）は出来事と数値の表。コンフォームドディメンション（共通ディメンション）は複数のファクトが同じ定義・同じキーで共有するディメンション、退化ディメンションはディメンション表を作らずファクトに残す自然キー（review_id など）、サロゲートキー（*_key）はソースの ID とは別に DWH 側で振る代理キーを指す。

1. この資料で決めること

この資料で固定するのは一点だけ。「このファクトの1行は何を意味するか」を一文で宣言できるか。宣言できない表は作らない。

宣言の順序は「ソース → 粒度 → ディメンション → ファクト」（DWT ch.2 の4ステップ）。この順序を入れ替えると、ディメンションの都合で粒度が後付けに決まる。粒度が混ざった表は例外なく二重計上する。

決めること選択肢この資料の結論
1行の意味の水準原子（1イベント）／集約（1日・1月にまとめる）原子で宣言する。集約は agg_* として別テーブルに作る（集約テーブルの作り方は DM04『加法性と派生指標』で扱う）。集約だけを持つのは禁止（DT#77）
宣言の順序①ソース → ②粒度 → ③ディメンション → ④ファクトこの順序は変えない。ディメンションとファクトには、宣言した粒度に合っている（1行の意味と同じ水準の）属性と数値だけを入れる
1表に複数の粒度混ぜる／分ける分ける。プロセスが違えば表も違う（fct_review と fct_review_moderation、fct_scout と fct_scout_funnel）
粒度をどこに書くか設計書／Wiki／コードdbt の description 第1文（「1行 = …」）＋ dbt_utils.unique_combination_of_columns テスト。文書だけでは腐る
行（プロセス）の単位部門／ビジネスプロセスビジネスプロセス（DT#3）。「営業部のマート」を作らない
バスマトリクス—この資料の §3 に置く全体表を基準にする。ビジネスプロセス（行）と共有するディメンション（列）の対応をここで一度に決め、個々の列の設計は別の資料で1本ずつ深掘りする

2. よくある失敗

(a) fct_review に「投稿」と「審査イベント」を混ぜる

クチコミの投稿（reviews）と審査の状態遷移（review_moderation_events）は別のビジネスプロセスだが、「どちらもクチコミの話だから1表で」とやると 1行が投稿でも遷移でもある表になる。R001（M001 → C002、2026-03-10 投稿、差し戻し1回を経て 03-12 公開）の遷移は3件ある。

行の出所review_idfrom_status → to_statusoccurred_atoverall_score
投稿（reviews）R001—2026-03-103.5
遷移1（review_moderation_events）R001submitted → screening2026-03-10（複製 3.5）
遷移2R001screening → submitted（差し戻し low_quality）2026-03-11（複製 3.5）
遷移3R001submitted → published2026-03-12（複製 3.5）

この表では、指標ごとに違う絞り込みと重み付けが必要になる。

  • 全行に review_count = 1 を置く: SUM(review_count) = 4。真値は 1。R001 が「4件のクチコミ」として企業ページの評価件数に出る。
  • 遷移行を review_count = 0 にする: 件数は 1 に戻るが、二重計上が消えたわけではない。overall_score はクチコミ粒度の値なので4行すべてに複製されており、AVG(overall_score) は行数＝遷移回数で重み付けされる。差し戻しの多いクチコミほど企業平均を強く引っ張る、という業務上まったく正当化できない重み付けが入る。正しく 3.5 を出すには SAFE_DIVIDE(SUM(overall_score * review_count), SUM(review_count)) のように、集計する側が「どの行が投稿行か」を知って書く必要がある。粒度を宣言した表なら誰も知らなくてよい知識を、利用者全員に要求することになる。

後者の厄介さは、R001 単独では平均が 3.5 のまま正しく見えることにある。誤った値が出ていても気付けない。件数の 1→4 と違い、この歪みはテストでも目視でも表面化しない。

正しくは、投稿は fct_review（1行 = 投稿された1クチコミ、トランザクション）、審査ライフサイクルは fct_review_moderation（1行 = 1クチコミの審査ライフサイクル、累積スナップショット、moderation_rounds = 2 ＝ 審査担当者が判定を下した回数（03-11 の差し戻しと 03-12 の公開）であって、screening を通過した回数ではない）。両者は review_id（退化ディメンション）で繋がるが、同じ表には入らない。

(b) fct_scout と fct_scout_funnel を1表にする

スカウトは S001（C001 → M001、J001、06-20 送信 → 06-21 開封 → 06-22 返信 interested）と S002（AG01 → M003、J002、06-25 送信、未開封）の2件。この2つを1表にまとめるなら、送信・開封・返信をそれぞれ行にして、イベント種別の区分値を持たせる形になる。中身は次のようになる。

scout_idevent_typeevent_date宛先送信主体reply_typescout_count
S001sent2026-06-20M001C001—1
S001opened2026-06-21M001C001—0
S001replied2026-06-22M001C001interested0
S002sent2026-06-25M003AG01—1

実際のファクトでは、宛先と送信主体はサロゲートキー（member_key / scout_sender_key）で持ち、日付は event_date_key と event_date の組で持つ。上の表は中身が分かるように業務上の ID で書いている。

この形なら、送信日でも返信日でも集計できる。6/20 の送信数は event_type = 'sent' で絞って 1、6/22 の返信数は 'replied' で絞って 1、6月の送信数は 2 になる。scout_count を送信行だけに 1 で置いているので SUM(scout_count) も 2 で一致する（全行に 1 を置くと 3 になるため、メジャーはイベント種別に合わせて置く）。後述の fct_selection_event（1行 = 1選考ステージ遷移）と同じ構造であり、それ自体は誤りではない。

それでもスカウトを2表に分けるのは、次の2つの利点があるためである。

  • 集計がシンプルなままで済む: 1行 = 1スカウトなら、送信数は COUNT(*)、開封率は SUM(is_opened) / COUNT(*) で書ける。統合表ではどちらにも event_type の条件が要り、分母と分子で条件が違う指標ほど書き分けが増える。
  • 更新の作法を分けられる: 送信の記録は追加するだけで済み、開封・返信・応募のたびに更新されるのはファネル側だけになる。

この方針で分けた2表は次のとおり。

  • fct_scout — 1行 = 送信された1スカウト。sent_date_key 1本。行は更新されない（不変トランザクション）。
  • fct_scout_funnel — 1行 = 1スカウトの送信→開封→返信→応募。sent_date_key / opened_date_key / replied_date_key / applied_date_key の4本を dim_date のロールプレイングで持ち、行が更新される（累積スナップショット）。S002 の未達マイルストーンは -1（DT#43、NULL 外部キーを作らない）。

粒度が同じでも、この2表は更新の作法が違う。不変な表と更新される表は、1つのパーティション再構築ジョブには乗らない（増分ロードの作法は DM09『増分・遅延到着・冪等性』で扱う）。

(c) fct_selection_event を作らず fct_application_pipeline だけを作る

累積スナップショットは DWT ch.4 が扱うファクト型で、マイルストーンごとの日付キー列を持ち、行が更新される。ここでの論点は累積スナップショットという型の良し悪しではなく、この型「だけ」を持つとどうなるかにある。

P001（M001 → J001、scout_company、06-23 応募 → 07-01 書類 → 07-08 一次 → 07-15 最終 → 07-20 内定 → 07-22 承諾 → 08-01 入社）は、累積スナップショットでは 1行（到達した7つのマイルストーンが日付キー列に埋まる。列としては未到達の closed_date_key を含め8本、未達は -1）、原子ファクトでは 6行（document, first_interview, final_interview, offer, accepted, hired）になる。サマリーだけを持つと、次の問いに答えられなくなる。

答えられない問いなぜ
同じ応募で first_interview が2回起きた（再面接）のは何件かfirst_interview_date_key は1列。2回目は上書きされるか無視される
rejected / withdrawn の直前ステージは何か持っているのは current_stage と is_rejected / is_withdrawn フラグだけ。そこに至る経路は残らない
ステージ間を行き来した応募（差し戻し・保留）の比率マイルストーンが単調に進む前提の構造なので、逆行そのものが表現できない

「2026年7月に発生した選考イベントは全部で何件か」のような件数は、パイプラインの8本の日付キー列を縦に展開すれば数えられる。ただしマイルストーンが増えるたびに展開する部分を書き直すことになり、原子ファクトなら event_date_key で絞るだけで済む。

DT#77（Margy Ross）: “you can’t magically explode summary data into its underlying components.” 集約は原子データの “performance-tuning complements to the atomic level, not replacements.” — サマリーは補完であって代替ではない。

そこでこの題材では、fct_application_pipeline の裏に必ず fct_selection_event を置くと決めておく（ファクトの3つの型の使い分けは DM02『ファクトの3型とファクトレス』で扱う）。逆向きは成立する。原子ファクトからパイプラインは再構築できるが、パイプラインから原子ファクトは復元できない。

3. Kimball の原則

4ステップのディメンショナル設計

この定式化は Grain（2003）のもので、DWT 3rd ed. ch.2 が同じ順序を提示し、ch.3（小売）が実例で通す。順序そのものが主張であって、②を先に置くことに全ての意味がある。

#ステップCareerVoice での具体飛ばすと起きること
1ビジネスプロセス（＝ソース）を選ぶ「選考イベント」を選ぶ。ソースは selection_events部門単位のマートになる（DT#3）
2粒度を宣言する（可能な限り原子で）「1行 = 1応募の1選考ステージ遷移」設計が流砂の上に建つ。以降の議論が堂々巡りになる
3その粒度について知っていることを全てディメンションにする日付・会員・企業・求人・エージェント・職種・チャネルディメンションが後付けになり、粒度が後から動く
4粒度に忠実な数値メジャーを足すevent_count = 1 だけ「この応募の内定までの日数」のような別粒度の数値が紛れ込む
Grain（2003）: “Declaring the grain means saying exactly what a fact table record represents.” / “If the grain isn’t clearly defined, the whole design rests on quicksand… rogue facts that introduce application errors sneak into the design.”
そして粒度違反のメジャーについて: “Helpful facts… aren’t true to the grain. …dangerous because they invite the end user to make mistakes. Omit them from the design.”（訳: 便利そうなファクトは粒度に合っていない。利用者の誤りを誘うので危険であり、設計から外す）

原子粒度の原則

Kimball の主張は「原子粒度は次元数が最大になる」。fct_selection_event の1行には7つのディメンションが自然に付く。これを「応募あたり1行」にまとめた瞬間、ステージ（stage）という軸が消える。

Kimball の言い方では——“Atomic data has the most dimensionality and so it can be constrained and rolled up in every way possible for that data source.”（Grain, 2003）。

粒度は最も原子的な水準で宣言し、集約はそのあとで別テーブルとして作る。集約テーブル（agg_company_rating_daily、agg_company_entity）は原子ファクトから導出される性能チューニングであって、設計の一次判断ではない。この非対称性が DT#77 の核。

DT#3: 行はビジネスプロセス、部門ではない

スカウトのデータは営業も CS も分析するが、表は1つ。“If you establish departmentally-bound marts, you’ll duplicate data… multiple data flows into the marts invariably result in data inconsistencies.” CareerVoice のバスマトリクスに「営業」「編集」「カスタマーサクセス」という行は無い。あるのは「スカウト送信」「クチコミ審査」「応募〜入社」。

DT#179: 粒度宣言が仕様書になる

DT#179 の7項目のうち粒度宣言に関係するのは3つ。“The dimensional model is the best specification for the DW/BI system.”（モデル自体が要求仕様である）、“Dimensional modeling is a group activity.”（粒度宣言は一人で決めるものではない）、“It’s all about the business.”。

だから粒度の一文はビジネス側が読んで是非を判定できる日本語でなければならない。「event_id がユニーク」ではなく「1行 = 1応募の1選考ステージ遷移」と書く理由がここにある。

バスマトリクス（CareerVoice 完全版）

行 = ビジネスプロセス、列 = コンフォームドディメンション。1999年の原文は行を “all the first-level data marts that you could possibly build” と呼んでおり、「ビジネスプロセス」は DWT 3rd ed.（2013）と DT#3 での言い直し。単一ソース1つ＝1行という中身は変わっていない。

列については “a column in the matrix is a map of where the dimension is required”（The Matrix, 1999）。同じ列に ✓ が2つ以上あるディメンションはコンフォームドでなければならない（完全に同一か、一方が他方の完全な部分集合）。このマトリクスがこの題材の設計の基準表になる。以降の資料では各セル・各列を1本ずつ掘り下げるが、行と列の対応そのものはここで決まる。

このマトリクスから読み取れる設計上の事実を3点だけ挙げる。

  • fct_review の member 列だけが ✗。これは技術的制約ではなく方針。少人数企業ではクチコミの属性から投稿者が特定できるため、fct_review は member_key を持たず、投稿時点の会員属性は dim_review_attributes（employment_status × employment_type × years_of_service_band = 30行のジャンクディメンション）に持たせる。会員 × クチコミの結合が必要な分析は int_review_member_link に隔離する。マトリクスの空セルには「そのプロセスに関係ない」と「意図的に持たない」の2種類がある。後者は理由を書き添える。
  • agent 列は、担当者（agent）とエージェンシー（agency）という粒度の違う2つをまとめた表記。担当者まで決まるファクトは agent_key、エージェンシー止まりのファクトは縮約ディメンション dim_agency の agency_key を持つ（両方持つファクトもある）。マトリクスの列はコンフォームドな意味の単位であって物理テーブル1本とは限らない。
  • date 列に単純な ✓ が無い。累積スナップショットの行は複数の日付ロールを持つ。ロールプレイングディメンション（submitted_date, published_date, replied_date…）は同一の dim_date を別名で参照する。1つの物理テーブルが1列に複数回現れるのは、コンフォームド性が保たれている証拠。
  • company 列は10プロセス全てに ✓ が付く。10行を貫く唯一のディメンションであり、上の「✓ が2つ以上ある列はコンフォームドでなければならない」を最も強く受けるのがここ。つまり dim_company の定義が全社の分析結果を左右する。「投稿当時の企業規模」と「現在の企業規模」を両方答えるため、ファクトはイベント時点の company_key（SCD2 版）を持ち、現在値は company_id で is_current 版に再結合する（属性の版をどう持つかは DM05『履歴を持つ：SCD とスナップショット』で扱う）。

4. 現代の再解釈

Joe Reis は概念（CDM）→ 論理（LDM）→ 物理の3層を明確に分ける。CDM はビジネスの名詞と動詞だけ（「会員」が「クチコミ」を「投稿する」）。LDM で属性・キー・カーディナリティが入る。

物理で初めて BigQuery のパーティションやクラスタが出てくる。

Reis（Ch.14 The Levels of Data Modeling）: “At this stage, your goal is to capture the big picture: what fundamental concepts you’re modeling and how they relate to each other.” 概念層を飛ばすと “semantic conflict—where IT and Business can’t agree on what a ‘Customer’ even means” が起きる。引用される Larry Burns の一文: “The data model itself is not as important as the conversations the data model promotes.”

この枠組みに Kimball の4ステップを置くと、粒度宣言は概念層と論理層の継ぎ目にあるとわかる。ステップ1（プロセス選定）は概念層、ステップ3–4（ディメンションとメジャー）は論理層。

ステップ2（粒度）だけが両方に足を掛けている。「1行 = 1選考ステージ遷移」はビジネス側が読んで是非を言える文（概念）でありながら、そのまま主キー制約に翻訳できる（論理）。

CareerVoice で、この語義の食い違い（semantic conflict）が起きる場所は具体的に予測できる。

概念層で先に合意すべき語合意しないまま論理層へ行くと
「会員」— 退会者（members.deleted_at あり）を含むかdim_member の行数と fct_scout の会員数が一致せず、返信率の分母が部署ごとに違う
「クチコミ」— status が published のものだけか、submitted を含むか「クチコミ数の推移」が公開ベースか投稿ベースか不明になり、審査リードタイムの改善が投稿数の増加に見える
「スカウト」— company 送信と agent 送信を同じものと数えるかdim_scout_sender（異種ディメンション）を作る動機が共有されず、2本の外部キーで済ませる案と決着しない（送信主体が企業とエージェントに分かれるディメンションの持ち方は DM06『多対多・不揃い階層・異種ディメンション』で扱う）
「入社」— selection_events.stage = 'hired' か placements の行か直接応募の入社が成果報酬売上から漏れ、fct_placement と fct_application_pipeline の入社数が恒常的にずれる

何が残り、何が変わったか

1997年の Kimball列指向 DWH / dbt 時代
残る: 粒度宣言設計崩壊を防ぐ契約変わらない。むしろ description とテストとしてコードに埋め込めるようになった分、強制力が上がった
残る: 原子粒度で持つ次元数が最大になるから変わらない。加えてストレージが安く原子データを捨てる理由が消えた
変わる: 集約を作る動機クエリ性能のため必須に近い性能のための集約は多くの場合不要。agg_* を作るのは意味の共有（指標の定義を1か所に固定して全社で同じ数字を見る）のためで、性能はその副産物
変わる: 「マート」の物理的独立部門ごとに別 DB/サーバに置かれた同一プロジェクト内のデータセット。それでも DT#3 の教訓（部門で切らない）は名前空間の切り方として残る

5. BigQuery + dbt での実装

規約: 粒度宣言は description の第1文

全ての fct_* / agg_* モデルの description は「1行 = …」で始める。第2文で粒度キー（何が一意か）、第3文でこの表に入れないものを書く。3文目が重要で、境界を明示しないと後から粒度違反のメジャーが足される。

version: 2

models:
  - name: fct_selection_event
    description: |
      1行 = 1応募の1選考ステージ遷移（`selection_events` の1イベント）。
      粒度キー: `event_id`。`audit_key` は行の由来（バッチ・品質フラグ）を指す
      外部キーであって粒度キーではない。全ファクト共通、DT#164、10回で扱う。
      エージェント関与は解像度の違う2本で持つ: `agency_key`（縮約ディメンション。
      求人がエージェント経由なら紹介経由でも決まる）と
      `agent_key`（スカウト経由でのみ担当者まで決まる）。
      入れないもの: 応募そのもの（`applications.applied_at`）、
      応募単位の所要日数（`fct_application_pipeline` に置く）。
    data_tests:
      # 粒度宣言をテストとして固定する。この2本が緑である限り
      # 「1行 = 1遷移」は破れていない。
      - dbt_utils.unique_combination_of_columns:
          arguments:
            combination_of_columns:
              - event_id
      # 結合で行が増えて（一対多）も減って（INNER JOIN）もいないか
      - dbt_utils.equal_rowcount:
          arguments:
            compare_model: ref('stg_careervoice__selection_events')
    columns:
      - name: agency_key
        description: >
          エージェンシー。-1 = エージェンシーを特定できない
          （直接応募、企業スカウト、および直接掲載求人へのエージェント紹介）。
        data_tests:
          - not_null   # COALESCE(..., -1) が効いているか（DT#43、NULL 外部キー禁止）
      - name: agent_key
        description: "担当者。-1 = 担当者を特定できない（紹介経由を含む）。"
        data_tests:
          - not_null
      - name: event_count
        description: "常に 1。粒度に忠実な唯一のメジャー。"
        data_tests:
          - accepted_values:
              arguments:
                values: [1]
                # INT64 列には quote: false が要る。既定の quote: true だと
                # `not in ('1')` が生成され BigQuery が型エラーで落ちる
                quote: false

  - name: fct_review
    description: |
      1行 = 投稿された1クチコミ（`status` を問わない）。
      粒度キー: `review_id`。
      入れないもの: 審査の状態遷移（`fct_review_moderation`）、`member_key`（匿名性方針）。
    data_tests:

          arguments:

    description: |
      1行 = 1求人 × 掲載中の1日。

      入れないもの: 掲載終了後の日（行を作らない）、期間累計の応募数以外の派生指標。
    data_tests:

          arguments:
            combination_of_columns:
              - snapshot_date_key
              - job_posting_id

3点補足する。

  • fct_review は単一列なので unique テストでも同じ結果になるが、全ファクトで unique_combination_of_columns に揃える。粒度キーが1列か複数列かは設計変更で変わるので、テストの種類まで変えたくない。schema.yml を grep すれば全ファクトの粒度キーが一覧できる状態を保つ。
  • 引数の arguments: 入れ子は dbt 1.10.5 以降の書き方。それ以前は combination_of_columns をテスト名直下に置く。
  • description は文書であってテストではない。書き忘れを機械で防ぐなら CI に dbt ls --resource-type model --output json --output-keys name description を挟み、fct_ で始まるモデルの description が「1行 = 」で始まらなければ落とす。

fct_selection_event: 原子ファクトの SELECT

この SQL で粒度を決めているのは FROM {{ ref('stg_careervoice__selection_events') }} の1行だけ。以降の JOIN は全て多対一の LEFT JOINで、行数を増やしも減らしもしない。一対多が1つ紛れ込めば行が増え、粒度が静かに崩れる。

減る方も同じくらい危険で、こちらは見落としやすい。参照先が見つからない行を INNER JOIN で除外すると、粒度は宣言どおりのまま母数だけが静かに欠ける（応募の論理削除、Datastream の遅延で求人が未着、など）。

DT#43 の -1 は、参照先が無い行を除外せずに残すための仕組みなので、INNER JOIN と COALESCE(..., -1) を同じ SQL に同居させてはならない。両方向を検出するのが上の equal_rowcount。

時点結合（イベント時点の版に結ぶ結合。as-of join）の比較は DATE ではなく TIMESTAMP で行う。valid_from / valid_to も occurred_at も UTC の TIMESTAMP で統一し、JST は表示（と日付キーの算出）にだけ使う。DATE に変換して比較すると時刻が切り捨てられ、属性が変わった当日のイベントが変更前の版に結ばれる（時点結合の手順は DM05『履歴を持つ：SCD とスナップショット』で扱う）。

-- models/marts/fct_selection_event.sql
{{ config(
    materialized = 'table',
    partition_by = {'field': 'event_date', 'data_type': 'date', 'granularity': 'day'},
    cluster_by = ['company_key', 'stage']
) }}

WITH events AS (

    -- ★ 粒度はここで確定する: selection_events の 1 行 = 出力の 1 行
    SELECT
        event_id,
        application_id,
        stage,
        occurred_at,
        DATE(occurred_at, 'Asia/Tokyo') AS event_date
    FROM {{ ref('stg_careervoice__selection_events') }}

),

applications AS (

    SELECT
        application_id,
        member_id,
        job_posting_id,
        scout_id,
        source_channel
    FROM {{ ref('stg_careervoice__applications') }}

),

postings AS (

    SELECT
        job_posting_id,
        company_id,
        agency_id,          -- エージェント経由求人。agency_key の解決に使う
        job_category_code
    FROM {{ ref('stg_careervoice__job_postings') }}

),

scouts AS (

    SELECT
        scout_id,
        sender_agent_id
    FROM {{ ref('stg_careervoice__scouts') }}

)

SELECT
    -- 退化ディメンション（ディメンション表を作らずファクトに残す自然キー）
    e.event_id,
    e.application_id,
    e.stage,

    -- 日付キー: YYYYMMDD の INT64（DT#5）
    CAST(FORMAT_DATE('%Y%m%d', e.event_date) AS INT64) AS event_date_key,

    -- 外部キー。未知は NULL ではなく -1（DT#43）
    COALESCE(dm.member_key, -1) AS member_key,
    COALESCE(dc.company_key, -1) AS company_key,
    COALESCE(dj.job_posting_key, '-1') AS job_posting_key,
    COALESCE(dcat.job_category_key, '-1') AS job_category_key,
    COALESCE(dch.channel_key, '-1') AS channel_key,

    -- エージェンシー。-1 = エージェンシーを特定できない
    --   （直接応募、企業スカウト、および直接掲載求人へのエージェント紹介）
    -- 求人がエージェント経由（job_postings.agency_id）か、スカウト送信者の所属で決まる
    COALESCE(dag.agency_key, -1) AS agency_key,

    -- 担当者。-1 = 担当者を特定できない（直接応募・企業スカウト・紹介経由）
    -- スカウト経由（scouts.sender_agent_id）でのみ個人まで一意に決まる
    COALESCE(da.agent_key, -1) AS agent_key,

    -- 監査ディメンション（DT#164）。全ファクト共通。
    -- {{ audit_key() }} は10回で定義するマクロ。それまでは -1（dim_audit の未知行）を
    -- 置いても粒度の議論は変わらない
    {{ audit_key() }} AS audit_key,

    -- 粒度に忠実な唯一のメジャー
    1 AS event_count,

    e.event_date

-- 以下は全て多対一の LEFT JOIN。行を増やさず、減らしもしない
FROM events AS e
LEFT JOIN applications AS a
    ON e.application_id = a.application_id
LEFT JOIN postings AS p
    ON a.job_posting_id = p.job_posting_id
LEFT JOIN scouts AS s
    ON a.scout_id = s.scout_id

-- SCD2 は「イベント時点」で引く。比較は DATE ではなく TIMESTAMP 同士
-- （valid_from / valid_to / occurred_at はいずれも UTC。as-of join の作法は 05回）
LEFT JOIN {{ ref('dim_member') }} AS dm
    ON a.member_id = dm.member_id
   AND e.occurred_at >= dm.valid_from
   AND e.occurred_at < dm.valid_to
LEFT JOIN {{ ref('dim_company') }} AS dc
    ON p.company_id = dc.company_id
   AND e.occurred_at >= dc.valid_from
   AND e.occurred_at < dc.valid_to
LEFT JOIN {{ ref('dim_agent') }} AS da
    ON s.sender_agent_id = da.agent_id
   AND e.occurred_at >= da.valid_from
   AND e.occurred_at < da.valid_to
-- 縮約ディメンション。求人側の agency を優先し、無ければスカウト送信者の所属を使う
LEFT JOIN {{ ref('dim_agency') }} AS dag
    ON COALESCE(p.agency_id, da.agency_id) = dag.agency_id
   AND e.occurred_at >= dag.valid_from
   AND e.occurred_at < dag.valid_to
LEFT JOIN {{ ref('dim_job_posting') }} AS dj
    ON p.job_posting_id = dj.job_posting_id
LEFT JOIN {{ ref('dim_job_category') }} AS dcat
    ON p.job_category_code = dcat.job_category_code
LEFT JOIN {{ ref('dim_channel') }} AS dch
    ON a.source_channel = dch.source_channel

粒度の違う2本の外部キーを並べる。agent_key（担当者）はスカウト経由でしか決まらない。source_channel = 'agent_referral' のような紹介経由は scouts に行が無いからだ。

一方 agency_key は job_postings.agency_id（またはスカウト送信者の所属）から決まるので、求人がエージェント経由なら紹介経由でも失われない。逆に、直接掲載求人へのエージェント紹介はどちらの手がかりも無く -1 になる——粒度を1段粗くしても、関与の有無そのものを常に復元できるわけではない。

dim_agency は dim_agent の縮約（shrunken/rollup）ディメンション（DWT ch.4）。agency_name / agency_tier を dim_agent と同一の名前・同一の値で共有する（dim_agency 固有の contract_start_date は、エージェンシー粒度でしか意味を持たない属性）。

共有部分がコンフォームドである限り、横断集計（ドリルアクロス。別々のファクトを共通のディメンションで並べる集計）は成立する。だから「担当者別」と「エージェンシー別」を同じ agency_tier で並べられる。

ここで dim_agent を agency_id で結んで済ませたくなるが、1エージェンシーに複数担当者がいるので一対多になり粒度が崩れる。粒度が足りないときは、粗い側のディメンションを別の外部キーとして足すのが正解で、細かい側のディメンションを粗いキーで結ぶのは誤り。前者は行数を変えず、後者は変える。

P001 をこのモデルに通すと 6 行（document / first_interview / final_interview / offer / accepted / hired）。応募そのもの（06-23）は行にならない。

応募を数えたいなら fct_application_pipeline の1行を数える。「応募数」と「選考イベント数」は別の表で数える——粒度を分けるとは、この状態を作ることを指す。

入れたくなるが入れてはいけないメジャーの例を挙げておく。いずれも Grain の “aren’t true to the grain… Omit them from the design.”（粒度に合っていない。設計から外す）に該当する。

7. 演習

問1: fct_page_view の粒度

fct_page_view の粒度を「1行 = 1セッション」にすべきか「1行 = 1ページ表示」にすべきか。答えたい問いから判断せよ。セッション粒度なら行数は 1/10 以下になる——性能を理由にこちらを選ぶべきか。

解答例

1行 = 1ページ表示。§3 のバスマトリクスで宣言したとおりで、§6 の判断基準の第1行を適用する。

判断は性能ではなく問いで決まる。「クチコミ数・評価スコアの推移が応募率に影響するか」に答えるには、どのクチコミ（review_id）が読まれたかを数える必要がある。セッション粒度では1セッションに複数の review_id / page_type / company_id が含まれるため、これらが多値になり、dim_page_context（page_type × device × referrer_type × is_unlocked = 72行のジャンクディメンション）を1つの外部キーで結べない。

逆向きは無コストで成立する。session_id を退化ディメンションとして持てば、セッション指標はいつでも導出できる。

SELECT
    view_date_key,
    company_key,
    SUM(view_count)                 AS page_views,
    COUNT(DISTINCT session_id)      AS sessions,
    COUNT(DISTINCT review_id)       AS reviews_viewed,
    SAFE_DIVIDE(SUM(view_count), COUNT(DISTINCT session_id)) AS views_per_session
FROM {{ ref('fct_page_view') }}
GROUP BY view_date_key, company_key

DT#77 の非対称性そのもの: ページ表示からセッションはまとめられるが、セッションからページ表示は展開できない。スキャン量が問題になったら、粒度を上げるのではなく agg_* をもう1本作る（原子ファクトは残す）。fct_page_view は view_date パーティション + company_key クラスタで、企業単位の分析なら実スキャンは行数ほど増えない。

問2: fct_contract_monthly の粒度宣言と行数

contracts から fct_contract_monthly を作るときの粒度宣言を一文で書け。そのうえで、K001（C001 の premium、枠 200/月、300,000円、2026-01-01〜、end_date なし）は 2026-01 〜 2026-09 で何行になるか答えよ。

解答例

粒度宣言: 「1行 = 1契約 × その契約が有効だった1暦月」。粒度キーは month_date_key（月初）+ contract_id。

行数: 9行（month_date_key = 20260101, 20260201, …, 20260901）。end_date が NULL なので契約は継続中で、対象9か月すべてに行が立つ。

ただし 2026-09 は進行中の月なので scouts_sent / scouts_remaining は締まっておらず、日々更新される。定期スナップショットの最新月は未確定行であることを利用側に明示する必要がある（is_active とは別の問題）。

宣言を誤ったときに何が起きるか。

誤った宣言起きること
1行 = 1企業 × 1月C001 がプラン変更や別部門で複数契約を持った月に行が合体し、scout_quota と monthly_fee がどの契約のものか判別不能になる
1行 = 1契約月次の枠残高（scouts_remaining）を持つ場所が無い。MRR の推移も出せない
1行 = 1契約 × 1日ソース（contracts）が月周期でしか変化しないので情報が増えず、行数だけ30倍になる。粒度はソースの変化周期に合わせる

加法性の注意: scouts_remaining は半加法。企業をまたいでは足せるが、月をまたいで足すと意味が無い（1月と2月の残枠を合計しても何も表さない）。monthly_fee は月をまたいで足せる（＝期間売上）。

同じ表の中でメジャーごとに加法性が違うので、description の列コメントに書く（メジャーごとの加法性は DM04『加法性と派生指標』で扱う）。

問3: バスマトリクスに1プロセス追加する

「クチコミへの『参考になった』投票」を新しいビジネスプロセスとしてバスマトリクスに1行足せ。粒度宣言・型・各ディメンション列の ✓ / ✗ を決め、判断の根拠を書け。

解答例

まず4ステップの①。バスマトリクスに行を足すとは、ソースを1つ増やすと宣言すること。この題材のソースに投票を記録するテーブルは無いので、review_votes（vote_id, review_id, member_id, voted_at）相当が新たに要る（§3 のマトリクスに入れていないのはこのためで、題材への追加提案として扱う）。

以下はそのソースが在る前提での解答。

粒度宣言: 「1行 = 1会員による1クチコミへの1『参考になった』投票」。型はトランザクション（ファクトレス）。メジャーは vote_count = 1 のみ、退化ディメンションに review_id。

プロセスファクト型粒度宣言datemembercompanyjob_postingagentjob_categorychannel/junk
クチコミ投票fct_review_vote（題材への追加提案）トランザクション（ファクトレス）1行 = 1会員による1クチコミへの1投票投票日✓✓✗✗✓dim_page_context

各列の根拠。

  • date ✓ — 投票日。dim_date のロールプレイング。
  • member ✓ — fct_review が member_key を持たないのは投稿者の匿名性のため。投票者は投稿者ではないので、この制約は継承しない。ただし「同一クチコミへの投票者が1名しかいない企業」では投稿者と投票者の相関から推定される余地があるので、集計の最小件数ルールは別途要る。
  • company ✓ — クチコミの対象企業。review_id 経由でも辿れるが、fct_review とコンフォームドな company_key で横断集計（ドリルアクロス）するため直接持つ。「クチコミ数」と「投票数」を企業 × 日で並べる問いは確実に来る。
  • job_posting ✗ / agent ✗ — 投票は求人にもエージェントにも関係しない。空セルは「関係ない」種別。
  • job_category ✓ — クチコミの job_category_code。fct_review と同じ dim_job_category を使えば「職種別の投票率（投票数 ÷ 公開クチコミ数）」が横断集計（ドリルアクロス）で出る。ここが ✗ だとその問いに答えられない。
  • channel/junk — 既存の dim_page_context を再利用する。投票は company_review ページから device / referrer_type / is_unlocked の文脈で起きるので、72行のジャンクディメンションがそのまま当たる。新しいジャンクを作らずに済むなら作らない（コンフォームド化の機会）。

最大の注意点: 「参考になった数」を fct_review の列（helpful_count）として足したくなる。これは粒度違反で二重に危険。

(1) fct_review の粒度は「1投稿」であり投票累計はその粒度に忠実でない（Grain: “Omit them from the design.”）。(2) 投票は投稿の何か月も後に増えるため、fct_review が不変トランザクションでなくなり、パーティション単位で作り直す増分ロードが成立しなくなる（増分ロードの作法は DM09『増分・遅延到着・冪等性』で扱う）。累計が要るなら agg_company_rating_daily 側か、企業単位の agg_company_entity に置く（集約テーブルは DM04『加法性と派生指標』と DM08『コンフォームドとドリルアクロス』で扱う）。

8. 参考: 手元の基盤ではどうか

  • dbt_logs_analysis の mart_url_performance は「1行 = url_path × date」で作られているが、schema.yml に粒度テストが無い。v1 / v2 / incremental の3本が同じ粒度を主張しているのに、それを検証しているものが1つも無い状態。この資料の基準なら dbt_utils.unique_combination_of_columns: [url_path, date] が3本すべての最低条件。増分モデルは unique_key=['url_path','date'] を持っているので、粒度は宣言済みだが「テストされている」のは増分モデルだけ——full-refresh 版は無防備。
  • 同じ mart_url_performance は生ログ（1行 = 1リクエスト）を日次にまとめた集約で、原子ファクトが marts に残っていない。DT#77 の形そのもの。「特定の遅いリクエストの中身を見たい」に staging のビュー経由でしか答えられないのは、原子ファクトが marts の一級市民になっていないから。
  • news_pipeline は粒度の分離ができている側の例。summaries は「1行 = 1記事の最新スコア」（/recalculate が同じ行を上書き＝Type 1）、raw_articles は「1行 = 1収集イベント」に近く同一 article_id が複数行になりうる。この2つを1表にしなかったのは正しい。get_unnotified_summaries が両側を article_id ごとに1行へ絞っているのは、粒度の不一致を後段のクエリで吸収している証拠で、その吸収を忘れた版では通知が増幅していた。
  • 種: summaries に「1行 = 1 article_id」のアサーション（dbt を使わないなら BigQuery の ASSERT か、insert 前の COUNT(*) vs COUNT(DISTINCT article_id) 比較）を1本置くと、再採点バッチの二重挿入をデプロイ前に検出できる。fct_review に unique_combination_of_columns を置くのと同じ発想。
