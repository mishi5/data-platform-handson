1. この資料で決めること

ここまでの 9 本のドキュメントで決めたのは「何を作るか」だった。この資料で決めるのは「作ったものをどこに置き、どう名付け、何を保証し、どう変えるか」という運用規約である。中心の判断は 1 つで、テストは粒度・参照整合性・加法性の 3 種を層ごとに置き分ける。

2. よくある失敗

(a) モデル名にバージョンを埋め、両方が本番から参照される

fct_scout の member_key を「現在版」で解決していた誤りを直すとき、既存の数字を守るために fct_scout_v2 という別モデルを作ったとする。obt_scout_funnel は旧 fct_scout のまま、Looker Studio のスカウトファネルだけ fct_scout_v2 に差し替わる。半年後、同じ 2026-06 のスカウト件数が 2 箇所で違う値を返し、どちらが正しいかを判定する手段が無い。

問題があるのは SQL ではなく手順である。旧版に終了日が設定されておらず、誰がまだ旧版を参照しているかを機械が把握できず、「移行が終わった」と宣言する条件も定義されていない。versions: はこの 3 つを YAML に書かせる仕組みで、後述の §5(c) で扱う。

(b) staging に集約が入り、marts に型変換が入る

# models/staging/careervoice/stg_careervoice__scouts.sql（悪い例）
SELECT
    member_id,
    COUNT(*) AS scout_count,
    MIN(sent_at) AS first_sent_at
FROM {{ source('careervoice', 'scouts') }}
GROUP BY member_id

この時点で fct_scout の粒度（1 行 = 送信された 1 スカウト）はもう作れない。scout_id も template_id も消えており、原子粒度に戻すにはソースへ再アクセスするしかない（DT#77）。staging は「下流が何をしたいかを知らない」層なので、粒度を粗くする操作を置いてはいけない。

逆向きの事故も同じ根から出る。sent_at のキャストを staging に置かず各 mart で書くと、fct_scout は SAFE_CAST、fct_scout_funnel は CAST になり、不正値を含む日の行数が 2 つのファクトでずれる。同じ変換が 2 箇所にあれば、いつかは片方だけ直される。

(c) not_null だけでは粒度が守られない

stg_careervoice__reviews を作るとき、審査結果を一緒に持たせようとして review_moderation_events を結合したとする。R001 は submitted → screening → submitted（03-11 の差し戻し low_quality）→ published で審査イベントが 3 行あるので、クチコミが 3 行に増える。列は全て埋まっているので、既存の not_null テストは全て通る。

-- fct_review に R001 が 3 行入った状態で、C002 のクチコミを数える
SELECT
    c.name,
    SUM(f.review_count)                     AS review_count,      -- 3（正しくは 1）
    SAFE_DIVIDE(SUM(f.overall_score), SUM(f.review_count)) AS avg_overall_score  -- 3.5（分子も分母も 3 倍になるので変わらない）
FROM {{ ref('fct_review') }} AS f
JOIN {{ ref('dim_company') }} AS c
    ON f.company_key = c.company_key
WHERE f.submitted_date >= DATE '2026-03-01'
  AND c.company_id = 'C002'
GROUP BY c.name

件数だけが 3 倍になり、平均は同じ値を返す。平均が正しく見えるので気づかないのがこの失敗形の質の悪さで、企業別の投稿数ランキングと評価スコアが静かに矛盾する。粒度宣言をテストに翻訳していれば、fct_review のビルド直後にテストが失敗する。

(d) dim_audit が無く、どの実行が誤った行を入れたか追えない

2026-06-21 の実行で時点結合の条件を間違え、その日に読み込んだ fct_scout の member_key が全て -1 になったとする。audit_key が無いと、消すべき行を特定する手掛かりは sent_date しか無い。ところが増分実行はルックバック 3 日で過去日も書き直すので（DM09『増分・遅延到着・冪等性』）、sent_date で消すと正常に入り直した行まで巻き添えになる。

-- audit_key があれば、壊れた実行の行だけを名指しできる
SELECT
    a.dbt_invocation_id,
    a.batch_id,
    a.loaded_at,
    COUNT(*)                              AS rows_loaded,
    COUNTIF(f.member_key = -1)            AS unresolved_member_rows
FROM {{ ref('fct_scout') }} AS f
JOIN {{ ref('dim_audit') }} AS a
    ON f.audit_key = a.audit_key
WHERE f.sent_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY 1, 2, 3
ORDER BY a.loaded_at DESC

3. Kimball の原則

ETL 34 サブシステムのうち、マート設計に直接関わるもの

DWT ch.19 と Subsystems of ETL Revisited（2007）は ETL を 34 のサブシステムに分解する。抽出（3）・クレンジングとコンフォーム（5）・デリバリ（13）・管理（13）の 4 群のうち、マートの設計そのものを規定するのは次の 7 つである。

設計はいつ終わるか（DT#108）

Bob Becker は、モデルが書けたと思った時点ではまだ終わっておらず、最後の主要な設計活動はディメンショナルモデルのレビューと検証だと位置づける。そのうえで最低 3 種類の聴衆を挙げる。技術レベルとビジネス理解の度合いが違う相手に順に見せることで、別々の欠陥が出てくるという構成になっている。

進め方も指定がある。まずバスマトリクスをレビューし、スコープ・コンフォームドディメンションの役割・プロセスの優先順位を共有してから、選んだ行がどうモデルに翻訳されるかを示す。広い利用者向けのセッションでは時間の約 3 分の 1 を「このモデルで実際の問いにどう答えるか」の実演に充て、要件定義から拾った質問を順にたどって見せる。

DT#108 は最後をこう締める。ここまで来ればモデルの修正は軽微で、ユーザーは大した感動を示さない。モデルが当たり前に見えて筋が通っているなら、それは自分たちの業務の反射だからで、仕事がうまくいった印である。

品質スクリーンとエラー事象（An Architecture for Data Quality）

Kimball の品質アーキテクチャの中心は品質スクリーンで、ETL パイプラインの中に置く診断フィルタと定義される。テストに成功したら何も起きず副作用も無い。失敗したときだけ 2 つの責務が発生する。

  1. エラー事象スキーマに 1 レコード書き出す（error event fact の粒度は 1 スクリーンイベント、error event detail の粒度は 1 エラーに関わった 1 フィールド）。
  2. プロセスを止める／該当レコードを保留（suspension）へ送る／タグを付けてそのまま通す、のいずれかを選ぶ。
スクリーンの種類原典の定義dbt での対応CareerVoice の例
列スクリーン単一列の中を検査する。NULL でない、有限の値集合に属する、範囲内、書式に合うnot_null / accepted_values / dbt_utils.accepted_rangereviews.status が 4 値のいずれか、score_* が 1.0〜5.0
構造スクリーン列をまたぐ関係を検査する。複合キーが主キーになっている、FK と PK の対応、階層の整合unique_combination_of_columns / relationshipsfct_scout の scout_id が一意、member_key が dim_member に解決する
業務ルールスクリーン上の 2 つに収まらない複雑な規則。集約した閾値による検査（件数が想定外に多い等）も含むdbt_utils.expression_is_true / singular testscouts_remaining = scout_quota - scouts_sent、日次スカウト件数が前 7 日中央値の 3 倍以内

3 択のうち原典が推すのはタグを付けて通すである。停止は手動介入を要求し、保留ファイルは「いつ直って戻るのか」が不明なまま行が欠けるので、その間データベース全体の整合性が疑わしくなる。欠損・破損した数値は least biased estimator（もっともらしい推定値）で埋め、その事実を監査ディメンションに記述するほうが、NULL や 0 で置くより合計が実態に近い。

監査ディメンション（Data Quality / DT#164）

監査ディメンションはファクト行が作られた時点のメタデータを、普通のディメンションとして持つ。原典の狙いは「メタデータを通常のデータに格上げし、BI ツールの画面の第一階層に出す」ことで、レポートの行ヘッダに out-of-bounds 指標を 1 つ足すだけで、同じレポートがそのまま品質評価付きレポートになる。粒度は 1 行 = 1 つの異なる監査条件で、完璧に流れた実行なら 1 行しか生まれず、その日に読み込んだ全ファクト行が同じ 1 行を指す。

DT#164 の分類原典の列CareerVoice の dim_audit
環境変数ETL マスタ版番号、通貨換算版、配賦ロジック版batch_id, source_system, dbt_invocation_id, loaded_at
品質指標欠損フラグ、推定値で埋めたフラグ、ありえない値のフラグquality_flag（ok / estimated / suspect）

DT#164 の指示は「単純に始めよ、最初から理想主義になるな、優雅さで賞を狙うな」である。この資料の dim_audit が 5 列しか持たないのはこの指示に従っている。Data Quality 白書の完全版（completeness / validation / out-of-bounds / screens failed / record modified / 3 つの時刻）は、エラー事象スキーマを別に運用して初めて埋まる列なので、先に置いても NULL が並ぶだけになる。

4. 現代の再解釈

dbt structure が言う層の役割

dbt の How we structure our dbt projects は、staging を「常に必要で、下流の重複を消す変換だけを置く層」と定義する。許すのは改名・型変換・単純な計算（セントからドル等）・条件による区分化の 4 つで、結合と集約は明示的に禁止される。理由も書かれていて、結合は計算の重複と分かりにくい関係を生み、集約はソースの粒度を失わせて下流の柔軟性を奪うからである。

intermediate 層のガイドは「DAG を狭め、テーブルを広くする」と表現される。入力は複数でよいが出力は 1 つにし、marts へ向かって矢尻の形になる DAG を作る。マテリアライズは ephemeral が既定で、可視性が要るなら本番外の専用スキーマに view を置き、権限を絞る（§7(c) の int_review_member_link はこの但し書きに当てはまる）。

ただし marts の命名では、dbt の 2 つの公式文書が食い違う。structure ガイドは業務エンティティの平易な名前（orders, customers）で名付けよと書き、fct_ / dim_ の接頭辞に触れない。一方 dbt Developer Blog の Building a Kimball dimensional model with dbt は dim_product / fct_sales をそのまま使う。

このシリーズは後者を採る（前掲の命名規約）。ファクトとディメンションの区別は物理設計ではなく「加法性を持つか、文脈を与えるか」という意味の区別なので、名前で見えているほうが 11 本のドキュメントを跨ぐときに安い。

dbt Kimball 記事のテストと、そこに足りないもの

Neo の記事は AdventureWorks の受注を題材に、ビジネスプロセスの特定 → ファクトとディメンションの特定 → ディメンションの作成 → ファクトの作成 → 関係の文書化、という順で実装を追う。ディメンションには product_key の not_null ＋ unique、自然キーにも not_null ＋ unique、ファクトには sales_key の not_null ＋ unique と各 FK の not_null を置く。ここまではこのシリーズと同じ結論になる。

足りないのは 3 つで、参照整合性（relationships）・加法性・契約が無い。記事のファクトはサロゲートキーを都度ハッシュで作り直しているので、ディメンション側に無いキーが入っても誰も気づかない。この資料で relationships を marts の必須テストに入れるのはそのためである。

契約と改版

model contracts は「このモデルが返す列の名前・型・制約」を YAML に固定し、ビルド前に照合する。BigQuery では not_null だけが実際に強制され、primary_key / foreign_key は宣言できるがメタデータ扱いで強制されない（unique / check は宣言もできない）。契約が守るのは形だけで、列名も型も変えずに値の意味を変える種類の事故は検知しない。

破壊的変更（列の削除・改名、型の変更、既存制約の削除・変更）を検知したとき、dbt は版付きモデルではエラー、版無しモデルでは警告を出す。versions: は「新版を作る → latest_version を上げる → 旧版に deprecation_date を立てる → 下流の参照を移す → 旧版を消す」という手順を YAML に固定する仕組みで、docs 側では旧版を参照している下流に通知が出る。deprecation_date は dbt Core 1.6 で入った。

5. BigQuery + dbt での実装

(a) fct_scout の契約とテスト

契約は列の型を書かざるを得ないので、DM03『ディメンションの設計』で決めた型の割当に従う（SCD2 のキーは FARM_FINGERPRINT 由来の INT64、Type0/1 のキーは自然キーの型そのまま、date_key は INT64）。スタースキーマ側の fct_scout には require_partition_filter を付けない（正本は全期間の再集計・バックフィル・整合テストの対象になるため。DM07）。付けるのは配布物 obt_* と dim_member_daily の側で、そこでは事情が変わる — require_partition_filter = true のテーブルは、テストの生成 SQL がパーティションフィルタ無しで読むため全て失敗する。config: where: でフィルタを注入するのが回避策で、これはテスト対象のリレーションを (SELECT * FROM ... WHERE ...) dbt_subquery に差し替える機能である。下の fct_scout の例では窓はスキャン量を抑える運用上の選択にすぎないが、形はフィルタ必須テーブルで必要になるものと同じなので、この形で示す。

# models/marts/schema.yml
version: 2

models:
  - name: fct_scout
    description: |
      1 行 = 送信された 1 スカウト（01回の粒度宣言をそのまま転記）。
      sender_type は dim_scout_sender 側に持つ（06回の異種ディメンション）。
    config:
      materialized: incremental
      incremental_strategy: insert_overwrite
      partition_by:
        field: sent_date
        data_type: date
        granularity: day
      cluster_by: [scout_sender_key, member_key]
      # require_partition_filter は付けない（star = 正本。07回）
      contract:
        enforced: true

    columns:
      - name: scout_id
        description: 退化ディメンション（scouts.scout_id）
        data_type: string
        constraints:
          - type: not_null
      - name: template_id
        description: 退化ディメンション
        data_type: string
      - name: sent_date_key
        data_type: int64
        constraints:
          - type: not_null
      - name: sent_date
        description: パーティション列（sent_date_key と同じ日）
        data_type: date
        constraints:
          - type: not_null
      - name: member_key
        description: 送信時点の dim_member 版。解決できない場合は -1
        data_type: int64
        constraints:
          - type: not_null
      - name: member_profile_mini_key
        data_type: int64
        constraints:
          - type: not_null
      - name: scout_sender_key
        data_type: int64
        constraints:
          - type: not_null
      - name: job_posting_key
        description: scouts.job_posting_id が NULL のときは '-1'
        data_type: string
        constraints:
          - type: not_null
      - name: audit_key
        data_type: int64
        constraints:
          - type: not_null
      - name: scout_count
        description: 常に 1。加法
        data_type: int64
        constraints:
          - type: not_null

    data_tests:
      # 粒度: 01回の宣言「1 行 = 送信された 1 スカウト」の機械翻訳
      - dbt_utils.unique_combination_of_columns:
          arguments:
            combination_of_columns:
              - scout_id
          config:
            where: "sent_date >= date_sub(current_date(), interval 90 day)"

      # 加法性: scout_count は 1 以外を取らない
      - dbt_utils.expression_is_true:
          arguments:
            expression: "scout_count = 1"
          config:
            where: "sent_date >= date_sub(current_date(), interval 90 day)"

      # 既定行に落ちた行の監視（落とさず警告に留める）
      - dbt_utils.expression_is_true:
          arguments:
            expression: "member_key != -1"
          config:
            where: "sent_date >= date_sub(current_date(), interval 90 day)"
            severity: warn

relationships は列側に置く。where はテスト対象（子＝ファクト）だけを絞り、to: のディメンションには適用されないので、dim_member 側にパーティションフィルタは要らない。

# 上の columns: の該当エントリに data_tests: を足す（再掲は差分のみ）
      - name: member_key
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_member')
                field: member_key
              config:
                where: "sent_date >= date_sub(current_date(), interval 90 day)
                        and member_key != -1"

      - name: sent_date_key
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_date')
                field: date_key
              config:
                where: "sent_date >= date_sub(current_date(), interval 90 day)"

# dim_scout_sender 側（sender_type の列スクリーン）
  - name: dim_scout_sender
    columns:
      - name: sender_type
        data_tests:
          - accepted_values:
              arguments:
                values: ['company', 'agent']

# 加法性チェックの代表例は半加法メジャーの側にある
  - name: fct_contract_monthly
    data_tests:
      # 枠残高 = 枠 - 消化。月をまたいで足せないメジャーの内部整合
      - dbt_utils.expression_is_true:
          arguments:
            expression: "scouts_remaining = scout_quota - scouts_sent"
          config:
            where: "month_date >= date_sub(current_date(), interval 12 month)"

data_tests: の下で引数を arguments: に入れる書き方は dbt 1.10.5 以降で、それより前は引数をテスト名の直下に直接書く（config: の位置は同じ）。

member_key != -1 を外す判断には代償がある。このシリーズは dim_member に -1 の既定行（未知・未解決を表す 1 行）を置く方針なので（DM03）、外さなくてもテストは通る。外すと「実在するキーが解決できるか」だけを測る純度の高いテストになる代わりに、既定行そのものを消してしまった事故を検知できなくなるので、既定行の存在を別に確かめる singular test（SQL を 1 本書く形式のテスト）を対にする。

-- tests/assert_default_rows_exist.sql
-- -1 の既定行が消えていないこと（DT#43。消えると relationships の where が穴になる）
SELECT 'dim_member' AS dimension
FROM (SELECT 1)
WHERE NOT EXISTS (SELECT 1 FROM {{ ref('dim_member') }} WHERE member_key = -1)

UNION ALL

SELECT 'dim_date'
FROM (SELECT 1)
WHERE NOT EXISTS (SELECT 1 FROM {{ ref('dim_date') }} WHERE date_key = -1)

UNION ALL

SELECT 'dim_job_posting'
FROM (SELECT 1)
WHERE NOT EXISTS (SELECT 1 FROM {{ ref('dim_job_posting') }} WHERE job_posting_key = '-1')

where による窓（ここでは 90 日）は、require_partition_filter を張る配布物（obt_*）や dim_member_daily でテストを実行するために必要になる形である。fct_scout のようなスタースキーマ側の正本ではフィルタ強制が無いので窓は必須ではなく、スキャン量を抑えるための運用上の選択になる。どちらであれ全期間の粒度を保証したいなら、where を外した同じテストを別ジョブ（月次など）で実行する。+where は dbt_project.yml の data_tests: 配下にパス単位で既定値を書けるが（models: 配下に書いても反映されない）、ファクトごとにパーティション列名が違う（sent_date / applied_date / view_date）ので、この資料では各テストの config: に書く。

(b) audit_key() マクロと dim_audit

dim_audit は 1 実行 × 品質フラグごとに 1 行を作る増分モデルにする。invocation_id は dbt コマンド 1 回ごとに生成される UUID で、run_started_at は実行開始時刻の Python datetime（既定 UTC）である。両方ともコンパイル時に確定するので、同じ実行で作られた全ファクト行が同じ audit_key を指す。

DM03『ディメンションの設計』の §5(e) は呼び出し側の形（ディメンションとファクトが同じ実行を指すこと）だけを示している。マクロの正本はこの資料で、ここで初めて足すものが 2 つある。{%- do ref('dim_audit') -%} によるビルド順の依存と、incremental_strategy = 'merge' による実行ごとの積み増しである。引数は値で渡し（{{ audit_key('suspect') }}）、quality_flag は ok / estimated / suspect の 3 値に固定する（Data Quality 白書の「タグを付けて通す」に対応）。loaded_at には run_started_at を入れる（同一実行の全ファクト行が同じ時刻を指すため）。

-- models/marts/dim_audit.sql
{{ config(
    materialized = 'incremental',
    unique_key = 'audit_key',
    incremental_strategy = 'merge'
) }}

-- 監査ディメンション（DT#164）。1 行 = 1 dbt 実行 × 1 品質フラグ。
-- 完璧に流れた実行では ok の 1 行しか参照されない。
WITH quality_flags AS (
    SELECT flag
    FROM UNNEST(['ok', 'estimated', 'suspect']) AS flag
)

SELECT
    FARM_FINGERPRINT(CONCAT('{{ invocation_id }}', '|', flag)) AS audit_key,
    '{{ run_started_at.strftime("%Y%m%d%H%M%S") }}'            AS batch_id,
    'src_careervoice'                                          AS source_system,
    TIMESTAMP '{{ run_started_at.strftime("%Y-%m-%d %H:%M:%S") }}' AS loaded_at,
    '{{ invocation_id }}'                                      AS dbt_invocation_id,
    flag                                                       AS quality_flag
FROM quality_flags
-- macros/audit_key.sql
{% macro audit_key(quality_flag='ok') -%}
    {#- 値としては使わないが、dim_audit を必ず先にビルドさせるために依存を張る。
        これで `dbt build -s +fct_scout` に dim_audit が入る。 -#}
    {%- do ref('dim_audit') -%}
    farm_fingerprint(concat('{{ invocation_id }}', '|', '{{ quality_flag }}'))
{%- endmacro %}

ファクト側は列を 1 本足すだけで済む。品質フラグの引数は Data Quality 白書の「タグを付けて通す」に対応し、止めるほどではないが疑わしい行を分けて残すために使う。

-- models/marts/fct_scout_v2.sql（抜粋）
SELECT
    s.scout_id,
    s.template_id,
    CAST(FORMAT_DATE('%Y%m%d', DATE(s.sent_at, 'Asia/Tokyo')) AS INT64) AS sent_date_key,
    DATE(s.sent_at, 'Asia/Tokyo')                                       AS sent_date,
    IFNULL(m.member_key, -1)                                            AS member_key,
    IFNULL(m.member_profile_mini_key, -1)                               AS member_profile_mini_key,
    IFNULL(snd.scout_sender_key, -1)                                    AS scout_sender_key,
    IFNULL(s.job_posting_id, '-1')                                      AS job_posting_key,
    -- as-of join で会員の版を解決できなかった行は suspect として残す
    CASE
        WHEN m.member_key IS NULL THEN {{ audit_key('suspect') }}
        ELSE {{ audit_key() }}
    END                                                                 AS audit_key,
    1                                                                   AS scout_count
FROM scouts AS s
LEFT JOIN member_versions AS m
    ON  s.member_id = m.member_id
    AND s.sent_at >= m.valid_from
    AND s.sent_at <  m.valid_to
LEFT JOIN sender_versions AS snd
    ON  snd.sender_type = s.sender_type
    AND snd.sender_id = IFNULL(s.sender_company_id, s.sender_agent_id)
    AND s.sent_at >= snd.valid_from
    AND s.sent_at <  snd.valid_to

-s fct_scout のようにファクト単体を選んで実行すると、dim_audit はビルドされず新しい audit_key が宙に浮く。{% do ref('dim_audit') %} は依存グラフに辺を足すだけで、選択を広げはしないからである。audit_key の relationships テストを dim_audit に張っておくと、この運用ミスを dbt test で検知できる。

dim_audit 側は自己参照を避けるためマクロを呼ばず同じ式を直書きしている。式を変えるときは 2 箇所を同時に直す。この relationships テストはその取り違えも捕まえる。

(c) fct_scout を v2 にする

v1 は member_key を「現在版」で解決していて、member_profile_mini_key を持たなかった。v2 は送信時点の版で解決し、ミニディメンションのキーを足す。列の追加は破壊的変更ではないが、member_key の意味の変更は過去の全ての数字を静かに変えるので、契約が検知しなくても版を切る。

# models/marts/schema.yml
models:
  - name: fct_scout
    latest_version: 2
    config:
      contract:
        enforced: true
    columns:
      # ここは最新版（v2）の列定義。(a) の columns: をそのまま使う
      - name: scout_id
        data_type: string
      # ...（中略）...
      - name: member_profile_mini_key
        data_type: int64

    versions:
      - v: 1
        deprecation_date: 2026-12-31
        columns:
          - include: all
            exclude: [member_profile_mini_key]
      - v: 2

ファイル名の規約は <model_name>_v<v>.sql（最新版だけ接尾辞無しの fct_scout.sql でもよい）、生成されるリレーションは fct_scout_v1 と fct_scout_v2 になる。参照は常にモデル名で行い、版を固定したい下流だけが v= を付ける。

-- 移行が済むまで旧版に固定する下流
SELECT * FROM {{ ref('fct_scout', v=1) }}

-- 版を指定しなければ latest_version（= 2）に解決する
SELECT * FROM {{ ref('fct_scout') }}
# v1 だけ / v2 だけをビルドする
dbt build --select fct_scout.v1
dbt build --select fct_scout.v2

# 旧版を参照している下流を洗い出す
dbt list --select fct_scout.v1+

BI から project.marts.fct_scout という物理名で直接叩かれている場合は、版付きにするとテーブル名が fct_scout_v2 に変わって参照が切れる。旧名を残すなら該当版に config: alias: fct_scout を置くか、常に最新版を指すビューを自動生成する latest_version_pointer（dbt v1.12 以降）を使う。

(d) ソースの鮮度

下流の not_null は「昨日の分がまだ来ていない」を検知しない。行が無いだけならテストは全て通るからである。updated_at を持たないテーブル（page_views は viewed_at、selection_events は occurred_at）はテーブル側で loaded_at_field を上書きする。

# models/staging/careervoice/sources.yml
version: 2

sources:
  - name: careervoice
    schema: src_careervoice
    description: Datastream(CDC) による OLTP の複製
    config:
      loaded_at_field: updated_at
      freshness:
        warn_after: {count: 6, period: hour}
        error_after: {count: 24, period: hour}

    tables:
      - name: members
      - name: companies
      - name: scouts
      - name: applications

      - name: page_views          # updated_at を持たない
        config:
          loaded_at_field: viewed_at
          freshness:
            warn_after: {count: 1, period: hour}
            error_after: {count: 3, period: hour}
            # 全件スキャンを避ける（日次 2,000 万行）。filter は freshness の内側
            filter: viewed_at >= timestamp_sub(current_timestamp(), interval 2 day)

      - name: selection_events    # updated_at を持たない
        config:
          loaded_at_field: occurred_at

      - name: job_categories      # マスタ。鮮度を測らない
        config:
          freshness: null
dbt source freshness --select source:careervoice
dbt source freshness --select source:careervoice.page_views

filter は freshness: ブロックの内側のキーで、loaded_at_field の兄弟ではない。ソースレベルの既定にも同じ入れ子で置けるが、鮮度列の名前がテーブルごとに違う（updated_at / viewed_at / occurred_at）ので、テーブル側に書く。テストの where をモデル単位ではなく各テストの config: に書くのと同じ理由である。

freshness と loaded_at_field を config: の下に置く書き方は新しめで（それぞれ dbt 1.9 / 1.10）、古い版ではソース／テーブルの直下に直接書く。

(e) exposures で BI を依存に登録する

dbt の依存グラフは ref() の届く範囲で終わる。ダッシュボードが obt_scout_funnel を読んでいることは dbt からは見えないので、exposures に書いて初めて「このモデルを変更すると誰が困るか」が機械可読になる。§2(a) の「誰がまだ旧版を見ているか分からない」はここで解ける。

# models/marts/exposures.yml
version: 2

exposures:
  - name: scout_funnel_dashboard
    label: スカウトファネル
    type: dashboard
    maturity: high
    description: |
      送信主体（企業 / エージェント）別の 開封 → 返信 → 応募 → 入社 ファネル。
      更新: 毎日 08:00 JST。fct_scout は v2 に移行済み。
    depends_on:
      - ref('obt_scout_funnel')
      - ref('fct_scout')
      - ref('dim_scout_sender')
    owner:
      name: Data Platform
      email: data-platform@example.invalid

  - name: agency_fee_report
    label: 成果報酬レポート
    type: analysis
    maturity: medium
    description: エージェント別の成果報酬。v1 からの移行が未了。
    depends_on:
      - ref('fct_placement')
      - ref('dim_agency')
    owner:
      name: Revenue Ops
      email: revops@example.invalid
# ダッシュボードが依存する全モデルをビルドしてテストする
dbt build --select +exposure:scout_funnel_dashboard

6. 判断基準

テストを置く層と種類

層必須任意置かない（理由）
sourcefreshness（loaded_at_field）—行レベルのテスト。全件スキャンのコストに見合わず、自分たちでは直せない相手に指摘するだけになる
stagingnot_null（自然キー・時刻列）、accepted_values（区分値）、自然キーの uniqueaccepted_range（score_* が 1.0〜5.0）relationships。キーはまだ解決していないので、失敗しても原因がソースかモデルか切り分けられない
intermediate粒度（unique_combination_of_columns）結合前後の行数一致contract。公開面ではなく、形を凍結すると分割・統合の自由が消える
marts dim_*_key の unique ＋ not_null、-1 既定行の存在accepted_values、SCD2 の版の重なり無し加法性。メジャーが無い
marts fct_*粒度、全 FK の relationships、加法性（expression_is_true）、contract原子ファクトとの件数照合（DT#77）、業務ルールスクリーン—
marts agg_*粒度、素のファクトとの合計一致—relationships。上流のファクトで保証済みで、二重に実行するだけ
marts obt_*行数が元のファクトと一致（結合による増殖の検知）—粒度・参照整合性。スタースキーマ側で保証済み
snapshotsdbt_valid_from / dbt_valid_to の重なりが無いこと——

改版するか、上書きするか

変更契約での扱い判断理由
列を足す（fct_scout に member_profile_mini_key）非破壊上書き。columns: に足す既存の参照は影響を受けない。ただし契約下では YAML を更新しないとビルドが失敗する
列を消す・改名する破壊新版下流の SELECT がエラーになる
型を変える破壊新版BI 側の集計・書式が合わなくなる
制約（not_null）を外す・変える破壊（1.6 以降）新版NULL が来ない前提の下流がエラーになる
制約（not_null）を足す検知されない（dbt の破壊的変更の定義は「既存制約の削除・変更」）新版NULL を前提にしていた下流が誤った結果になるが、契約は検知しない
列も型も同じまま値の意味を変える（member_key を現在版から時点版へ）検知されない新版過去の全ての数字が黙って変わる。契約は形しか守らない
粒度を変える検知されない新モデル粒度が違えば別のファクトである（DM01『粒度を宣言する』）。版ではない
バグ修正（過去の数字が正しくなる）—上書き ＋ 告知版を切ると誤った版が本番に残り続ける
モデル名に _v2 を埋める—しないlatest_version も deprecation_date も無く、両方が本番参照される（§2(a)）

7. 演習

(a) fct_application_pipeline に置くべきテストを列挙し、それぞれがどの失敗を捕まえるか

解答例
テスト対象捕まえる失敗
dbt_utils.unique_combination_of_columns: [application_id]モデル§2(c)。selection_events をピボットせずに結合して P001 が 6 行に増える（selection_events に applied は無く、書類〜入社の 6 イベント）
全 _key 列の not_null列NULL の外部キー。hired_date_key が NULL だと JOIN dim_date で入社前の応募が丸ごと除外される（DT#43）
relationships: 8 本の日付キー → dim_date.date_key列未達を -1 にし忘れて 19700101 等を入れる事故。dim_date に -1 行があるので where で除かない
relationships: member_key / company_key / job_posting_key / agency_key / agent_key / job_category_key / channel_key列時点結合の窓がずれて、応募時点に存在しない版のキーを引く
accepted_values: current_stage列ソースに新しい stage が増えたのに気づかない。列スクリーン
expression_is_true: not (is_hired = 1 and hired_date_key = -1)モデルマイルストーンのフラグと日付キーの不整合。累積スナップショットの更新漏れ
expression_is_true: days_applied_to_offer >= 0モデルタイムゾーン（JST / UTC）の取り違えで負のリードタイムが出る
singular test: fct_selection_event の stage='hired' 件数と SUM(is_hired) の一致プロジェクト累積スナップショットだけがずれる。サマリー単独は危険（DT#77）
contract: enforced: trueモデル16 本の FK のうち 1 本を消す・改名する変更が、BI に届く前にビルドで失敗する

粒度・参照整合性・加法性の 3 種が揃っている。require_partition_filter を張る場合は、全テストの config に where: "applied_date >= date_sub(current_date(), interval 90 day)" を足す。

(b) dim_company の industry と sector の間に中間分類を 1 階層足す変更は、改版か上書きか

解答例

列を 1 本足すだけなら上書き。 §6 の改版表の第 1 行を適用する。契約の観点では非破壊（既存の列名も型も制約も変わらない）で、dbt も破壊的変更として扱わない。

ただし contract: enforced: true を張っているなら columns: への追記が必須で、忘れるとビルドが「契約と形が違う」というエラーになる。

ただし同じ依頼が「再分類」を含むなら新版。 中間分類を足すついでに industry の値の割り当てを変える（C002 を IT から別分類へ移す等）と、列も型も変わらないまま過去の全ての業界別集計が変わる。これは §6 の第 5 行「値の意味を変える」で、契約は検知しない。

依頼の実体判断やること
列を 1 本足すだけ上書きモデル ＋ columns: に追記。not_null は付けない（過去行が埋まらない）
足したうえで既存の industry を再分類新版versions: に v2。旧版に deprecation_date。exposures を見て下流に告知
SCD2 の版を切り直して過去も新分類にする新版 ＋ 再表明Type1 として全履歴を上書きするか、Type2 として新版を積むかは DM05 で扱った判断である。どちらでも数字は変わるので告知が要る

(c) int_review_member_link をどの層・どのデータセットに置き、テストで何を保証するか

解答例

層は intermediate、データセットは marts と別のアクセス制限つきスキーマ。 名前が int_ なのは前掲の命名規約どおりで、役割も intermediate の定義（結合を担い公開面ではない）に合う。

ただし ephemeral にはしない。会員とクチコミの結合という使うたびに監査したい操作なので、実体を持つテーブルとして残し、権限で守る。

# dbt_project.yml
models:
  careervoice:
    intermediate:
      +materialized: ephemeral
      +schema: intermediate
      restricted:
        +materialized: table
        +schema: restricted     # BigQuery 側で IAM を分ける
        +tags: ['pii']
保証することテスト
粒度が 1 行 = 1 クチコミであること（結合で増えていない）dbt_utils.unique_combination_of_columns: [review_id]
review_id が fct_review の退化ディメンションと一致relationships: to: ref('fct_review'), field: review_id
member_key が投稿時点の版に解決しているrelationships: to: ref('dim_member'), field: member_key ＋ member_key != -1 の expression_is_true
fct_review が member_key を持たないこと（匿名性の固定判断が破られていない）fct_review の contract: enforced: true。列を足せばビルドが失敗する
公開データセットに漏れていないことsingular test で int_review_member_link の下流に marts のモデルが無いことを確認するか、+tags: ['pii'] を CI で dbt list --select tag:pii+ して差分を見る

もう1つ、SQL のテストでは書きにくい保証がある。公開面（fct_review × dim_review_attributes）から個人が再識別できないことだ。準識別子の組合せごとの行数（k-匿名性）は singular test で HAVING COUNT(*) < 5 を出せば最低限は測れるが、l-多様性まで見るなら Sensitive Data Protection の Risk analysis ジョブを CI とは別の定期ジョブで回し、結果を dim_audit の quality_flag ではなく独立した監査テーブルに残す（DMBOK07 の「分類の自動化」）。

表の最後の 1 行が本題である。粒度も参照整合性も守れているのに公開面へ繋いでしまう事故は SQL のテストでは捕まらないので、依存グラフ側で守る（exposures と tags）。fct_review の契約は、匿名性という設計判断を機械が守れる形に翻訳したものになっている。

8. 参考: 手元の基盤ではどうか

  • dbt_logs_analysis には mart_url_performance / mart_url_performance_v2 / mart_url_performance_incremental の 3 本が別モデル名で並び、models/marts/exposures.yml の weekly_performance_report が _incremental と _v2 の両方に依存している。§2(a) の形そのもので、この資料の基準なら versions: ＋ latest_version にまとめ、旧版に deprecation_date を立てる。
  • mart_url_performance_incremental は unique_key=['url_path', 'date'] を config に書きながら、models/marts/schema.yml に項目自体が無く、テストは 0 件。宣言した粒度をテストに翻訳していないので §2(c) が起きても気づけない。dbt_utils を packages.yml に入れて unique_combination_of_columns: [url_path, date] を 1 本足すのが最短。
  • models/staging/sources.yml に loaded_at_field と freshness が無い。Glue Crawler の出力が止まっても、下流の not_null は「行が無い」を検知しないので全部通る。
  • 一方 exposures.yml は 3 件（dashboard / application / notebook）が既に登録済みで、§5(e) は実装済みと言える。足りないのは登録ではなく、そこから逆算した改版手順のほう。
  • news_pipeline の summaries.scoring_version は「どの版の採点ロジックで付けたスコアか」を行に持つ列で、監査ディメンションの発想を 1 列に縮めたものになっている。raw_articles.collected_at と合わせると dim_audit の batch_id / loaded_at 相当は揃うが、実行 ID（invocation_id 相当）が無いので「どの実行が入れた行か」は特定できない（§2(d)）。
  • 試せる種: dbt_logs_analysis に versions: を導入し、mart_url_performance を v1、_v2 を v2 として exposures.yml の参照を ref('mart_url_performance', v=2) に統一する。物理名が変わるので alias の挙動も同時に確かめられる。
