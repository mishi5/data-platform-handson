ファクトの3型とファクトレス

データマート設計 02 ／ 参照: DWT ch.4, Fact Tables, Design Tip #43 #50 #77 #95 ／ 再解釈: Functional Data Engineering（snapshotting）, dbt BigQuery configs

1. この回が決めること

同じソースイベントから、どの型のファクトを作るか。型は問いで決まる。ソースの形では決まらない。

selection_events という1本のテーブルから、トランザクションファクト（fct_selection_event）と累積スナップショット（fct_application_pipeline）の両方が出る。逆に job_postings という1本のマスタからは、定期スナップショット（fct_job_posting_daily）を毎日書き足さない限り「4/15 時点の掲載中件数」は二度と再現できない。

決めることこの回の結論
型の選び方問いの時制で決める。「いつ何件」＝トランザクション／「その日いくつ」＝定期／「どこまで進んだ・何日かかった」＝累積。ただし数えたい事象のトランザクションファクトが無い場合は例外（応募数は §6 の2行目）
型は排他か排他ではない。1プロセスに3型が同居してよい（選考は fct_selection_event と fct_application_pipeline の両方）
累積スナップショットの裏必ず原子トランザクションファクトを置く。サマリーだけ持たない（DT#77）
未達マイルストーン日付キーは -1（dim_date に -1 行）。NULL の外部キーを作らない（DT#43）
未達のラグメジャー側は NULL のままにする。0 で埋めない（0日で到達した、と区別できなくなる）
ヘッダ／明細applications（ヘッダ）の次元は selection_events（明細）に降ろす。application_id は退化ディメンション（DT#95）
ファクトレスイベント型 = fct_page_view、カバレッジ型 = 契約企業 × 月 × スカウト枠（DT#50）

2. どこで壊れるか

(a) 定期スナップショットを作らず、ソースから「その日」を再構成する

fct_job_posting_daily を作らずに、job_postings の posted_at / closed_at だけで「4/15 時点の掲載中求人数」を出そうとする。書けるクエリはこうなる。

-- 4/15 時点の掲載中件数（ソース再構成版・壊れている）
SELECT COUNT(*)
FROM {{ source('src_careervoice', 'job_postings') }}
WHERE DATE(posted_at, 'Asia/Tokyo') <= '2026-04-15'
  AND (closed_at IS NULL OR DATE(closed_at, 'Asia/Tokyo') > '2026-04-15')

これは「今の行の値から過去を推定している」だけで、「4/15 にそう見えた」ことの記録ではない。3通りに壊れる。

  • 後から埋まる列を後から読む。closed_at は掲載が閉じた瞬間に OLTP 側で埋まる。J001（C001 のデータエンジニア、4/1 掲載）を 5月に閉じてから同じクエリを流せば 4/15 の答えは変わらないが、閉じたあとに再掲載されて status が open に戻り closed_at が NULL に上書きされると、閉じていた期間そのものが消える。
  • 行が消えると過去も消える。論理削除（deleted_at）や物理削除が入った求人は、過去の日付の集計からも同時に消える。先月出したレポートと今月出したレポートで 4/15 の件数が違う、という説明できない差分になる。
  • その日限りの派生値を持てない。days_since_posted、application_count_cum、scout_count_cum は「その日の時点で何日経過・何件累積か」であって、ソースには存在しない。毎回 dim_date との範囲結合で作り直すことになり、日次の推移を出すたびに全求人 × 全日を展開する。

定期スナップショットを持てば、答えは WHERE snapshot_date = DATE '2026-04-15' の1パーティション読みになり、いつクエリを流しても同じ数字が返る。これは性能の話ではなく再現性の話である。

(b) 累積スナップショットを UPDATE で運用する

fct_application_pipeline を「応募が来たら INSERT し、ステージが進むたび UPDATE」で運用したくなる。OLTP の発想としては自然だが、BigQuery では次に当たる。

  • ストリーミングバッファの行は DML で触れない。ストリーミング挿入した直後の行はバッファがフラッシュされるまで UPDATE / DELETE / MERGE の対象にできない。応募当日に届いた document イベントを即座に反映しようとすると失敗する。
  • DML は行単位の更新に向かない。ステージ遷移1件ごとに UPDATE ... WHERE application_id = 'P001' を投げると、パーティション指定が無ければ表全体をスキャンして書き戻す。同一テーブルへの変更 DML は競合するとキューイングと再試行に回るので、件数が増えるほど詰まる。
  • 冪等でない。同じイベントを二度流したときに何が起きるかが、UPDATE 文の書き方次第で変わる。

この題材での決定は「更新しない実装で累積スナップショットを作る」。selection_events から毎回 GROUP BY application_id で全マイルストーンを畳み直せば、出力は入力の関数になり、何度流しても同じ表になる（§5）。差分だけを流す形（merge / insert_overwrite）と、そのときのルックバック幅は 09回で扱う。

(c) rejected と withdrawn を「終了」に丸める

selection_events.stage は8値（document / first_interview / final_interview / offer / accepted / hired / rejected / withdrawn）ある。ファクトを作るときに rejected と withdrawn をまとめて is_closed = 1 にすると、次の問いが二度と答えられなくなる。

  • 最終面接まで進んで企業が見送った件数と、候補者が辞退した件数の比。前者は求人票と選考基準の問題、後者は年収レンジと他社競合の問題で、打ち手が真逆になる。
  • チャネル別の辞退率。scout_agent 経由は search 経由より辞退が多いか、という dim_channel での切り口が消える。

だから fct_application_pipeline は is_hired / is_rejected / is_withdrawn を別々のメジャーとして持ち、終了日は closed_date_key 1本にまとめる。「終了」という粗い概念は BI 側で is_rejected + is_withdrawn と足せば作れる。

足して作れるものはファクトに置かない。足しても戻せないものだけをファクトに置く。

3. Kimball の原則

3型の定義

技法定義（DWT ch.4 / Fact Tables）使う条件
トランザクションファクトある一瞬の測定。測られた値は「その瞬間・その事象にとってのみ有効」。外部キーの組合せは予測できず、疎にも密にもなる事象が起きたことそのものを数えたい。最も細かい粒度が取れる
定期スナップショットファクトあらかじめ決めた期間（日・月）をまとめた測定。活動が無くても全エンティティの行が現れるという保証がある。予測どおりに密残高・在庫・掲載中・契約中のような「状態」を期間で切って見たい
累積スナップショットファクト始まりと終わりがはっきりしたプロセスを1行で表す。プロセスが進むたびに行が再訪され上書きされる。行数は他の2型より小さいパイプラインの通過・滞留・ラグを測りたい

Kimball の主張（Fact Tables, 2008 / DWT ch.4）: 3型はどれかを選ぶものではなく、同じビジネスプロセスに対して並存しうる。粒度の宣言は「外部キーの列挙」ではなく1行が業務上何を表すかの言明であり、これを先に決めないと加法性の判断（単価は足せない、金額は足せる）ができない。

定期スナップショットの半加法性

DWT ch.4（在庫）の中心はここにある。fct_job_posting_daily.is_open は求人をまたいでは足せる（＝その日の掲載中件数）が、日をまたいで足すと意味を失う（4/1〜4/30 の合計 = のべ掲載日数であって「4月の掲載件数」ではない）。fct_contract_monthly.scouts_remaining も同じで、企業をまたいでは足せるが月をまたいでは足せない。

半加法メジャーの正しい時間方向の集約は平均か期末値である。「4月の平均掲載中件数」なら AVG、「4月末の掲載中件数」なら snapshot_date_key = 20260430 の行を取る。この判断は BI 側の集計定義に閉じ込めず、メジャー名（is_open）と粒度宣言で読み手に伝える。

ファクトレス・ファクトの2種（DT#50）

種類持つもの答えられる問い題材での例
イベント記録型事象が起きたという関係だけ（数値メジャーが無い）「何回起きたか」＝行を数えるfct_page_view。view_count = 1 以外にメジャーが無い
カバレッジ型「起こりえた組合せ」の関係「起きなかったこと」＝カバレッジ側にあってイベント側に無い組合せ契約企業 × 月 × 付与されたスカウト枠

Kimball の主張（DT#50）: ファクトレス・ファクトはディメンション間の多対多の関係だけを捕まえ、数値も文字列のファクトも持たない。用途は2つ — 事象の記録（受講・出席・事故）と、カバレッジ（販促対象になった商品、施設の予約枠）。カバレッジ型の存在理由は「販促したのに売れなかった商品」のような、イベント表だけでは答えられない問いにある。

fct_page_view はイベント記録型そのものである。1行 = 1ページ表示で、数値らしい数値は無い。それでも page_context_key（page_type × device × referrer_type × is_unlocked）と company_key を持つので、「iOS から company_review を閲覧権限なしで見た回数」が数えられる。

メジャーが無いことは、ファクトを作らない理由にならない。

カバレッジ型は「スカウト枠の付与」で必要になる。fct_scout（送信されたスカウト）だけでは、枠を持っていたのに1通も送らなかった企業が表から消える。分母が消えるので消化率が計算できない。

この題材では純粋なファクトレス表を別に作らず、fct_contract_monthly に scout_quota / scouts_sent / scouts_remaining を載せて「契約している企業 × 月」の行を必ず立てる形にした。メジャーを持つので厳密にはファクトレスではないが、役割はカバレッジ型と同じ（K001 が 2026-07 に0通しか送らなくても 2026-07 の行が存在する）。

ヘッダ／明細の扱い（DT#95）

applications（ヘッダ: 誰がどの求人に、どのチャネルで応募したか）と selection_events（明細: そのステージ遷移）は、Kimball が名指しで警告するヘッダ／明細の関係にある。避けるべき2パターンはこうだ。

  • ヘッダをディメンションにする。応募ヘッダをそのままディメンション化すると、明細が1応募あたり数件しか無いので、ディメンションがファクトの数分の1という異常な比率になる。ディメンションはファクトよりはるかに小さいという前提が崩れる（だから正典に応募のディメンションは無い）。
  • ヘッダを別ファクトにして明細と結合する。大きいファクトともっと大きいファクトを結合することになる。会員属性や企業規模で選考イベントを切るたびにこの結合が要る。

Kimball の主張（DT#95）: ヘッダの次元性をすべて明細に降ろす。ヘッダの伝票番号は退化ディメンションとしてファクトに残し、それ専用のディメンション表は作らない。

ヘッダ単位の金額（送料のような、明細に自然に割り当てられない額）の扱いは DT#95 の範囲外である。この題材では applications がヘッダ金額を持たないので問題にならない。

この題材の決定: fct_selection_event は member_key / company_key / job_posting_key / agency_key / agent_key / job_category_key / channel_key を全部自分で持つ（applications と、その求人・スカウトから降りてきた次元）。application_id はディメンションを作らず退化ディメンションとして置く。fct_application_pipeline も同じ次元を持つので、両者は同じディメンションで drill across できる。

サマリー単独は危険（DT#77）

Kimball の主張（DT#77）: 詳細データは予測できない形に丸められるが、逆は成り立たない — 「サマリーを魔法のように構成要素へ分解することはできない」。集約表は原子データの補完であって置き換えではない。

fct_application_pipeline は8本の日付キーで応募のライフサイクルを畳んでいる。ここで失われるのは「同じステージを2回通った」情報である。first_interview が2回記録されている応募（面接をやり直した）は、MIN() で畳んだ瞬間に1回に見える。

だから正典の固定判断として、fct_application_pipeline の裏に fct_selection_event を必ず置く。累積スナップショットは「速く答えるための表」であり、真実は原子ファクトの側にある。fct_review_moderation.moderation_rounds のように「何周したか」をメジャーとして持ち上げるのは、この損失に対する部分的な埋め合わせでしかない。

4. 現代の再解釈

この回に割り当てられた再解釈記事は無い。3型の区別そのものは、列指向 DWH でも変わらずに残る（型は問いの形を写したものであって、ストレージの都合ではない）。変わるのは累積スナップショットの「行を更新する」という実装だけである。

Functional Data Engineering（snapshotting）: パーティションを不変オブジェクトとして扱い、更新せず新しいスナップショットを積むだけにする。同じパーティションを何度作り直しても同じ結果になる（再現性）、ジョブを再実行しても副作用が無い（冪等性）、時系列は GROUP BY の日付で自然に取れる。代償はデータの重複だが、ディメンション規模なら工数に対して安い。

この主張は定期スナップショットと相性が完全に一致する。fct_job_posting_daily は「日付パーティションを1日1枚積む」だけで、Kimball の言う定期スナップショットの性質（密・不変・半加法）をそのまま満たす。dbt では insert_overwrite がこの形にあたる。

-- 定期スナップショット = 不変パーティションの積み上げ（詳細は 09回）
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'snapshot_date', 'data_type': 'date', 'granularity': 'day'}
) }}

partition_by は snapshot_date_key（INT64）ではなく、正典どおり並べて持つ DATE 列 snapshot_date に張る。整数のレンジパーティションでも書けるが、日付関数がそのまま使えるほうが運用が素直になる。

一方、累積スナップショットは原理的に「過去の行を書き換える」型なので、不変パーティションと正面から衝突する。BigQuery での実務上の答えは2つに割れる。

方式やること向く条件この題材での判断
全再構築selection_events から毎回 GROUP BY で作り直す行数が小さい（累積スナップショットは元々小さい）。完全に冪等これを既定にする。応募数規模なら全再構築で足りる
差分マージincremental_strategy='merge' + unique_key='application_id'行数が大きく全再構築のコストが無視できない規模が問題になってから。ルックバック幅の設計込みで 09回

残るもの／変わるもの: 型の選択（何を1行にするか、日付キーを何本持つか、何を -1 にするか）は意味の設計なので変わらない。変わるのは「更新」を UPDATE 文で実現するか、パーティションの入れ替えで実現するかという物理の話だけである。Kimball の累積スナップショットは「行を UPDATE せよ」ではなく「1行がプロセス1件を表し、進捗を反映せよ」という要求だと読めば、全再構築は原典への違反ではない。

5. BigQuery + dbt での実装

日付キーのマクロ

8本の日付キーを書くので、-1 の埋め方をマクロに閉じ込める。未達は -1、dim_date 側に -1（full_date = NULL、表示名「未到達」）の行がある前提（DT#43）。

-- macros/date_key.sql
{% macro date_key(ts_expr) -%}
    COALESCE(CAST(FORMAT_DATE('%Y%m%d', DATE({{ ts_expr }}, 'Asia/Tokyo')) AS INT64), -1)
{%- endmacro %}

-- macros/audit_key.sql（この実行の監査行。本設計は 10回）
{% macro audit_key() -%}
    COALESCE((
        SELECT MIN(audit_key) FROM {{ ref('dim_audit') }}
        WHERE dbt_invocation_id = '{{ invocation_id }}'
    ), -1)
{%- endmacro %}

fct_application_pipeline — selection_events から畳む

ソースは selection_events（1行 = 1ステージ遷移）。これを application_id で GROUP BY し、ステージごとに条件付き MIN() でピボットする。MIN() なのは、同じステージが複数回記録されたときに最初の到達をマイルストーンとするため（何回通ったかは fct_selection_event 側で数える）。

-- models/marts/fct_application_pipeline.sql
{{ config(
    materialized='table',
    partition_by={'field': 'applied_date', 'data_type': 'date', 'granularity': 'day'}
) }}

WITH milestones AS (

    SELECT
        application_id,
        MIN(IF(stage = 'document',        occurred_at, NULL)) AS document_at,
        MIN(IF(stage = 'first_interview', occurred_at, NULL)) AS first_interview_at,
        MIN(IF(stage = 'final_interview', occurred_at, NULL)) AS final_interview_at,
        MIN(IF(stage = 'offer',           occurred_at, NULL)) AS offer_at,
        MIN(IF(stage = 'accepted',        occurred_at, NULL)) AS accepted_at,
        MIN(IF(stage = 'hired',           occurred_at, NULL)) AS hired_at,
        MIN(IF(stage = 'rejected',        occurred_at, NULL)) AS rejected_at,
        MIN(IF(stage = 'withdrawn',       occurred_at, NULL)) AS withdrawn_at
    FROM {{ ref('stg_careervoice__selection_events') }}
    GROUP BY application_id

),

applications AS (

    SELECT
        application_id,
        member_id,
        job_posting_id,
        scout_id,
        source_channel,
        applied_at
    FROM {{ ref('stg_careervoice__applications') }}

),

postings AS (

    SELECT
        job_posting_id,
        company_id,
        agency_id,
        job_category_code
    FROM {{ ref('stg_careervoice__job_postings') }}

),

scouts AS (                -- 応募のきっかけになったスカウト（担当エージェントはここから）

    SELECT
        scout_id,
        sender_agent_id

ディメンションキーを全部 COALESCE(..., -1) で包んでいるのは、未達だけでなく「ディメンション側に該当行が無い」場合も未知として -1 に落とすためである。SCD2 の区間が応募時刻をカバーしない（遅延到着・区間の穴）と member_key は NULL になるが、relationships テストは NULL 行を黙って無視するので気づけない。-1 に落としておけば not_null で検出できる。

エージェント側のキーが agent_key ではなく agency_key なのは、job_postings が持つのが agency_id（会社としてのエージェンシー）までで、dim_agent の粒度である担当者は求人だけでは決まらないからである。担当者ディメンションに agency_id で結ぶと1求人 × 担当者数に行が増え、粒度宣言（1行 = 1求人 × 1日）が壊れる。

だからここは dim_agent を agency_id 粒度へ畳んだ縮約ディメンション dim_agency（DWT ch.4）に結ぶ。直接掲載（agency_id が NULL）は -1。担当者別に見たい問いは fct_scout / fct_placement 側で答える。

materialized='incremental' + insert_overwrite にしているのがこのモデルの要点である。ルックバック窓（3日）より前のパーティションは二度と作り直さない。これが「いつ流しても同じ数字」の実体である。

毎回ソースの現在値から全期間を再展開するなら、§2(a) で否定したクエリと同じ弱点を抱えることになる（ルックバック幅の設計は 09回）。

累計メジャー（application_count_cum / scout_count_cum）を window 関数で積み上げていないのは、増分実行では直近3日分の行しか作らないからである。窓に過去の行が入らないので、SUM() OVER (ORDER BY snapshot_date_key) は 0 から数え直してしまう。累計は常にソース側の全履歴から <= で数える。

この累計は掲載期間内に届いた分だけを数える。掲載終了後に届いた応募は、その求人の行がもう立たないので入らない。

掲載期間は [posted_date, closed_date) の半開区間として扱う。終了日当日は掲載中に数えない — §2(a) の「壊れている」クエリ（closed_at > '2026-04-15'）と同じ規約に揃えてある。

dim_date の -1 行は full_date が NULL なので比較が NULL になり、勝手に混ざらない。J001 の行はこうなる（J001 宛のスカウトは正典に2件ある。S003 が 6/18 送信、S001 が 6/20 送信、P001 が 6/23 応募）。

7. 演習

(a) スカウト枠の消化は、定期スナップショットで持つべきか

「契約企業が月次のスカウト枠をどれだけ消化したか」を出したい。fct_contract_monthly（1行 = 1契約 × 1月）を作る必要があるか、それとも fct_scout を月で GROUP BY して contracts.scout_quota_monthly と突き合わせれば済むか。

解答例

定期スナップショットが要る。fct_scout の集約では3つ落ちる。

  • 送信ゼロの企業と月が消える。消化率の分母は「契約していた企業 × 月」であって「送信があった企業 × 月」ではない。0通の企業こそ解約予兆として見たい対象なので、これが消えるのは致命的（判断基準の表「起きなかったこと」の行 / DT#50 のカバレッジ型）。
  • 枠がその月いくつだったかが分からない。scout_quota_monthly は contracts の現在値で、プラン変更で上書きされる。K001 が premium（枠 200）から途中で変われば、過去の月の消化率が遡って変わる。スナップショットに scout_quota を焼き込めば固定される。
  • 残枠が半加法であることを表現できない。scouts_remaining は企業をまたいでは足せるが月をまたいでは足せない。この性質はメジャーとして持って初めて明示できる。
-- 消化率（送信ゼロの企業も分母に残る）
SELECT
    month_date_key,
    SAFE_DIVIDE(SUM(scouts_sent), SUM(scout_quota)) AS quota_usage_rate,
    COUNTIF(scouts_sent = 0) AS companies_with_no_scout
FROM {{ ref('fct_contract_monthly') }}
WHERE is_active = 1
GROUP BY month_date_key

この行の要点は「キーは -1、ラグは NULL、フラグは 0」という3種類の埋め方を1行の中で使い分けること。開封率は SAFE_DIVIDE(SUM(is_opened), COUNT(*))、平均開封時間は AVG(hours_to_open) で未開封が自動的に除外される。

(c) page_views.is_unlocked はメジャーかディメンションか

is_unlocked（閲覧権限ありで見たか）を fct_page_view のメジャーとして置くか、dim_page_context の属性として置くか。

解答例

ディメンション属性（dim_page_context のジャンク列）。判断基準の表「0/1 のフラグをどこに置くか」の行を適用する。

  • 粒度が 1行 = 1ページ表示なので、SUM(is_unlocked) は「権限ありの表示回数」になり、COUNT(*) との比で率が出せる — つまりメジャーに置いても数字は出る。それでもディメンションに置くのは、これが測定値ではなく表示の文脈だからである。page_type × device × referrer_type と同格の切り口で、単独で足す場面が無い。
  • ジャンクディメンション（72行）に入れれば、他の3属性との組合せで WHERE と GROUP BY の両方に使え、ファクトの列も1本増えない。
  • 逆に is_hired（fct_application_pipeline）はメジャーでよい。足すと「入社数」という業務上の量になり、他のファクトと drill across する対象になる。
-- 閲覧権限あり比率（is_unlocked はディメンション側）
SELECT
    pc.page_type,
    COUNTIF(pc.is_unlocked) AS unlocked_views,
    COUNT(*)                AS total_views,
    SAFE_DIVIDE(COUNTIF(pc.is_unlocked), COUNT(*)) AS unlocked_rate
FROM {{ ref('fct_page_view') }} AS pv
INNER JOIN {{ ref('dim_page_context') }} AS pc USING (page_context_key)
GROUP BY pc.page_type

8. 参考: 手元の基盤ではどうか

  • dbt_logs_analysis の mart_url_performance は 1行 = URL × 日。型としてはトランザクション（アクセスログ）を日で畳んだ集約であって定期スナップショットではない。アクセスが0件の URL には行が立たないので、「その日 1度も叩かれなかった URL」は答えられない（DT#50 のカバレッジ型が要る問い）。
  • mart_url_performance_incremental は unique_key=['url_path','date'] で MERGE するので、行を上書きするという意味では累積スナップショットと同じ挙動をする。ただし上書きしているのは過去日の再計算であってマイルストーンではないので、型は集約のまま。
  • news_pipeline の raw_articles.content_status は pending → ok → summarized / failed / filtered と1行を上書きしていく。粒度（1行 = 1記事のライフサイクル）は累積スナップショットそのものだが、各遷移の時刻を持たないので「収集から要約までのラグ」が測れない。残っているのは retry_count だけである。
  • この回の基準で言えば、raw_articles は「日付キー1本 + 状態列」の形なので累積スナップショットとしては未完成。遷移ごとの時刻列（または遷移イベント表）を足せば fct_review_moderation と同じ構造になる。
  • 試せる種: summaries のスコア上書き（Type 1）を、上書きせず scoring_version ごとに行を積む形に変えると、採点ロジック変更の影響が「同じ記事の版違い」として測れるようになる。
