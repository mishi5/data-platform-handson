コンフォームドとドリルアクロス

データマート設計 08 ／ 参照: DWT ch.4, The Soul of the Data Warehouse Part 1–2, Design Tip #135 ／ 再解釈: ECM, Hightouch Modelling Part 2

1. この回が決めること

クチコミ・スカウト・応募という別々のビジネスプロセスの数字を、同じ企業・同じ月で横に並べる方法を決める。並べるための技法がドリルアクロスで、その前提がコンフォームドディメンションである。あわせて「集約テーブルを何本持つか」と「エンティティ表 agg_company_entity に指標を入れてよい条件」を決める。

コンフォームドの 3 条件

Kimball の判定基準は「行ヘッダに使うフィールドが同じドメインを持つこと」で、片方がもう片方の部分集合でもよい。運用上はこれを 3 条件に分解して点検する。

条件意味CareerVoice での点検破れる例
同じ意味同じ値が同じ実体を指すdim_company の 1 行は法人 1 社。corporate_number が同一なら同一企業片方が「掲載主体」、片方が「採用法人」を company と呼ぶ
同じキー行ヘッダに使うキーの採番が一致fct_scout / fct_scout_funnel を除く全ファクトが dim_company 由来の company_key を持つ。この 2 本は dim_scout_sender（sender_id が company なら company_id）経由で企業に戻す片方がイベント時点版、片方が現在値版
同じ属性名列名と値の集合が一致employee_size_band は lt50/50_299/300_999/ge1000 の 4 値だけ片方だけ lt300 という区分を足す

2. どこで壊れるか

(a) ファクトごとに SCD2 の版がずれる

C002（ネクスト技研）は 2026-05-01 に employee_size_band が 50_299 から 300_999 へ変わり、dim_company に 2 行を持つ。fct_review は投稿時点、fct_application_pipeline は応募時点の company_key を持つので、3 月のクチコミは旧版キー、6 月の応募は新版キーに乗る。この 2 つを company_key のまま横に並べると C002 は 2 行に割れ、内部結合にすればどちらの行も相手を見つけられず消える。

fct_scout はさらに厄介で、そもそも company_key を持たない。送信主体は scout_sender_key（dim_scout_sender、これも SCD2）で、企業に戻すには sender_type = 'company' の sender_id を company_id と読み替える一段が要る。この「寄せ方」をモデルごとに各自が書くと、同じ C002 の集計が 3 通り出る。

対策は 1 つ。ドリルアクロスの各パスの先頭で、必ず company_id を経由して is_current 版の company_key に寄せる（§5-1 の company_map）。投稿当時の規模で切りたい場合は、寄せた上で行ヘッダに employee_size_band を足す（それがドリルダウン）。

(b) ファクト同士を直接 JOIN して fan-out する

C001（アオゾラ商事）に 2026-06 のクチコミが 3 件、送信スカウトが 5 件あるとする。fct_review と fct_scout を company_key で JOIN すると 3 × 5 = 15 行になり、SUM(review_count) は 15、SUM(scout_count) も 15 になる。正解は 3 と 5 で、どちらも 5 倍・3 倍に膨らんでいる。

クエリC001 / 2026-06 の結果正しいか
2 ファクトを company_key で直接 JOIN → SUMreview 15 / scout 15✗ 両方が相手の行数倍に膨らむ
同上で COUNT(DISTINCT review_id) 等に逃げるreview 3 / scout 5△ 件数は戻るが SUM(overall_score) は救えない
各ファクトを企業×月に集約してから FULL OUTER JOINreview 3 / scout 5✓ ドリルアクロス

片方が 0 件の月では逆に行が落ちる。Soul 2 はこの症状を、結果が低くも高くもなりうる（"too low or too high, or both"）と書いている。

(c) 問いごとに集約を作って正本が消える

「企業×月のクチコミ」「企業×職種×月のクチコミ」「企業×月のスカウト」「企業×四半期の応募」と問いのたびに集約を足すと、半年で 20 本になる。危険なのは本数ではなく、同じ名前の指標が本ごとに違う定義を持つことである。

ずれる場所具体例結果
母集団片方は published のクチコミだけ、片方は submitted 全件C001 の 4 月クチコミ数が 0 と 1 に分かれる（R002 は却下）
日付の役割片方は submitted_date、片方は published_date で集計月末投稿・翌月公開のクチコミが別の月に落ちる（R001 は 3/10 投稿・3/12 公開で同月だが、境界では割れる）
企業の版片方は投稿時点 company_key、片方は現在値(a) と同じ割れ方
平均の持ち方片方が avg_overall_score を持ってしまう企業をまたぐ再集約が不能。04 回の原則違反

この回の決定は、集約を agg_company_rating_daily（日次・単一ファクト・和と件数）と agg_company_entity（企業 1 行・窓付き）の 2 系統に固定し、それ以外の問いはドリルアクロスのクエリで答えることである。

3. Kimball の原則

技法定義使う条件
コンフォームドディメンション（DWT ch.4）複数のファクトから同じ意味・同じキー・同じ属性名で参照されるディメンション2 つ以上のビジネスプロセスを横断して見たいとき。バスマトリクスの列が正本
縮約ディメンション（DWT ch.4）コンフォームドディメンションの属性・行の部分集合。粒度の粗いファクトに結ぶdim_agency は dim_agent の縮約。担当者が特定できない fct_job_posting_daily はこちらに結ぶ
コンフォームドファクト（DWT ch.4）複数プロセスに現れる同名メジャーの定義・単位・計算式を揃えること揃えられないなら名前を変える。fee_amount と monthly_fee を「売上」に丸めない
ドリルダウン（Soul 1）SELECT に行ヘッダ（グルーピング列）を 1 つ足すこと常に。階層を降りる操作ではない
ドリルアクロス（Soul 2）ファクトごとに別クエリを投げ、同一の行ヘッダで sort/merge（＝外部結合）して列を足すこと2 つ以上のファクトを 1 つの表に並べるとき。UNION（行の追加）ではない

Soul 1 は、ドリルダウンとは SELECT に "adding a row header" することであり、"Row headers and grouping columns are the same thing" だと言う。さらに "drilling down has nothing to do with descending a predetermined hierarchy" と念を押す。つまり C001 の月次クチコミ数に employee_size_band を足すのも dim_date.day_of_week を足すのも、同格のドリルダウンである。

Soul 2 のドリルアクロスは、1 本の SQL で複数ファクトを結ぶのではなく "separate requests to the target fact tables followed by a simple sort/merge on the identical row headers returned from each request" である。前提は "All fact tables in a drill-across query must use conformed dimensions" で、その判定は "Two dimensions are conformed if the fields that you use as common row headers have the same domain"。完全一致は要らず、片方が部分集合でもよい（＝縮約ディメンションが使える）。

バスマトリクスの列が正本

正典のバスマトリクス（canon/domain.md §3）で company 列に ✓ が付いた行が、企業でドリルアクロスできるプロセスの全部である。fct_review の member 列は ✗ なので、会員を行ヘッダにしたクチコミとスカウトの横並びは設計上できない。マトリクスは絵ではなく制約表として読む。

Design Tip #135 は、コンフォームドディメンションがアジャイルを遅くするのではなく可能にすると論じる。ディメンションが揃うほど新プロセスはファクトを 1 本足すだけになり、"the development crank starts turning faster and faster"。全属性の合意は不要で、まず "identify a subset of attributes that have significance across the enterprise" から始めればよい。

逆側の警告も同じ Design Tip にある。個別に作られたマートは "inconsistent categorizations and labels" を持ち、さらに悪いことに一見比較可能なのに業務ルールが "slightly different" になる。§2(c) の 20 本問題は、この現象がチーム内で起きたものである。

4. 現代の再解釈

ECM（Beauchemin, 2023）の出発点は、Kimball 自身の禁止事項である "A BI application must never issue SQL that joins two fact tables together across the fact table's foreign keys"。1 つのエンティティについて複数ファクトの指標を見るたびに回避策を書くのは摩擦が大きい、という主張である。

解は、エンティティ表に窓付き指標（visits_7d, visits_28d, visits_90d）を直接持たせ、"simple queries (without having to use JOIN, UNION ALL, or subqueries)" を可能にすること。保証されるのは "every row is an instance of an entity" であり、COUNT(*) がエンティティ数になる。

ECM は Kimball の否定ではなく、ドリルアクロスの結果を事前に計算して物理化したものである。行ヘッダをエンティティ 1 列（company_key）に固定し、時間窓を _30d / _90d に固定した特殊形と読める。ECM 自身も欠点として保存の冗長、幅の広い表の性能劣化、"column overload" を挙げ、"restraint and limit the number of metrics" を勧めている。

Hightouch 2 は staging / core / consumption の 3 層を置き、"To get the best of both worlds, we can still utilize Kimball's Star Schema as an intermediate step after the staging layer, then materialize Wide Tables out of it" と書く。Wide Table 側の根拠は速度（"25-50% faster in Redshift, Snowflake and BigQuery than Star Schema and joins"）と、JOIN を理解しない利用者にも読めること。ただし結論は "there is no one-size-fits-all model" である。

論点Kimball（原典）現代（ECM / Hightouch 2）CareerVoice の決定
複数ファクトの横断クエリ時にドリルアクロス（マルチパス＋sort/merge）事前に計算してエンティティ表に置く両方。探索はドリルアクロス、定型は agg_company_entity
コンフォームドの必要性ドリルアクロスの絶対条件事前計算でも同じ。むしろ 1 回きりの計算に固定されるので条件が厳しい変わらず必須。§1 の 3 条件で点検する
指標の正本ファクトテーブルエンティティ表を触るのは利用者、正本は上流正本は各ファクト。agg_company_entity は再計算可能な派生物
時間軸行ヘッダに dim_date の属性を足す（任意の期間）固定窓（_30d, _90d）を列にする固定窓だけをエンティティ表に。任意期間はドリルアクロスへ
列数ファクトは細く、ディメンションは広く広い表を許容。ただし列の増やしすぎを自制正典の 7 指標に固定。追加は正典改訂として扱う

5. BigQuery + dbt での実装

5-1. ドリルアクロス（企業 × 月）

3 つのファクトをそれぞれ同じ行ヘッダ (company_key, month_key) に集約し、FULL OUTER JOIN ... USING で並べる。BigQuery の USING は結合キーを 1 列に併合し、FULL OUTER JOIN では両側の値を合成するので、3 段のチェーンでもキー列は 1 つのまま残る。

フィルタは DATE 型のパーティション列（submitted_date / sent_date / applied_date）に掛ける。_date_key（INT64）で絞るとプルーニングが効かない。行ヘッダの month_key も DATE_TRUNC が返す DATE で、正典の date_key（INT64 YYYYMMDD）とは別物である（ブリーフの列名に合わせただけで、ディメンションのキーではない）。

-- analyses/drill_across_company_month.sql
-- 企業 × 月で クチコミ / スカウト / 応募 を横に並べる
WITH company_map AS (
    -- 全 SCD2 版 -> 現在版の company_key（§2a の対策）
    SELECT
        v.company_key,
        cur.company_key AS current_company_key
    FROM {{ ref('dim_company') }} AS v
    INNER JOIN {{ ref('dim_company') }} AS cur
        ON v.company_id = cur.company_id
        AND cur.is_current
),

review_monthly AS (
    SELECT
        m.current_company_key AS company_key,
        DATE_TRUNC(f.submitted_date, MONTH) AS month_key,
        SUM(f.review_count) AS review_count,
        SUM(f.overall_score) AS sum_overall_score
    FROM {{ ref('fct_review') }} AS f
    INNER JOIN company_map AS m
        USING (company_key)
    WHERE f.submitted_date BETWEEN DATE '2026-01-01' AND DATE '2026-08-31'
    GROUP BY 1, 2
),

scout_monthly AS (
    -- fct_scout は company_key を持たない。dim_scout_sender 経由で企業に戻す
    SELECT
        c.company_key,
        DATE_TRUNC(f.sent_date, MONTH) AS month_key,
        SUM(f.scout_count) AS scout_count
    FROM {{ ref('fct_scout') }} AS f
    INNER JOIN {{ ref('dim_scout_sender') }} AS s
        ON f.scout_sender_key = s.scout_sender_key
    INNER JOIN {{ ref('dim_company') }} AS c
        ON c.company_id = s.sender_id
        AND c.is_current
    WHERE f.sent_date BETWEEN DATE '2026-01-01' AND DATE '2026-08-31'
        AND s.sender_type = 'company'
    GROUP BY 1, 2
),

application_monthly AS (
    -- 分母（企業送信スカウト）と母集団を揃えるため、経路別の内訳も出す
    SELECT
        m.current_company_key AS company_key,
        DATE_TRUNC(f.applied_date, MONTH) AS month_key,
        COUNT(*) AS application_count,
        COUNTIF(ch.source_channel = 'scout_company') AS application_count_scout_company,
        SUM(f.is_hired) AS hired_count
    FROM {{ ref('fct_application_pipeline') }} AS f
    INNER JOIN company_map AS m
        USING (company_key)
    INNER JOIN {{ ref('dim_channel') }} AS ch
        ON ch.channel_key = f.channel_key
    WHERE f.applied_date BETWEEN DATE '2026-01-01' AND DATE '2026-08-31'
    GROUP BY 1, 2
),

drilled AS (
    -- sort/merge を FULL OUTER JOIN で書く。ファクト同士は結ばない
    SELECT
        company_key,
        month_key,
        r.review_count,
        r.sum_overall_score,
        s.scout_count,
        a.application_count,
        a.application_count_scout_company,
        a.hired_count
    FROM review_monthly AS r
    FULL OUTER JOIN scout_monthly AS s
        USING (company_key, month_key)
    FULL OUTER JOIN application_monthly AS a
        USING (company_key, month_key)
)

SELECT
    c.name AS company_name,
    d.month_key,
    d.review_count,
    SAFE_DIVIDE(d.sum_overall_score, d.review_count) AS avg_overall_score,
    d.scout_count,
    d.application_count,
    -- 分子分母とも「企業が送ったスカウト」に揃える（全チャネル応募を分子にしない）
    SAFE_DIVIDE(d.application_count_scout_company, d.scout_count) AS apply_rate_scout_company
FROM drilled AS d
INNER JOIN {{ ref('dim_company') }} AS c
    ON c.company_key = d.company_key
    AND c.is_current
ORDER BY company_name, month_key

読み方の要点は 3 つ。各パスは 1 ファクトしか触らない、平均や比率は結合したあとに SAFE_DIVIDE で作る、行ヘッダを増やしたければ 3 つのパス全部に同じ列を足す（Soul 1 のドリルダウン）。3 つ全部に足せない列は、そもそもコンフォームドではない。

比率の分子と分母は母集団を揃える。scout_count は sender_type = 'company' に絞った企業送信スカウトなので、分子も dim_channel で scout_company に絞る。揃えないなら名前を変えて母集団の違いを列名に出す（§3 のコンフォームドファクト）。

ただしチャネルが揃っても、分母は「その月に送信されたスカウト」、分子は「その月に応募された scout_company 応募」でコホートが一致しない。S001（6/20 送信）→ P001（6/23 応募）は同月に収まるが、月末送信では前月分が当月の分子に乗る。月次トレンドの近似としては足りるが、送信を起点に揃えるなら 1 行 = 1 スカウトの送信→応募を持つ fct_scout_funnel を使う。

company_map は INNER JOIN なので、dim_company に -1（未知）行が is_current で存在しないと、未知企業のファクト行が黙って消える。この回のテーマがまさに「行が消える」ことなので、-1 行は必ず現行版として置く（DT#43）。

5-2. グループ企業まで畳む

C003（ヒノデ物流）は parent_company_id が C001 なので、グループ単位で見たい問いがある。br_company_hierarchy の祖先側は is_current 版だけ、子孫側は全 SCD2 版を採り、company_id（自然キー）で畳む。出力を company_key にしておけば company_map とそのまま差し替えられる。

group_map AS (
    -- 全 SCD2 版の company_key -> グループ親（is_current）の company_key
    SELECT DISTINCT
        des.company_key,
        anc.company_key AS group_company_key
    FROM {{ ref('br_company_hierarchy') }} AS b
    INNER JOIN {{ ref('dim_company') }} AS anc
        ON anc.company_key = b.ancestor_company_key
        AND anc.is_current
    INNER JOIN {{ ref('dim_company') }} AS des
        ON des.company_key = b.descendant_company_key
)

§5-1 の 3 パスすべてを畳む。review_monthly / application_monthly は INNER JOIN company_map AS m USING (company_key) を INNER JOIN group_map AS g USING (company_key) に、m.current_company_key AS company_key を g.group_company_key AS company_key に置き換える。

scout_monthly は company_map を経由していないので、dim_scout_sender → dim_company で得た c.company_key に INNER JOIN group_map AS g ON g.company_key = c.company_key を足し、出力を g.group_company_key AS company_key にする（group_map の company_key は全 SCD2 版を含むので is_current 版も引ける）。3 パスのうち 1 本でも畳み忘れると行ヘッダのドメインが揃わず、§2(a) と同じ割れ方をする。

結果は C001 のグループ行に C001 自身と C003 の数字が合算され、同時に C003 単体のグループ行も出る（depth = 0 で自分自身も自グループの子孫だから）。したがって全行の合計は取れない。レベルを選ぶなら b.depth を行ヘッダに足すか is_root で絞る。

br_company_hierarchy は 06 回の実装で既に「祖先側は is_current のみ、子孫側は全版」で作られているので、anc.is_current は安全網としての再指定である。祖先側に旧版が混ざると同じグループが版の数だけ増える。

        USING (company_key)

MV の制約この回のモデルへの影響
RIGHT/FULL OUTER JOIN と自己結合が不可（LEFT OUTER JOIN と UNION ALL はプレビュー）§5-1 のドリルアクロスは MV にできない。company_map（dim_company の自己結合）も不可
集約は出力そのものでなければならない。集約値をさらに計算・フィルタ・結合できないSAFE_DIVIDE(sum, count) を MV 内に持てない。04 回の「和と件数だけ持つ」方針と一致する
使える集約関数は限定（SUM, COUNT, COUNTIF, AVG, MIN, MAX, APPROX_COUNT_DISTINCT, HLL_COUNT.INIT ほか）一覧外の COUNT(DISTINCT ...) は不可。近似でよければ APPROX_COUNT_DISTINCT（内部はスケッチ）
非決定的関数（CURRENT_DATE() など）と UDF、ウィンドウ関数が不可agg_company_entity の _30d / _90d 窓は CURRENT_TIMESTAMP() 起点なので MV にできない
MV のパーティションは任意だが、張るならベーステーブルと同じパーティション列でなければならない（"If the base table is partitioned, then you can partition a materialized view on the same partitioning column."）。時間パーティションでは粒度も一致が要る（"For time-based partitions, the granularity must match (hourly, daily, monthly, or yearly)."）。非パーティションのベーステーブルの上にパーティション MV は作れない（"You cannot partition a materialized view over a non-partitioned base table."）。また "You can't nest materialized views over other materialized views."rating_date は fct_review の submitted_date の別名で、fct_review は DATE 列でパーティションされているので 3 条件を満たす。ネスト禁止はここでは効かない — 参照側の agg_company_entity は materialized='table' であり MV ではない
定義 SQL は後から変更できない（--full-refresh で drop/create）集約定義が動く時期は通常のテーブルで運用し、固まってから MV に移す

MV は普通のテーブルと同じように参照でき、ベーステーブルへのクエリも自動で書き換えられる（"If any part of a query against a base table can be resolved by querying the materialized view, then BigQuery reroutes the query to use the materialized view for improved performance."）。agg_company_entity は materialized='table' なので、agg_company_rating_daily を MV 化しても {{ ref('agg_company_rating_daily') }} はそのまま通る。参照側は移行の障害にならない。

MV 化を止めているのは定義 SQL の不変性である。agg_company_rating_daily の 8 軸の和はまだ動く余地があり、変更のたびに drop/create が要る。定義が固まり、09 回の insert_overwrite より自動維持が有利になった時点で MV へ移す。

7. 演習

(a) 「クチコミ平均が上がった企業は応募率も上がるか」

この問いに答える SQL の骨格を書け。どのファクトを何で結ぶか、応募率の分母を何にするかを先に決めること。

解答例

結ぶのは fct_review（企業×月の sum_overall_score と review_count）と fct_scout（企業×月の送信数）と fct_application_pipeline（企業×月の応募数）の 3 パス。応募率は「企業が送ったスカウト 1 通あたりの、scout_company チャネル応募数」と定義する。分母が sender_type = 'company' に絞られている以上、分子も dim_channel で同じ経路に絞らないと母集団が揃わない（§3 のコンフォームドファクト）。

ファクト同士は結ばず、§5-1 の drilled を入力にして前月差を取る。

-- §5-1 の CTE 群（company_map / *_monthly / drilled）をそのまま前置する
SELECT
    company_key,
    month_key,
    SAFE_DIVIDE(sum_overall_score, review_count) AS avg_score,
    SAFE_DIVIDE(sum_overall_score, review_count)
        - LAG(SAFE_DIVIDE(sum_overall_score, review_count)) OVER w AS d_avg_score,
    SAFE_DIVIDE(application_count_scout_company, scout_count) AS apply_rate,
    SAFE_DIVIDE(application_count_scout_company, scout_count)
        - LAG(SAFE_DIVIDE(application_count_scout_company, scout_count))
            OVER w AS d_apply_rate
FROM drilled
WINDOW w AS (PARTITION BY company_key ORDER BY month_key)

上に CORR(d_avg_score, d_apply_rate) を被せれば相関が出る。ただし FULL OUTER JOIN は「どちらかにデータがある月」しか作らないので、クチコミも応募も 0 の月は行ごと欠け、LAG が飛ぶ。厳密にやるなら dim_date から企業 × 月のスパインを作り、そこへ drilled を LEFT JOIN する。

(b) avg_overall_score_90d は 04 回の原則と矛盾しないか

04 回の固定判断は「集約テーブルは avg_* を持たず sum_* + count を持つ」である。agg_company_entity が avg_overall_score_90d を持つのは違反か。違反でないとすれば、どの条件が効いているか。

解答例

違反ではない。04 回の原則が守るのは「再集約可能性」であり、再集約しないと契約できる終端テーブルでは要件が外れる。§6「エンティティ表に指標を入れる条件」の 3 行（粒度・再集約・非加法指標）を適用した結果である。

効いている条件成立の仕方破れたら
1 エンティティ 1 行の終端テーブルスパインが dim_company の is_current。企業をまたぐ再集約の用途を持たせない業界別平均を AVG(avg_overall_score_90d) で出され、企業ごとの件数差が消える
算出は sum/count からSAFE_DIVIDE(sum_overall_score_90d, review_count_90d)。日次平均の平均を取らない1 件の日と 50 件の日が同じ重みになる
窓が固定で列名に現れる_90d。任意期間の平均は agg_company_rating_daily から作る「平均」が何期間かの合意が失われる

正本は agg_company_rating_daily（さらに遡れば fct_review）のままである。業界別・グループ別の平均が要るときは、そちらから SUM(sum_overall_score)/SUM(review_count) で作る。

(c) agg_member_entity には何を持てるか

dim_member を中心にした会員版のエンティティ集約を検討する。匿名性の固定判断（fct_review は member_key を持たない）を踏まえ、持てる指標と持てない指標を分けよ。

解答例

agg_member_entity は正典未登録の候補である（この回の report に正典への変更提案として記録）。スパインは dim_member の is_current 版 1 行。

候補指標元ファクト可否
受信スカウト数（30 日）fct_scout✓ member_key を全 SCD2 版から現在版に寄せる
開封率・返信率（90 日）fct_scout_funnel✓ ただし SUM(is_opened) と件数を別列で持ち、比率は下流で作る。(b) と同じ条件で比率を持たせてもよいが、返信率は分母が「送信」か「開封」かで 2 通りあるため、分子分母を残して下流に選ばせる
応募数（30 日）・入社（90 日）fct_application_pipeline✓ ただし固定窓なので両方には立たない。M001 の P001（6/23 応募・8/1 入社）は asof が 7/23 以前なら applications_30d に、8/1〜10/30 なら hires_90d にしか入らない。窓幅の選択がファネルの見え方を決める
閲覧企業数（30 日）fct_page_view△ COUNT(DISTINCT company_key) は再集約不能。持つなら会員単位の終端値と割り切る
投稿クチコミ数・平均スコアfct_review✗ member_key が無い。int_review_member_link の再結合は制限データセット外に出せない
希望職種br_member_desired_job_category△ 多値。1 行 1 会員を壊すので priority = 1 の 1 件だけを属性として持つ
現在の年収帯・転職意欲dim_member_profile_mini✓ 指標ではなく属性。M001 は 6/15 以降 600_800/active

クチコミ由来の指標を 1 列でも入れた瞬間に、会員とクチコミの結合結果を公開層へ持ち出したことになる。少人数企業では属性の組合せで投稿者が特定されうるため、この列は「集計値だから安全」とは言えない。会員×クチコミの分析は int_review_member_link 側に閉じたままにする。

8. 参考: 手元の基盤ではどうか

dbt_logs_analysis の mart_url_performance は url_path × date（GROUP BY url_path, date）、mart_error_analysis は date × hour × error_source × error_detail を行ヘッダに持つ。共通する行ヘッダは date だけで、mart_error_analysis は access_errors CTE で読んだ url_path を GROUP BY date, hour, status_code で捨てている。この 2 本は URL でドリルアクロスできない — Soul 2 の「共通の行ヘッダが同じドメインを持つ」以前に、片方に列が無い。

url_path の導出自体は stg_access_logs の split(url, '?')[offset(0)] 1 か所に閉じており、両マートはそれを継承している。つまりコンフォームドの前提は既にできていて、条件は「揃える」ではなく「粒度を落とさない」側にある。exposures.yml の error_monitoring_alert は mart_error_analysis だけ、url_performance_dashboard は mart_url_performance_incremental だけを参照しており、両者を横断する利用者は今のところいない。

news_pipeline の summaries と raw_articles は article_id で横に並ぶが、日時列が raw_articles 側にしかない。日付を行ヘッダにするには必ず片側結合が要る状態で、dim_date に相当する共通軸が存在しない。この回の基準で言えば、日付がコンフォームドディメンションになっていない。
