多対多・不揃い階層・異種ディメンション

データマート設計 06 ／ 参照: DWT ch.7, ch.8, ch.10, Design Tip #142, Kimball Dimensional Modeling Techniques ／ 再解釈: BigQuery ネスト・繰り返し列

1. この回が決めること

ディメンションとファクトの関係は普通は多対一で、ファクト 1 行に対してディメンション値は 1 つに定まる。CareerVoice にはこれが成り立たない箇所が 3 種類ある。会員の希望職種は 1 人に複数（M002 は ENG-BE と ENG-DATA の 2 件）、企業グループと職種は深さが揃わない階層（ENG-DATA は level2 で終端）、スカウトの送信主体は企業とエージェントという別種のエンティティ。この回はこの 3 つを、ブリッジ表・平坦化・supertype のどれで持つかを決める。

問題題材の具体手段 A手段 Bこの回の決定
多値会員の希望職種。member_desired_job_categories、M002 は 2 件br_member_desired_job_category + weighting_factordim_member に desired_job_categories ARRAY<STRUCT<…>> を内包ブリッジ。ARRAY は §4・§6 の条件下での対案

共通する判断軸は 1 つ。「ファクト 1 行 × ディメンション 1 値」を崩すコストを、どこに払わせるかである。ブリッジは行の増殖と重み付けの責任をクエリ側に押しつけ、ARRAY はスキーマの読みにくさを BI ツール側に押しつけ、supertype は NULL 列の存在をディメンション側に押しつける。払う先を決めずに 3 つを混ぜると §2 になる。

2. どこで壊れるか

(a) 重みなしでブリッジを結合してスカウトが 2 倍になる

正典の S003（AG02 → M002、J001、2026-06-18 送信）は fct_scout の 1 行である。M002 の希望職種は ENG-BE と ENG-DATA の 2 件なので、br_member_desired_job_category には M002 の行が 2 本ある。この 1 行に重みなしでブリッジを結合すると 2 行になる。

クエリ結果正しい値
SUM(scout_count)（fct_scout のみ）11
ブリッジを結合して SUM(scout_count)21
ブリッジを結合して SUM(scout_count * weighting_factor)11

職種別に割ると、重み付きは ENG-BE 0.5 / ENG-DATA 0.5 で合計 1。重みなしは 1 / 1 で合計 2。

壊れるのは数字そのものではなく、「明細を足すと総数になる」という読み手の前提である。S003 と同型のスカウトが 6 月に 1,240 件あれば、上段の「6 月のスカウト送信数 1,240 件」に対して下段の職種別内訳の合計が 1,240 を超える。

(b) level3 固定で ENG-DATA が NULL に落ちる

job_categories は ENG → ENG-BE → ENG-BE-JAVA が level3 まで伸びる一方、ENG → ENG-DATA は level2 で終端する。dim_job_category.level3_name をソースのまま引くと ENG-DATA の行は NULL になる。

  • GROUP BY level3_name → BI に「(null)」という行が出る。ENG-DATA と、他の level2 終端の枝が全部そこに混ざる。
  • WHERE level3_name = 'データエンジニア' → 1 行もヒットしない。
  • BI のフィルタが level3_name IN (…) の形になっていると、J001（C001 のデータエンジニア求人、ENG-DATA）が集計から丸ごと消える。「消えた」ことは画面に出ない。

DT#43 の「ディメンションに NULL を置かない」がそのまま効く。正典の決定は level3_name を level2_name の値で埋めること。埋めた事実は leaf_level（この行が実際に何レベルで終端したか）で残す。

(c) 2 本の FK にすると「送信主体別」が UNION になる

採用しなかった対案として、fct_scout に scout_sender_key 1 本ではなく sender_company_key と sender_agent_key の 2 本を持たせた場合を見る。S001（C001 発）は前者に企業キー・後者に -1、S002（AG01 発）はその逆になる。

  • 「送信主体別の返信率」が 2 本のクエリの UNION ALL になる。BI ツールから見ると 2 つの別ディメンションが並んでいるだけで、1 本のドリルダウン軸にできない。
  • 送信主体を 3 種類目に増やすと FK 列が 1 本増える。fct_scout を参照している既存クエリを全部直すことになる。
  • どちらの列も半分の行で -1 になるので、COUNT(DISTINCT sender_agent_key) のような素朴な指標が「エージェント数 + 1」を返す。

3. Kimball の原則

技法定義使う条件
多値ディメンションとブリッジ表ファクトからディメンションへ、グループキー経由でブリッジ表を挟む。ブリッジは「同時に成立する 1 値」につき 1 行を持つディメンションが正当に多値のとき（患者 1 回の診療に複数の診断名）
重み付け係数（weighting factor）ブリッジの各行に、そのグループ内での配分比を持つ。1 グループ内の合計が 1 になる加法メジャーを多値の軸で割りたい。合計を総数と一致させたいとき
impact report / weighted report重みを掛けない集計が impact（「この職種を希望する会員に何件届いたか」）、掛けた集計が weighted（「この職種に帰属する件数」）両方作る。どちらが欲しいかは問いによって変わる。同じ画面に混ぜない
時間可変ブリッジブリッジ表に有効期間のタイムスタンプを持ち、クエリ側が特定時点に制約する関係そのものが時間で変わり、かつ両端が Type 2 のとき（口座と顧客）
固定深さ位置階層多対一の連鎖で、各レベルに合意された名前があるとき、レベルをディメンションの別々の位置属性にする最も速く最も分かりやすい。条件を満たすなら常にこれ
わずかに不揃いな階層深さは一定でないが幅が小さい場合、最大深さの位置属性に業務ルールで押し込む「不定深さ用の複雑な機構を使うよりは」force-fit してよい範囲
不揃い/可変深さ階層のブリッジ階層中のあり得る全経路に 1 行ずつ持つ表。祖先・子孫・depth・末端/根のフラグ深さが不定、代替階層を差し替えたい、共有所有がある、階層が時間変化する
pathstring 属性ディメンション行ごとに、根から自分までの経路を符号化した文字列を 1 列持つブリッジを避けたいとき。ただし代替階層の差し替えと共有所有は表現できず、構造変更で全体の付け替えが要る
supertype / subtype スキーマ共通属性だけを持つ supertype ディメンションと、種別ごとの subtype 表に分ける。core / custom とも呼ぶ異種の製品・口座で、互換しない属性やメジャーが多いとき

Kimball Dimensional Modeling Techniques より。

不揃い階層について: “All these objections can be overcome in relational databases by modeling a ragged hierarchy with a specially constructed bridge table. This bridge table contains a row for every possible path in the ragged hierarchy and enables all forms of hierarchy traversal to be accomplished with standard SQL rather than using special language extensions.”（SQL の再帰拡張では代替階層の差し替え・共有所有・時間変化が扱えない。その全部をブリッジ表が解き、しかも標準 SQL のまま辿れる）

異種ディメンションについて: “The solution is to build a single supertype fact table that has the intersection of the facts from all the account types (along with a supertype dimension table containing the common attributes), and then systematically build separate fact tables (and associated dimension tables) for each of the subtypes.”

多値について: “the multivalued dimension must be attached to the fact table through a group dimension key to a bridge table with one row for each simultaneous diagnosis in a group.” さらに、両端が Type 2 の場合はブリッジ自身に有効/失効タイムスタンプが要り、“the requesting application must constrain the bridge table to a specific moment in time”。

DT#142「Building Bridges」（Warren Thornthwaite）。ブリッジを 2 種類に分ける。1 つは静的ブリッジで、1 ファクト行に紐づく値の集合が時間変化しない（救急外来の受診時診断）。もう 1 つは時間可変ブリッジで、関係が測定対象のトランザクションとは独立に存在し、時間で変わる（顧客と口座）。

作り方は、値の組合せを重複排除してグループを作り、グループに一意キーを振り、それを行方向に展開してブリッジにする。

この Design Tip 自身は静的ブリッジの手順だけを扱い、重み付けには触れていない。重み付け係数と impact / weighted の対比は DWT ch.10（Financial Services）の口座-顧客ブリッジ側の議論。

CareerVoice の 3 つを、この表のどこに当てるか。希望職種は静的ブリッジ（ソースの member_desired_job_categories に履歴が無く、updated_at しか持たない）。企業グループは時間可変の不揃い階層（C003 が C001 から離脱しうる）。

職種はわずかに不揃いな階層で、深さの幅が 1〜3 に収まるので force-fit して dim_job_category に平坦化する。スカウト送信主体は supertypeで、企業とエージェントの共通属性（名前・種別）に対して固有属性が company_industry と agency_tier の 2 列しかないので、subtype 表を分けずに 1 本に畳む。

4. 現代の再解釈

BigQuery のスキーマ設計ガイドは、ブリッジ表という発想そのものへの対案を出している。「ネストと繰り返し列でストレージを非正規化してクエリ性能を上げよ」であり、その理由は結合のためのシャッフルを消せることにある。ガイドの言葉では “Denormalization localizes the data to individual slots, so that execution can be done in parallel”、そして “Increases in storage costs are worth the performance gains of using denormalized data.”

BigQuery ネスト・繰り返し列ガイドの要点と、この題材での効き方。

  • 推奨される形: 一緒にクエリされる低〜中カーディナリティの 1 対多。M002 の希望職種 2 件（仕様上の上限 priority 1..3）はここに当たる。
  • 推奨されない形: 高カーディナリティの 1 対多。会員の閲覧履歴（page_views）を dim_member に ARRAY で内包するのは明確に対象外で、そちらはファクト表のまま。
  • 効かない場合の明記: すでに分析向けに最適化されたスタースキーマは、さらに非正規化してもそれほど得をしない。ガイド自身がそう書いている。CareerVoice の規模ではブリッジ結合のコストは測定誤差の内側で、性能は選択理由にならない。

下の図は同じ問い（「S003 のような M002 宛のスカウトを希望職種別に割る」）を 2 通りの物理設計で表したもの。ブリッジは行を 2 本に増やし、ARRAY は dim_member の 1 行に畳む。どちらも weight を持つ。重みは物理設計ではなく意味の問題なので、ARRAY にしても消えない。

何が変わり、何が残るか

論点Kimball の前提BigQuery + ARRAY で残るもの
結合コストブリッジ 1 本の追加は結合 2 回分の負担。避けられるなら避けるUNNEST は同一テーブル内の展開でシャッフルが起きない。スキャン課金も ARRAY 列を読むぶんだけCareerVoice の規模ではどちらも無視できる。性能は決め手にならない
重みブリッジ行に weighting_factor。合計 1STRUCT の中に weight FLOAT64。持たないと同じ二重計上が起きるそのまま残る。物理設計ではなく意味の問題
グループキー組合せを重複排除してグループ表を作り、ファクトはグループキーを持つ（DT#142）不要。ARRAY はファクトやディメンションの行に直接ぶら下がる組合せの数が少なく再利用されるなら、グループ化はストレージではなく一貫性のために効く
BI からの見え方ブリッジは普通の表。BI ツールが素の JOIN で扱える繰り返しフィールドを「ディメンションとして直接選べるか」は BI ツールごとに違う。直接選べないツールでは、カスタムクエリで UNNEST して平坦化するか、モデリング層（LookML 等）で展開済みビューを先に定義することになるここが最大の差。セルフサービス BI を前提にするならブリッジが強い
更新希望職種が 1 件変わればブリッジの 1 行を差し替える配列は部分更新できない。1 要素の変更で dim_member の行全体を書き直す。SCD2 と組むと版が丸ごと 1 本増える更新頻度が高い多値は ARRAY に向かない

階層側にも同じ対案がある。br_company_hierarchy の代わりに dim_company へ祖先コードの ARRAY を持たせれば「C001 傘下か」は UNNEST なしの IN UNNEST(…) 一発で判定できる。ただしこれは Kimball の pathstring と同じ性質で、depth を使ったレベル別の集計や代替階層の差し替えは表現できない。正典では br_company_hierarchy をブリッジとして持つ。

5. BigQuery + dbt での実装

(a) br_member_desired_job_category と weighted report

-- models/marts/br_member_desired_job_category.sql
{{ config(materialized='table') }}

WITH weighted AS (

    SELECT
        member_id,
        job_category_code,
        priority,
        -- グループ内の合計が 1 になる配分比。DWT の weighting factor
        SAFE_DIVIDE(1.0, COUNT(*) OVER (PARTITION BY member_id)) AS weighting_factor
    FROM {{ ref('stg_careervoice__member_desired_job_categories') }}

)

SELECT
    m.member_key,
    jc.job_category_key,
    w.priority,
    w.weighting_factor
FROM weighted AS w
-- is_current で絞らない。dim_member の全 SCD2 版に希望職種を展開しておくと、
-- ファクト側の sent 時点 member_key と直接結合できる（下の weighted report 参照）
INNER JOIN {{ ref('dim_member') }} AS m
    ON w.member_id = m.member_id
INNER JOIN {{ ref('dim_job_category') }} AS jc
    ON w.job_category_code = jc.job_category_code

ここでは member_key がグループキーを兼ねる。会員ごとに希望職種のグループが 1 つしかないので、DT#142 の「組合せを重複排除してグループを作る」段は利得を生まない。

ここで 1 つ判断している。DT#142 の分類では、関係が時間変化するなら時間可変ブリッジ（有効/失効タイムスタンプ付き）が要る。しかしソースの member_desired_job_categories は updated_at しか持たず、過去の希望職種は残っていない。

取れない履歴は作れないので、現在値の希望職種を dim_member の全版に複製する静的ブリッジにする（正典もこの展開を明記している）。代償は「2026-06 時点で M002 が何を希望していたか」に答えられないこと。答える必要が出たらソース側にスナップショット（snap_*）を足すのが先で、ブリッジの形を変えるのは後。

-- 希望職種別のスカウト送信数。impact と weighted を 1 クエリで並べる
SELECT
    jc.level2_name,
    SUM(f.scout_count)                       AS scout_count_impact,
    SUM(f.scout_count * b.weighting_factor)  AS scout_count_weighted
FROM {{ ref('fct_scout') }} AS f
INNER JOIN {{ ref('br_member_desired_job_category') }} AS b
    ON f.member_key = b.member_key
INNER JOIN {{ ref('dim_job_category') }} AS jc
    ON b.job_category_key = jc.job_category_key
WHERE f.sent_date BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
GROUP BY jc.level2_name

scout_count_impact は「この職種を希望する会員に届いたスカウト数」で、列の合計は総送信数を超える。scout_count_weighted は合計が総送信数に一致する。この 2 列は必ず並べて出す。片方だけを出すダッシュボードは、読み手が勝手にもう片方だと思い込む。

# models/marts/schema.yml
version: 2

models:
  - name: br_member_desired_job_category
    description: |
      会員の希望職種（多値）をファクトに結ぶブリッジ。DT#142 の静的ブリッジ。
      weighting_factor は member_key 内で合計 1。重みなしで結合すると二重計上になる。
    columns:
      - name: member_key

          - relationships:

              field: member_key
      - name: job_category_key

      - name: weighting_factor
        data_tests:
          - not_null
          - dbt_utils.accepted_range:

              max_value: 1
    data_tests:
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [member_key, job_category_key]

-- tests/assert_desired_weights_sum_to_one.sql
-- 合計 1 はブリッジの定義そのもの。壊れたら weighted report が静かにずれる
SELECT
    member_key,
    SUM(weighting_factor) AS total_weight
FROM {{ ref('br_member_desired_job_category') }}
GROUP BY member_key
HAVING ABS(total_weight - 1.0) > 1e-9

(b) br_company_hierarchy を再帰 CTE で作る

-- models/marts/br_company_hierarchy.sql
{{ config(materialized='table') }}

WITH RECURSIVE

base AS (

    SELECT
        company_id,
        parent_company_id
    FROM {{ ref('stg_careervoice__companies') }}

),

flags AS (

    SELECT
        b.company_id,
        b.parent_company_id IS NULL AS is_root,
        NOT EXISTS (
            SELECT 1 FROM base AS c WHERE c.parent_company_id = b.company_id
        ) AS is_leaf
    FROM base AS b

),

paths AS (

    -- 自己参照行。depth 0。これが無いと「C001 グループ」に C001 自身が入らない
    SELECT
        company_id AS ancestor_company_id,
        company_id AS descendant_company_id,
        0          AS depth
    FROM base

    UNION ALL

    -- 1 段ずつ下る。C001 → C003 が depth 1
    SELECT
        p.ancestor_company_id,
        b.company_id AS descendant_company_id,
        p.depth + 1  AS depth
    FROM paths AS p
    INNER JOIN base AS b
        ON b.parent_company_id = p.descendant_company_id

)

SELECT
    anc.company_key AS ancestor_company_key,
    des.company_key AS descendant_company_key,
    p.depth,
    fd.is_leaf,   -- 子孫側が末端か
    fa.is_root    -- 祖先側がグループの頂点か
FROM paths AS p
-- 祖先は「現在の」グループ定義で辿る
INNER JOIN {{ ref('dim_company') }} AS anc
    ON p.ancestor_company_id = anc.company_id
   AND anc.is_current
-- 子孫は全 SCD2 版に展開し、ファクトのイベント時点 company_key と直結できるようにする
INNER JOIN {{ ref('dim_company') }} AS des
    ON p.descendant_company_id = des.company_id
INNER JOIN flags AS fd ON p.descendant_company_id = fd.company_id
INNER JOIN flags AS fa ON p.ancestor_company_id = fa.company_id

BigQuery の WITH RECURSIVE は、再帰項が CTE をちょうど 1 回参照すること、UNION ALL で基底項と繋ぐこと、再帰項に集計関数・分析関数・LIMIT を置かないことを要求する。反復上限は 500 で、それを超えるとエラーで止まる。C001 の親を C003 にして循環を作ってしまった場合も、新しい行が出続けて 500 反復に達しエラーで落ちる。無限ループにはならない。

-- 「C001 グループのクチコミ数」。C001 自身 + C003 が 1 回ずつ数えられる
SELECT
    anc.name AS group_parent_name,
    SUM(r.review_count) AS review_count
FROM {{ ref('fct_review') }} AS r
INNER JOIN {{ ref('br_company_hierarchy') }} AS h
    ON r.company_key = h.descendant_company_key
INNER JOIN {{ ref('dim_company') }} AS anc
    ON h.ancestor_company_key = anc.company_key
WHERE anc.company_id = 'C001'
  AND anc.is_current
GROUP BY anc.name

木構造なら子孫から祖先への経路は 1 本なので、祖先を 1 社に固定すればファクト行は 1 回しか数えられない。共有所有（1 社が 2 つの親を持つ）を許した瞬間にこれは崩れ、多値ブリッジと同じ重み付けが必要になる。正典では companies.parent_company_id が単一なので木のまま。

        c.name                                          AS sender_name,
        i.name                                          AS company_industry,   -- company 固有
        CAST(NULL AS STRING)                            AS agency_tier,        -- agent 固有 → NULL
        c.dbt_valid_from                                AS valid_from,
        IFNULL(c.dbt_valid_to, TIMESTAMP '9999-12-31')  AS valid_to
    FROM {{ ref('snap_companies') }} AS c
    LEFT JOIN {{ ref('stg_careervoice__industries') }} AS i
        ON c.industry_code = i.industry_code

),

agent_senders AS (

    SELECT
        'agent'                                         AS sender_type,
        a.agent_id                                      AS sender_id,
        a.name                                          AS sender_name,
        CAST(NULL AS STRING)                            AS company_industry,
        ag.tier                                         AS agency_tier,
        a.dbt_valid_from                                AS valid_from,
        IFNULL(a.dbt_valid_to, TIMESTAMP '9999-12-31')  AS valid_to
    FROM {{ ref('snap_agents') }} AS a
    INNER JOIN {{ ref('stg_careervoice__agencies') }} AS ag
        ON a.agency_id = ag.agency_id

),

unioned AS (

    SELECT * FROM company_senders
    UNION ALL
    SELECT * FROM agent_senders

)

SELECT
    -- SCD2 なので、ハッシュの入力に版を識別する valid_from を必ず入れる（03回の結論）。
    -- 生成方式は 03回の判断（FARM_FINGERPRINT の INT64）に従う
    FARM_FINGERPRINT(
        CONCAT(sender_type, '|', sender_id, '|', CAST(valid_from AS STRING))
    ) AS scout_sender_key,
    sender_type,
    sender_id,
    sender_name,
    company_industry,
    agency_tier,
    valid_from,
    valid_to,
    valid_to = TIMESTAMP '9999-12-31' AS is_current
FROM unioned

UNION ALL の両側で列の順序・型を完全に揃えるのがこのパターンの全部で、固有属性は「無い側で CAST(NULL AS …)」と書く。SELECT * で繋ぐなら位置が意味を持つので、列を足すときは両側を同時に直す。

キーの入力に valid_from を入れるのは省略可能なオプションではない。正典で dim_scout_sender は SCD2 なので、自然キー（sender_type, sender_id）だけでハッシュすると同じ送信主体の全版が同一の scout_sender_key を持つ。fct_scout を結合した瞬間に 1 スカウトが版の数だけ増え、§2(a) と同じ二重計上が supertype 側で起きる。

agency_tier は現在値を引いている。エージェンシーの tier 変更でも版を作るなら、そちら側も snapshot して版に展開する（05回）。

属性の NULL 率が高い supertype は、BI で「業種で絞ると agent 発のスカウトが全部消える」事故を生む。防ぐのは列名の規律で、片方にしか無い属性は名前に出自を残す（company_industry、agency_tier）。共通属性のつもりで industry と名付けると、読み手は両方に入っていると思う。

固有属性が 2 列を超えて増え、種別ごとにメジャーまで違ってくるなら、Kimball の core / custom に分けて subtype 表を別に持つ。判断の境界は §6 の 3 番目の表。

(d) ARRAY 版の dim_member と UNNEST クエリ

-- models/marts/dim_member_with_desired.sql
-- ARRAY を内包する対案。dim_member に列を 1 本足すだけで、本体は一切変えない
WITH weighted AS (

    SELECT
        member_id,
        job_category_code,
        priority,
        SAFE_DIVIDE(1.0, COUNT(*) OVER (PARTITION BY member_id)) AS weight
    FROM {{ ref('stg_careervoice__member_desired_job_categories') }}

),

desired AS (

    SELECT
        member_id,
        ARRAY_AGG(
            STRUCT(job_category_code AS code, priority, weight)
            ORDER BY priority
        ) AS desired_job_categories
    FROM weighted
    GROUP BY member_id

),

member_versions AS (

    -- 05回の dim_member をそのまま読む。版の畳み込み（同内容の連続版をまとめる）、
    -- deleted_at の除外、member_key = FARM_FINGERPRINT(member_id + '|' + valid_from)
    -- は 05回で済んでいる。ここでは再現も再計算もしない
    SELECT
        member_key,
        member_id,
        -- 属性列（birth_year, prefecture, region, …）は省略
        valid_from,
        valid_to,
        is_current
    FROM {{ ref('dim_member') }}

)

SELECT
    m.*,
    -- 希望を登録していない会員は NULL ではなく空配列。クエリ内では NULL 配列と
    -- 空配列は別値なので、下流で取り違えないようここで揃える
    IFNULL(
        d.desired_job_categories,
        ARRAY<STRUCT<code STRING, priority INT64, weight FLOAT64>>[]
    ) AS desired_job_categories
FROM member_versions AS m
LEFT JOIN desired AS d
    ON m.member_id = d.member_id

-- (a) と同じ問いを ARRAY 版で。ブリッジへの JOIN が UNNEST に置き換わる
SELECT
    jc.level2_name,
    SUM(f.scout_count)            AS scout_count_impact,
    SUM(f.scout_count * d.weight) AS scout_count_weighted
FROM {{ ref('fct_scout') }} AS f
INNER JOIN {{ ref('dim_member_with_desired') }} AS m
    ON f.member_key = m.member_key
CROSS JOIN UNNEST(m.desired_job_categories) AS d
INNER JOIN {{ ref('dim_job_category') }} AS jc
    ON d.code = jc.job_category_code
WHERE f.sent_date BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
GROUP BY jc.level2_name

member_key は 05回の dim_member のものをそのまま持ち越す。版の数も変わらない——M001 は snap_members では 3 版だが 05回の畳み込みを経て dim_member で 2 行になっており、この対案でも 2 行のままである。fct_scout.member_key（送信時点の版）との突き合わせが (a) と同じに保たれるのはこのためで、キーを作り直すとここが崩れる。

結果は (a) と同じ。差は 3 点ある。

  1. CROSS JOIN UNNEST は空配列の行を落とす（ブリッジへの INNER JOIN と同じ挙動）。希望職種を登録していない会員のスカウトも数えたいなら LEFT JOIN UNNEST(…) AS d にする。
  2. weight は STRUCT の中にあるので、書き忘れの結果は (a) と同じ二重計上になる。ARRAY にしても重みの規律は緩まない。
  3. この UNNEST を誰が書くかが変わる。BI のセルフサービス画面が繰り返しフィールドを直接扱えないなら、カスタムクエリかモデリング層のどちらかで、誰かが先に平坦化しておく必要がある。

6. 判断基準

多値: ブリッジか ARRAY か

多値の個数の分布BI の UNNEST 可否更新頻度選択理由
上限が仕様で決まっている（希望職種は priority 1..3）セルフサービス BI が直結する（UNNEST を書かせられない）低ブリッジ素の JOIN で見える。CareerVoice の決定はこれ
同上クエリは dbt / モデリング層が書く低ARRAY結合が 1 つ減り、行数が増えない
数十〜数百（閲覧履歴、応募履歴）問わない問わない別ファクト表更新頻度ではなくカーディナリティで落ちる。ガイドが明示的に外す形で、ディメンションが肥大する
個数が可変で頻繁に変わる問わない高ブリッジARRAY は部分更新できず、1 要素の変更で行全体を書き直す
関係自体が時間変化し、過去の状態を問う問わない問わない時間可変ブリッジ有効/失効タイムスタンプを持てるのはブリッジだけ（DT#142）

階層: 平坦化かブリッジか

深さの分布問いの形選択理由
固定。各レベルに合意された名前がある「level2 別の応募数」固定深さ位置属性最速・最も分かりやすい。条件を満たすなら常にこれ
1〜3 で幅が狭い（job_categories）同上平坦化 + 終端埋めdim_job_category。level3_name を level2_name で埋め、leaf_level に実際の終端を残す（DT#43）
不定。買収で伸びる（企業グループ）「C001 配下の全社を合計」階層ブリッジ全経路 1 行。depth でレベル別にも切れる
不定だが「祖先の集合」しか要らない「C001 傘下かどうか」pathstring / 祖先 ARRAYブリッジより軽い。代替階層の差し替えは捨てる
共有所有（1 社が複数の親を持つ）任意ブリッジ一択クエリ時に親子表を辿るだけでは解けず（pathstring も同じ）、あり得る全経路を持つ表が要る。再帰 CTE は §5(b) と同じくその生成手段としては使える。経路が複数になるので重み付けも要る
階層自体が時間変化する「2026-01 時点のグループで集計」ブリッジ + 有効期間祖先-子孫の行に valid_from/valid_to。§7(b) で扱う

異種: supertype か分離か

共通属性の割合メジャー選択理由
高い。固有は 1〜2 列（dim_scout_sender: 固有は company_industry と agency_tier のみ）同じsupertype 1 本NULL 列 2 本の代償で、ファクトの FK が 1 本になり「送信主体別」が 1 クエリになる
半々同じsupertype + subtype共通属性の supertype で横断集計、固有は subtype 表へ（core / custom）
低い。属性もメジャーも粒度も違う違うファクトごと分離無理に畳むと「数百の互換しない属性」の失敗形になる
任意任意2 本の FK + -1 は採らない種別が増えるたびに列とクエリが増える。§2(c)

7. 演習

(a) reviews に「タグ（複数）」が付いたら fct_review にどう持つか

クチコミに「残業少なめ」「リモート可」のような多値タグが付くようになった。fct_review の粒度は「1 行 = 投稿された 1 クチコミ」で変えない。タグをどこに置くか。

解答例

命名規約 br_* に従うブリッジを 1 本置く（fct_review に review_id は退化ディメンションとして既にあるので、ブリッジはそれで結べる。表名は正典に追加が要る）。判断基準の 1 番目の表を当てる。

軸この場合効き方
個数の分布1 クチコミに数個。上限は運用で決まるブリッジ・ARRAY ともに可
BI の UNNEST 可否クチコミのタグ別集計はセルフサービスで見たい典型ブリッジに寄る
更新頻度審査時に確定してほぼ変わらない（DT#142 の静的ブリッジ）どちらでも可

重みは持つが、既定の見せ方は impact。「残業少なめのタグが付いたクチコミは何件か」が主な問いで、合計が総クチコミ数と一致する必要はない。

ただし weighting_factor の列自体は作っておく。タグ別の件数を合計して総クチコミ数と突き合わせるときと、タグ展開後の全行をプールして 1 本の平均を出すときに、重みが無いと 3 タグのクチコミが 3 回数えられるため。タグ 1 つの中での平均には掛けない（掛けると多タグのクチコミだけが不当に軽くなり、答えが変わる）。

fct_review 側に ARRAY<STRING> で持たない理由がもう 1 つある。fct_review はパーティション付きのファクトで行数が最も伸びる表であり、タグの付け直し（審査のやり直し）が起きるたびにファクト行を書き換えることになる。ブリッジなら差分はブリッジ側の数行で済む。

(b) C003 が C001 から離脱したら br_company_hierarchy はどうなるか

2026-09-01 に C003（ヒノデ物流）が C001（アオゾラ商事）グループから離脱し、companies.parent_company_id が NULL になった。§5(b) の実装のまま dbt build したら何が起きるか。SCD の観点で答える。

解答例

起きること: 過去のクチコミが遡って C001 グループから消える。§5(b) は base をソースの現在値から作り直す全件再構築なので、離脱後の実行では C001 → C003（depth 1）の行が消える。「C001 グループのクチコミ数」を 2026-08 の期間で出しても、C003 分が入らなくなる。階層が Type 1 として振る舞っている。

ただし完全には消えない。dim_company は正典で Type 2（name のみ Type 1）なので、parent_company_id の変化で C003 に新しい版が生まれる。§5(b) は子孫側を全 SCD2 版に展開しているので、離脱前の C003 の版キーは C001 の子孫として残せる余地がある。実装上そうするには、再構築を「現在値からの全件再生成」ではなく「版ごとの親を辿る」形に変える必要がある。

主に答えたい問い設計代償
「当時の C001 グループの実績」ブリッジに valid_from / valid_to を持ち、集計時に sent_date 等で as-of 制約する（DT#142 の時間可変ブリッジ）全クエリに時点条件が必要。忘れると行が重複する
「今の C001 グループの過去実績」（M&A の効果測定）現在値からの全件再生成のまま（§5(b)）過去のレポートの数字が実行日で変わる
両方時間可変ブリッジを正とし、「現在のグループ」は is_current な祖先だけを見るビューを別に置くブリッジ 1 本ぶんの運用が増える

正解は 1 つではない。判断基準の 2 番目の表の最終行「階層自体が時間変化する」に当たるかどうかは、離脱・買収がどれくらいの頻度で起きるかで決まる。年に数件なら時間可変ブリッジのコストは正当化される。

(c) fct_placement.agent_key が -1 のとき dim_agent に -1 行を持つべきか

正典の fct_placement は agent_key を applications.scout_id → scouts.sender_agent_id で解決し、辿れなければ -1 を入れる。dim_agent に -1 行を作るのと、dim_scout_sender に寄せて統一するのと、どちらか。

解答例

まず -1 の意味を確定させる。fct_placement の粒度は「1 行 = 1 入社（エージェント経由）」なので、agency_key は必ず埋まる。埋まらないのは agent_key のほうで、その意味は「直接応募」ではなく「仲介した担当者を特定できない」である。

source_channel が agent_referral でスカウトを経由していない入社がこれに当たる。意味が「該当なし」なのか「不明」なのかで表示名が変わるので、ここを曖昧にしたまま -1 行を作ってはいけない。

dim_agent に -1 行を持つ。DT#43 の「ディメンションの外部キーに NULL を置かない」がそのまま効く。-1 行の agent_name には「担当者不明」を入れる。

これが無いと、fct_placement と dim_agent の INNER JOIN でこれらの入社が静かに消える。消えたことは画面に出ない（§2(b) と同じ壊れ方）。

ただし、この問いには正典側の先回りがある。dim_agency（dim_agent の縮約ディメンション）が用意されており、fct_placement は agency_key も持つ。担当者別に切れない分析は最初から dim_agency を主軸にするのが正しく、agent_key = -1 は「担当者別のドリルダウンでは不明として1 行に集まる」という副次的な扱いになる。-1 行を置くことと、-1 が多い軸を主軸にしないことは別の判断で、両方要る。

dim_scout_sender には統一しない。DT#3 の「部門ではなくビジネスプロセス」がそのまま効く。dim_scout_sender の意味は「スカウトを送った主体」で、値域には企業が入る。fct_placement.agent_key の意味は「入社を仲介した担当者」で、企業は入らない。

別プロセスの別の役割であり、畳むと「送信主体別の入社数」という、企業側の行が常に空になる軸ができる。判断基準の 3 番目の表の第 3 行「属性もメジャーも粒度も違う → 分離」。

同じ担当者が dim_agent と dim_scout_sender の両方に出る重複は許容する。dim_scout_sender の自然キーは (sender_type, sender_id) なので agent_id から辿れる。コンフォームドディメンションとして共有すべきなのは dim_agent のほうで、dim_scout_sender はスカウトプロセス専用の supertype と割り切る。

8. 参考: 手元の基盤ではどうか

news_pipeline の summaries.tags は STRING の REPEATED 列で、まさに §4 の ARRAY 選択をしている。多値の個数が数個、更新はほぼ無し、クエリを書くのは BI ツールではなくアプリ側のコードなので、判断基準の 1 番目の表では ARRAY 行に当たる。妥当。

bq_client.get_favorite_tag_counts は , UNNEST(s.tags) AS tag で展開し COUNT(DISTINCT f.article_id) を数えている。これは impact report で、タグ列の合計はお気に入り記事数を超える（3 タグの記事は 3 タグそれぞれに 1 を寄与する）。採点のヒント用途としては impact が正しい。「タグ別の記事数の内訳」を出す場面が来たら、weight = 1 / ARRAY_LENGTH(tags) 相当が要る。

dbt_logs_analysis には多値も階層も無い。mart_url_performance の url_path は文字列 1 本で、実際には / 区切りの不揃い階層を内側に持っている。今後試せる種: url_path を SPLIT して祖先-子孫のブリッジを作り、「/api 配下の全パスの p95」を §5(b) と同じ形で出す。深さが不定なので、§6 の 2 番目の表ではブリッジ側に落ちる。
