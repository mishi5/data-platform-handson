ディメンションの設計

データマート設計 03 ／ 参照: DWT ch.3, ch.6, Kimball Dimensional Modeling Techniques (2013), Surrogate Keys (1998), Design Tip #5 #43 #46 #83 #100 #127 #164 ／ 再解釈: dbt Kimball (Neo 2023), ECM (Beauchemin 2023), FDE / スナップショット (Beauchemin 2018)

1. この回が決めること

ファクトの粒度が決まれば（01回）、次は「その粒度に何をぶら下げるか」だけが残る。この回で決めるのは2つ。サロゲートキーは BigQuery + dbt で本当に要るのか（結論: SCD2 の 5 ディメンションだけ）、そしてある属性を本体ディメンション・ミニ・ジャンク・退化・メジャーのどこに置くか。

CareerVoice のディメンションは正典で名前まで固まっているので、ここでは「なぜその形なのか」を技法名に紐付けて言語化する。

この回の決定
論点決定理由（詳細は §3–§6）
サロゲートキーを全ディメンションに振るか振らない。SCD2 の dim_member / dim_company / dim_agent / dim_agency / dim_scout_sender の 5 本だけKimball が SK(1998) で並べた理由のうち、BigQuery + 単一ソースで残るのは「1自然キーに複数行」だけ

fct_review が member_key を持たないのは技法の帰結ではなく、正典の固定判断（匿名性）だ。投稿者の属性は dim_review_attributes にジャンク化して落とす。つまりここではジャンクディメンションが匿名化装置を兼ねている。

ただし 30 行の粗い帯でも小規模企業では特定されうる（C002 の former/fulltime/1_3 が1人しか居ない場合）。会員×クチコミの結合が要る分析は int_review_member_link に隔離する。

2. どこで壊れるか

(a) 速く変わる属性を dim_member に Type2 で持つ

以下、規模は正典 §5 の想定規模（会員 300 万人、page_views 日次 2,000 万行）を使う。断定ではなく前提で、この回の判断のいくつかはこの桁に乗っている。

annual_income_band と job_change_intent を dim_member の Type2 属性にしたとする。M001 は 2026-06-15 に passive/400_600 → active/600_800 へ変わるので、この日に新しい member_key が発行される。壊れ方は3つ。

  • 行数: 転職意欲は求人を見た会員が数か月単位で切り替える。会員 300 万人 × 年2回でディメンションが年 600 万行ずつ伸びる。5年で 3,000 万行超のディメンションを、fct_page_view（日次 2,000 万行）に毎日結合することになる。
  • 会員数が二重計上される: SELECT COUNT(DISTINCT member_key) FROM fct_page_view は 6月の M001 を 2 人と数える。正しく数えるには member_id（耐久キー）で数え直す必要があり、「キーで数える」という素直な操作が使えなくなる。
  • ETL が範囲結合になる: イベント時点の版を引くために、fct_page_view のロードが毎回 valid_from <= viewed_at AND viewed_at < valid_to の範囲結合になる。日次 2,000 万行 × 3,000 万行の範囲結合は BigQuery でも重い。

正典の形（ミニディメンション）では (i) が消え、(ii)(iii) が桁で軽くなる。dim_member は 6/15 に行が増えない。dim_member_profile_mini も組合せ 15 通りのまま動かず、動くのは「ファクト行がどの1つを指すか」だけだ。

ただし(ii)(iii) は消えない。正典の dim_member は SCD2 のままで、M001 は current_company_id が変わる 8/1 に版が増えて member_key が2つになる。会員数は member_id（耐久キー）で数える必要が残り、イベント時点の版を引く as-of 結合も残る。

ミニが消すのは「速く変わる属性のせいで版が増える」分だけで、規模を桁で下げても現象そのものは残る（05回）。

(b) dim_date を作らず DATE 列で済ませる

fct_application_pipeline に applied_date DATE を直接置いた場合、次の食い違いが必ず起きる。

要件DATE 列だとどうなるかdim_date があるとどうなるか
年度（4月始まり）ある mart は EXTRACT(YEAR FROM applied_date)、別の mart は EXTRACT(YEAR FROM DATE_SUB(applied_date, INTERVAL 3 MONTH))。2026-03 の応募が 2025年度と 2026年度の両方に現れるdim_date.fiscal_year 一箇所。定義は1回だけ書かれる
営業日でのリードタイム祝日判定を各クエリの CASE に書く。2026-09-21 / 09-23 のように年ごとに動く祝日で必ずずれるdim_date.is_holiday_jp を COUNTIF するだけ
「内定月 × 応募月」のクロス集計7つの日付列それぞれに FORMAT_DATE を書く。列名の付け方がクエリごとに違う同じ dim_date を役割ごとに別名で結ぶ（ロールプレイング）。属性名は共通
未達マイルストーンNULL しか置けない → (c) へdate_key = -1、dim_date の既定行に落ちる

(c) 未達日付を NULL にして LEFT JOIN と COUNT がずれる（DT#43）

fct_application_pipeline は累積スナップショットなので、P001 のように 8/1 入社まで進んだ行と、7/20 の内定で止まっている行が同じ表に混在する。hired_date_key を NULL にすると:

-- 壊れる形 1: INNER JOIN が未入社の行を丸ごと落とす
SELECT d.year, COUNT(*) AS applications
FROM fct_application_pipeline AS f
INNER JOIN dim_date AS d ON f.hired_date_key = d.date_key
GROUP BY d.year;

-- 壊れる形 2: LEFT JOIN にすると行は残るが COUNT がずれる
SELECT COUNT(*) AS applications, COUNT(d.date_key) AS hired   -- 未入社の分だけ食い違う
FROM fct_application_pipeline AS f
LEFT JOIN dim_date AS d ON f.hired_date_key = d.date_key;

-- 壊れる形 3: 絞り込みを1つ足した瞬間に INNER JOIN と同じ結果に戻る
SELECT d.year, COUNT(*) AS applications
FROM fct_application_pipeline AS f
LEFT JOIN dim_date AS d ON f.hired_date_key = d.date_key
WHERE d.year = 2026        -- NULL になった行がここで静かに落ちる
GROUP BY d.year;

1本目は「2026年の応募数」を出したつもりで「2026年に入社した応募数」を返す。2本目は COUNT(*) と COUNT(d.date_key) が食い違い、集計関数の選び方で答えが変わる。3本目は絞り込みを1つ足しただけで INNER JOIN と同じ挙動に戻る（1本目を 2026 年で絞ったものと一致する）。

3つともエラーにならないのが最悪の性質だ。-1 行があれば INNER JOIN が常に成立し、恒等式 applications = still_open + hired_count がクエリの中で検算できる（§5 のロールプレイング例を参照）。

3. Kimball の原則

技法原典の定義使う条件
ディメンションサロゲートキー「主キーはソースの自然キーであってはならない。変化を追跡すると1つの自然キーに複数のディメンション行が生じるからだ」（Techniques, p.7）。1から順に振る単純整数1自然キーに複数行が生じる（＝SCD Type 2）。または自然キーが複数ソース由来で互換性がない
自然キー / 耐久キー版が増えても変わらないキー。「従業員の版が増えるにつれ複数のサロゲートキーがその従業員に結び付きうるが、耐久キーは決して変わらない」（Techniques, p.7）。CareerVoice では member_id / company_id / agency_id が耐久キーにあたるSCD2 のディメンションには必ず両方置く。Type 0/1 ならこれだけで足りる
退化ディメンション（DT#46）「ファクト表の中でディメンションキーとして機能するが、対応するディメンション表を持たない」。伝票番号・注文番号がその典型属性が全部他のディメンションに吸われ、主キーしか残らないとき。ディメンション表がファクト表とほぼ同じ速度で伸びていたら、見落とした退化ディメンションが潜んでいる（DT#46）
ロールプレイング「1つの物理ディメンションがファクト表から複数回参照され、それぞれが論理的に別の役割にリンクする」。各 FK は別のビューを参照し、属性列名を役割ごとに変えるべき（Techniques, p.9）同じディメンションを1ファクトから2回以上参照するとき。累積スナップショットは常にこれになる
ジャンクディメンション雑多な低カーディナリティのフラグ・指示子を1本にまとめる。「全属性値の直積である必要はなく、ソースデータに実際に出現する組合せだけを持てばよい」（Techniques, p.9）単独ではディメンションにする価値がないフラグが3つ以上あるとき
ミニディメンション（Type 4, DT#127）「属性群が急速に変化し、ミニディメンションへ切り出される。ミニディメンションは独自の主キーを持ち、本体とミニの両方の主キーがファクトに入る」（Techniques, p.12）。連続値は帯にしてから入れる。本体にも現在のミニキーを Type1 で埋めると Type 5 だが、正典は採らない（dim_member にミニキーを持たせると時点解決の経路が2本になる）本体ディメンションが大きく（数百万行）、その一部の属性が速く変わる／頻繁に絞り込みに使われるとき
監査ディメンション（DT#164）「ファクト行が ETL のバックルームで作られるとき、その時点で分かっている ETL 処理メタデータを持つ監査ディメンション行を作ると役に立つ」。ETL コードの版や実行時刻を入れる行がいつ・どの版のコードで作られたかを BI 側からドリルダウンしたいとき（＝いつでも）
NULL 外部キー「ファクト表の外部キーに NULL があってはならない。参照整合性違反を自動的に引き起こす。NULL 外部キーの代わりに、ディメンション表が未知または該当なしを表す既定行（とサロゲートキー）を持たなければならない」（Techniques, p.4）常に。ただしメジャーの NULL は残してよい（集計関数が正しく扱う）

サロゲートキーが要る理由（SK, 1998）と、この題材での成否

Kimball は 1998 年の Surrogate Keys でサロゲートキーの理由を並べた。内訳は「本番系があなたのキーを踏む」6通り ＋ 未知値の符号化 ＋ 4バイト整数による容量削減 ＋ 結合性能の計9つ。「本番系はパージしたキーを再利用しうるが、あなたはまだそれを保持している」「本番系はキー空間を再圧縮しうる」「4バイト整数の美点は 20 億以上の値を表現できることだ」。

いずれも1998年の行指向 RDBMS と複数の業務システムを前提とした主張である。最後の結合性能の理由については Kimball 自身が留保をつけている——「サロゲートキーについて私が思いつく最後の理由は、強く疑ってはいるが証明したことのないものだ。大きく醜い自然キーや複合キーを、美しく引き締まった整数のサロゲートキーで置き換えれば、結合性能は上がるはずだ」。

SK (1998) の理由CareerVoice + BigQuery で成立するか
1. 本番系がパージ済みキーを再利用する✗ members / companies は論理削除（deleted_at）で、member_id は再利用されない
2. 本番系が誤ってキーを再利用する✗ 同上。CDC で複製している以上、起きたらソース側の障害として扱う
3. 本番系がキー空間を再圧縮する（全顧客キーの再割当）✗ Datastream の CDC は OLTP の PK をそのまま複製する。再割当が起きたら CDC 自体が破綻するので、DWH のキー設計で吸収する話ではない
4. 本番系が記述を上書きしてもキーは変えない（＝SCD）✓ これだけが残る。 dim_member, dim_company, dim_agent, dim_agency, dim_scout_sender の 5 本
5. 本番系がキー書式を一般化する（整数→英数字）✗ 起きたら staging を直して marts を再構築する。BigQuery ではフルリビルドが現実的な選択肢になった
6. 買収による複数ソースシステムの統合✗ ソースは src_careervoice 単一。将来 M&A で2つ目が来たらこの行は ✓ に変わる
7. 未知値の符号化（誰か分からない / 特定がまだ / 取得に失敗 / そもそも該当なし）△ 既定行は要るが、それはキーの型ではなく値の約束（-1）の問題。自然キーが STRING なら '-1' で足りる
8. 4バイト整数による容量削減✗ 列指向＋圧縮。M001 のような短い STRING は INT64 より小さいことすらある。差は測ってから決める話で、設計を左右する理由ではない
9. 結合性能（「大きく醜い自然キー・複合キーを整数のサロゲートキーに置き換えれば結合性能は上がるはずだ」）△ 原典自身が「強く疑ってはいるが証明したことはない」と断っている。BigQuery でもシャッフル量の差として実在するが（§5(d) の結合コスト行）、M001 程度の短い STRING では測定に埋もれる。測ってから決める

DT#100「キーは単純に」

DT#100 は「SCD2 のキーを、固定キー（自然キーと 1:1）＋日付範囲の組合せにするのは明確に間違いだ」と言い切る。理由は9つ挙がる。この題材に効くのは次の3つ。

(1) 複合フィールドの結合は性能を損なう——「最良の結合性能は、ディメンションとファクトの間を単一フィールドの整数キーで結ぶことで得られる」。(2) 日付範囲は隙間なく連続していなければならないが、それは「正しくやるのが難しく、しばしばほぼ不可能」だ。ある行の valid_to と次の行の valid_from が一致すると、その境界の瞬間に BETWEEN が2行を返す。

(3) 「単純なサロゲートキーを使えばこの反論は消える。ディメンション行とファクト行の正しい対応が ETL 時に解決されるからだ」。

この主張は現在も生きている。ただし「単一列の整数キー」であることが要点で、「1から順に採番すること」ではない。DT#100 が禁じているのは、クエリ時に日付範囲の制約を書かせる設計だ。

FARM_FINGERPRINT(member_id || '|' || valid_from) は連番ではないが、単一列 INT64 であり、対応付けは ETL（＝dbt モデル）で解決されている。DT#100 の中心の要件（単一列・整数・ETL 時に対応付けを解決）は満たす。 残る理由9（「ソースシステム由来の自然キーの中身への明示的な依存は、複数ソース統合の課題に対応できない」）はハッシュの入力が自然キーである以上まともに当たるが、ソースが src_careervoice 単一である限り効かない——2つ目のソースが来たら、上の表の6行目と一緒に ✓ に変わる。

ミニディメンションの設計

ミニディメンションを作る手順は3段。

  1. 本体ディメンションから速く変わる属性を選ぶ
  2. 連続値は帯にする
  3. 組合せにサロゲートキーを振る

(2) について DT#127 は「サロゲートキー列を持つ新しい表を作り、本体ディメンションの列の SELECT DISTINCT で埋めるだけだ」と書くが、これは属性が既に帯になっていることを前提にしている。年収 4,850,000 円を生のまま入れると行数が会員数と同じになり、ミニにする意味が消える。

行数は属性値の組合せ数で決まり、会員数にもイベント数にも依存しない。ここが本体ディメンションとの決定的な違いだ。

CareerVoice では帯化がソース側で既に済んでいる（members.annual_income_band が lt400〜ge1000 の5値、job_change_intent が3値）。だから dim_member_profile_mini の組合せは 15 通りに固定される。ソースが生の年収を持っていたら、帯の切り方こそがこの回の最大の設計判断になっていた。

DT#127 の但し書き: 「顧客属性がファクトイベントを伴わずに変化しうる場合、これは変化の完全な履歴を捉えないかもしれない」。M001 が 6/15 に active へ変わっても、その後スカウトも閲覧も発生しなければ、その変化はどのファクト行にも刻まれない。完全な履歴が要るならファクトレスファクト表を別に置く——ミニディメンションは「イベント時点の属性」を安く持つ技法であって、属性履歴の保存装置ではない（05回）。

4. 現代の再解釈

dbt Kimball（Jonathan Neo, 2023）— キーの作り方は変わり、要否は変わらない

この記事はサロゲートキーの作り方を3つに整理する。ハッシュ（md5(key_1, key_2, key_3)）、連番（row_number()）、連結（concat(key_1, key_2, key_3)）。そのうえでハッシュを「おそらく最も簡単な方法」として dbt_utils.generate_surrogate_key() を推す。

利点として挙げるのは「ファクト表のサロゲートキーを生成するときにディメンション表との結合を行う手間が省ける」こと。

変わったのは作り方だ。連番が使えなくなった——BigQuery には IDENTITY もシーケンスもなく、ROW_NUMBER() は再実行のたびに値が変わりうる（＝冪等でない／09回）。Kimball の「1から順に振る単純整数」は、採番機構を持つ RDBMS の前提だった。

決定的ハッシュはこの穴を埋める。しかも ETL 時にディメンションを引く必要がないので、ファクトとディメンションを並列に構築できる。

変わっていないのは要否の判断のほうだ。記事のコードは generate_surrogate_key(['stg_product.productid']) のように自然キー1列をハッシュしている。これは自然キーの再符号化であって、§3 の表の9つの理由を1つも満たさない。

M001 を -5137... に置き換えても、再利用も再割当も統合も起きない題材では可読性を失うだけだ。ハッシュがサロゲートキーになるのは、入力に版を識別する要素（valid_from）が入るときだけだ。これがこの回の中心的な結論である。

ECM（Maxime Beauchemin, 2023）— ディメンションに指標を持たせる

Beauchemin は自らを「Ralph Kimball の弟子」と呼びつつ、「ディメンショナルモデルを使いながら一群の指標をエンティティの隣に並べるのは厄介だ」と述べ、指標をディメンションの中に入れることを提案する。「Ralph Kimball ならディメンション表に多くの指標を持ち込むことに眉をひそめるところだが、エンティティ中心のアプローチはむしろそうすることを推奨する」。時間軸は 7d_visits / 28d_visits のような時間窓付き指標の列で扱う。

この回のディメンション（dim_member, dim_company）は Kimball 側に置く。属性だけを持ち、指標は持たない。ECM 風の拡張は agg_company_entity（review_count_total, avg_overall_score_90d, mrr …）に隔離してあり、08回で扱う。

ディメンションと集約エンティティを別テーブルにするのが、この題材での折衷である。理由は再集約可能性で、avg_overall_score_90d のような窓付き平均は他の粒度へ持ち上げられないため、ディメンションに置くと「ディメンションで絞ってからファクトを足す」という基本操作が壊れる（04回）。

Kimball が指標をディメンションに置くのを嫌うのは、ディメンションが「絞り込みとグループ化の対象」でファクトが「計測結果」という役割分担（DWT ch.1）を守るためだ。ECM はこの分担を意図的に崩す。

ECM がもう一方で推すのがディメンションの日次フルスナップショットだ。「ディメンションの完全なスナップショットを毎日保持する……ポイントインタイムのクエリ・比較が容易になる」。正典にはこれが dim_member_daily（1行 = 1会員 × 1日）として置かれている。

3つの手法を並べる。

手法行数（会員 300 万人・1年）as-of の書きやすさファクト結合
速く変わる属性まで本体を Type2（§2(a) の失敗形）年 +600 万行（変化回数依存）範囲結合が要る版で分裂した巨大ディメンションに結合
ミニディメンション（正典 dim_member_profile_mini、この回）組合せ 15 通り（固定）ファクトが既に時点の member_profile_mini_key を持つので不要15 行への結合＝実質ブロードキャスト
ECM / FDE の日次スナップショット（正典 dim_member_daily、05回）約 11 億行/年（300万 × 365）。ただし partition_by=snapshot_date ＋ require_partition_filter=true なので1クエリのスキャンは1日分 ≒ 300 万行に閉じるWHERE snapshot_date = ... だけ。最も簡単日付で絞ってから結合

スナップショットは「分析者が書く SQL の簡単さ」を、ミニディメンションは「ファクト結合の安さ」を買う。正典は両方を定義しており、どちらを主経路にするかは 05回で決める。 日次 2,000 万行の fct_page_view に毎日結合するのはミニの側で、dim_member_daily は会員断面の時系列分析（属性が変わった前後の行動差）用だ。

同じ属性を2経路で持つので、dim_member_daily.member_profile_mini_key がミニ側と一致することが整合条件になる。トレードオフは保管コスト対 SQL の簡単さで、行数そのものではない（require_partition_filter がスキャンを1日分に閉じるため）。SCD2 と日次スナップショットの選択そのものは 05回で扱う。

SELECT
    -1                    AS date_key,
    CAST(NULL AS DATE)    AS full_date,
    '未到達'              AS date_label,
    CAST(NULL AS INT64)   AS year,
    CAST(NULL AS INT64)   AS quarter,
    CAST(NULL AS INT64)   AS month,
    CAST(NULL AS INT64)   AS iso_week,
    '未到達'              AS day_of_week,
    FALSE                 AS is_holiday_jp,
    CAST(NULL AS INT64)   AS fiscal_year

3点だけ補足する。

  • YYYYMMDD は「スマートキー」の唯一の例外。DT#5（2000年）は時間ディメンションのキーについて「時間ディメンションのキーはアプリケーション上の意味を持ってはならない。ただの整数であって、計算に使ってはいけない」と書いていた。この立場は 2013 年の Techniques で明示的に緩められている: 「パーティショニングを容易にするため、日付ディメンションの主キーは YYYYMMDD を表す整数のように、より意味のあるものにしてよい」。
    ただし DT#5 の禁止の主旨は残っている——「絞り込みとグループ化は、スマートキーではなく日付ディメンションの属性に基づいて行うべきだ」。つまり WHERE date_key BETWEEN 20260601 AND 20260630 ではなく JOIN dim_date … WHERE d.year = 2026 AND d.month = 6 と書く。
  • 数値属性の -1 行は NULL のままにする。DT#43 と Techniques は「ディメンション属性の NULL は Unknown / Not Applicable の記述文字列で置き換えよ」と言うが、これは文字列属性の話だ。year に -1 を入れると年の並び順とレンジ集計が壊れる。文字列属性（date_label, day_of_week）に 未到達 を入れて、レポートの行見出しはそこから取る。
  • DT#5 は特殊行を4種類に分けていた（Normal / Not_Applicable / Hasnt_Happened_Yet / Corrupted）。正典は -1 の1行に畳んでいる。CareerVoice の未達はすべて「まだ起きていない」なので今は足りるが、「該当しない」（例: 応募せずに終わったスカウトの applied_date_key）と区別したくなったら -2 を足すことになる。

ロールプレイングと -1 の効き目

-- 分析クエリ（モデルではない）。
-- fct_application_pipeline は dim_date を 8 本の FK で参照する。
-- Kimball は「各 FK は別のビューを参照すべき」と言うが、
-- dbt では BI 側が別名を要求しない限りクエリ内の別名で足りる。
SELECT
    applied_d.fiscal_year,
    COUNT(*)                            AS applications,
    COUNTIF(hired_d.date_key = -1)      AS still_open,
    COUNTIF(hired_d.date_key <> -1)     AS hired_count
FROM {{ ref('fct_application_pipeline') }} AS f
INNER JOIN {{ ref('dim_date') }} AS applied_d ON f.applied_date_key = applied_d.date_key
INNER JOIN {{ ref('dim_date') }} AS hired_d   ON f.hired_date_key   = hired_d.date_key
GROUP BY applied_d.fiscal_year
ORDER BY applied_d.fiscal_year;

-1 行があるので INNER JOIN でも行が落ちない。結果として applications = still_open + hired_count が常に成立し、クエリ自身が検算になる。§2(c) の3つの壊れ方はこれで消える。

(b) dim_review_attributes — ジャンクを CROSS JOIN で作る

-- models/marts/dim_review_attributes.sql
{{ config(materialized='table') }}

WITH statuses AS (
    SELECT employment_status
    FROM UNNEST(['current', 'former']) AS employment_status
),
types AS (
    SELECT employment_type
    FROM UNNEST(['fulltime', 'contract', 'parttime']) AS employment_type
),
bands AS (
    SELECT years_of_service_band
    FROM UNNEST(['lt1', '1_3', '3_5', '5_10', 'ge10']) AS years_of_service_band
)

SELECT
    FARM_FINGERPRINT(CONCAT(
        s.employment_status, '|', t.employment_type, '|', b.years_of_service_band
    )) AS review_attributes_key,
    s.employment_status,
    t.employment_type,
    b.years_of_service_band
FROM statuses AS s
CROSS JOIN types  AS t
CROSS JOIN bands  AS b   -- 2 × 3 × 5 = 30 行（＝組合せ数）

dim_page_context も同じ形で、page_type(3) × device(3) × referrer_type(4) × is_unlocked(2) = 72 行になる。

Techniques は「ジャンクディメンションは全属性値の直積である必要はなく、ソースデータに実際に出現する組合せだけを持てばよい」と言う。ここで直積を採るのは、行数が 30 / 72 と小さく、キーが最初から全部確定するからだ。

SELECT DISTINCT 方式だと新しい組合せが初めて出現した日にキーが増え、増分ロードで組合せの検出漏れが起きるとファクトの FK が解決できなくなる。切り替えの目安は直積が数千行を超えるかどうか。属性が 10 個・各 5 値なら直積は 977 万行になり、そこでは SELECT DISTINCT 一択になる。

WITH income_bands AS (

ファクト側は「そのイベントが起きた時点の帯」を解決して member_profile_mini_key に入れる。fct_scout は member_profile_mini_key（送信時点）、fct_application_pipeline は応募時点、fct_page_view は閲覧時点。

(d) サロゲートキーの作り方 — 3案の比較

観点A. FARM_FINGERPRINT(CONCAT(...))B. dbt_utils.generate_surrogate_key(...)C. 自然キーをそのまま _key に
型INT64（8バイト、符号付き）STRING。BigQuery では TO_HEX(MD5(...)) に展開され 32 文字の16進ソースの型。member_id なら STRING 'M001'
衝突64bit。誕生日問題で 1,000 万行なら約 3×10⁻⁶、10 億行なら約 2.7%。ディメンションでは非現実的だが、ファクト表の主キーに使うなら要注意128bit MD5。10 億行でも 10⁻²¹ 台で実質ゼロ衝突なし（ソースが一意である限り）
可読性✗ -5137827...。BigQuery コンソールでの目視デバッグが効かない✗ 7c9e6679...。同上✓ M001 / J001 / 20260620 がそのまま読める。障害調査でこれが効く
結合コスト8バイト整数のハッシュ結合。最も安い32バイト STRING。fct_page_view 規模でシャッフル量が効いてくる短い STRING なら A とほぼ同等。長い自然キー（corporate_number 13桁など）だと不利
-1 既定行✓ そのまま -1 を使える△ '-1' か、センチネル文字列のハッシュ。後者は可読性ゼロ△ '-1'。自然キーの値空間と衝突しないことを確認する
落とし穴CONCAT は引数に NULL があると NULL を返し、キーが NULL になる。必ず IFNULL(x, '') で包む。区切り文字 '|' が値に現れないことも確認する区切りが - 固定。値に - を含む列が並ぶと ('a-b','c') と ('a','b-c') が同じキーになる。NULL は _dbt_utils_surrogate_key_null_ に置換されるソースがキー書式を変えたら marts を作り直す必要がある（§3 の表の5番目）

HAVING COUNT(*) <> 16   -- 組合せ 15 通り ＋ -1 の既定行

BigQuery には外部キー制約が無い（NOT ENFORCED の宣言はできるが検証されない）。relationships テストが参照整合性の実装であり、-1 行を作り忘れた瞬間にこれが落ちる。-1 行は設計であると同時にテストの前提条件だ。

ただしテストは物理設計に従属する。require_partition_filter=true のテーブルに素の generic テストを当てると、テストは失敗するのではなく実行自体が拒否される。直近3日だけを検査するのは全期間を諦めたのではなく、全期間の整合は dim_member_daily を作る側のモデルで担保するという分担だ（09回・10回）。

(e) dim_audit と dbt の invocation_id

正本は 10回（マクロ定義・dim_audit モデル・運用まで扱う）。ここでは呼び出し側の形、つまりディメンションとファクトが同じ実行をどう指すかだけを示す。

-- macros/audit_key.sql（正本は 10回）
{% macro audit_key(quality_flag='ok') -%}
    FARM_FINGERPRINT(CONCAT('{{ invocation_id }}', '|', '{{ quality_flag }}'))
{%- endmacro %}
-- models/marts/dim_audit.sql
-- 実行ごとに行が積まれる。full-refresh すると履歴が消えるので運用で禁じる
{{ config(materialized='incremental', unique_key='audit_key') }}

SELECT
    FARM_FINGERPRINT(CONCAT('{{ invocation_id }}', '|', flag)) AS audit_key,
    '{{ run_started_at.strftime("%Y%m%d%H%M%S") }}'            AS batch_id,
    'src_careervoice'                                          AS source_system,
    TIMESTAMP '{{ run_started_at.strftime("%Y-%m-%d %H:%M:%S") }}' AS loaded_at,
    '{{ invocation_id }}'                                      AS dbt_invocation_id,
    flag                                                       AS quality_flag
FROM UNNEST(['ok', 'estimated', 'suspect']) AS flag
-- models/marts/fct_scout.sql（抜粋）
SELECT
    CAST(FORMAT_DATE('%Y%m%d', DATE(s.sent_at, 'Asia/Tokyo')) AS INT64) AS sent_date_key,
    DATE(s.sent_at, 'Asia/Tokyo')                                       AS sent_date,  -- partition_by 用
    m.member_key,
    p.member_profile_mini_key,
    snd.scout_sender_key,
    IFNULL(s.job_posting_id, '-1')                                      AS job_posting_key,
    s.scout_id,        -- 退化ディメンション
    s.template_id,     -- 退化ディメンション
    1                  AS scout_count,
    {{ audit_key() }}                                                   AS audit_key
FROM {{ ref('stg_careervoice__scouts') }} AS s
...

invocation_id は dbt が実行ごとに発行する UUID で、Jinja コンテキストからそのまま参照できる。同じ実行の中で dim_audit とファクトが同じ式でキーを作るので、追加の結合なしに整合する。run_started_at は Python の datetime なので strftime で整形する。loaded_at に CURRENT_TIMESTAMP() ではなく run_started_at を使うのは、同一実行の全ファクト行が同じ時刻を指すようにするためである。quality_flag の値域 ok / estimated / suspect と、引数を SQL 式ではなく値で渡す形も 10回の正本に合わせている。

これが効く場面は具体的だ。「7月の入社数が前月比で 3 割落ちた」ときに、fct_placement を dim_audit と結んで batch_id 別に件数を見れば、業務の変化なのか特定バッチのロード漏れなのかが1クエリで分かる。Techniques が「環境変数はコンプライアンスと監査の目的で特に有用で、BI ツールがどの版の ETL でどの行が作られたかをドリルダウンできるようになる」と言うのはこのことだ。

6. 判断基準

属性が来たら、「変化速度」と「カーディナリティ」の2軸で置き場所を決める。第3の問い（その属性でグループ化するか）は同点のときのタイブレークに使う。

変化速度カーディナリティ置き場所理由CareerVoice の例
変わらない高（≒ファクト行数）退化（ファクトの列）ディメンション表を作ってもファクトと同速度で伸びるだけ（DT#46）review_id, scout_id, application_id, event_id, session_id
変わらない低（組合せ数 < 数千）ジャンクフラグごとにディメンションを作るとファクトの FK が増えすぎるdim_review_attributes(30), dim_page_context(72)

遅い（年単位）中〜高、履歴が要る本体を Type 2「投稿当時の企業規模」を答える必要があるdim_company.employee_size_band, dim_agent.agency_id

Kimball の但し書きも1つ入れておく。DT#83 は「人・場所・物」を1本の汎用ディメンションに抽象化するのを戒める。「我々が自社の内部エンティティについて収集し知っている情報は、外部エンティティについてのそれとは大きく異なる」「抽象化のプロセスは業務ユーザーにとっての明快さを減じ、必然的により大きな表を生む」。

dim_scout_sender は企業と担当者を1本に載せる異種ディメンション（supertype）なのでこの警告の射程に入る。正典が採る理由は、fct_scout の粒度が「送信された1スカウト」で送信主体が排他的に1つだからだ。対案（2本の FK + -1）との比較は 06 回で行う。

7. 演習

問1

scouts.template_id は退化ディメンションのままでよいか、それともディメンション表を新設すべきか。判断基準の表のどの行を使ったかを示すこと。

解答例

現状は退化のままでよい。 判断基準の表の1行目（変わらない × 高カーディナリティ → 退化）ではなく、実は3行目（変わらない × 中、独自の属性を持つか）で分岐する。

条件判断
template_id で fct_scout の行をグループ化したいだけ（「テンプレ別の返信率」を ID のまま見る）退化。正典どおり fct_scout の列に置く
テンプレ名・種別（求人紹介 / カジュアル面談 など）・作成企業で切りたいディメンション化。ただし正典にテーブルが無いので、まず 01 回のバスマトリクスに列を足す提案をする
テンプレ数が fct_scout の行数に近づいた（1スカウト1テンプレの自動生成になった）退化に戻す。DT#46 の「ディメンション表がファクト表とほぼ同じ速度で伸びていたら、見落とした退化ディメンションが潜んでいる」に該当

CareerVoice のテンプレは企業の採用担当が手で作るもので、数百件で頭打ちになる。名前や種別が分析要件に上がるまでは退化で足りる。「属性が要る」のが唯一の昇格条件であり、カーディナリティが低いことは昇格の理由にならない点に注意する。

問2

is_unlocked（閲覧権限の有無）を dim_page_context に入れるべきか、fct_page_view のメジャーにすべきか。

解答例

正典どおり dim_page_context に入れる（72行の第4軸）。 判断基準表の2行目（変わらない × 低カーディナリティ → ジャンク）と、タイブレーク表の1問目（グループ化するか → Yes）の両方に当たる。

メジャー案が成立しない理由: SUM(is_unlocked) は「解錠状態での閲覧数」を返して数値としては意味を持つが、これは view_count を is_unlocked で絞ったものと同じで、新しい計測ではない。Techniques の「true/false フラグや業務上の指示子は、単独で見て意味を持つ完全な語でディメンション表に補うべきだ」に従い、軸として持つ。

反論も書いておく。BigQuery では fct_page_view に is_unlocked BOOL を直接持てば結合なしで絞り込める。

ただし (1) page_context_key の結合先は 72 行で実質ブロードキャストなので結合コストはほぼゼロ、(2) 2値属性は選択率 50% でクラスタリングも効かない、(3) ファクトとジャンクに同じ値を二重に持つと更新経路が2つになる。採らない。 配布用に非正規化した1枚を別途作る話は 07 回（OBT）で扱う。

問3

M001 は 2026-06-15 に job_change_intent が passive → active、annual_income_band が 400_600 → 600_800 へ変わり、2026-08-01 に C001 へ入社する。dim_member と dim_member_profile_mini のそれぞれに何が起きるか。

解答例

6/15 の変化では、どちらのディメンションも行が1行も増えない。 変わったのは annual_income_band と job_change_intent の2つで、どちらも dim_member の属性ではない（正典の dim_member は birth_year, gender, prefecture, region, current_company_id, current_job_category, registered_date）。dim_member_profile_mini は 15 通りの全組合せを最初から持っているので、こちらも増えない。

変わるのはファクト行がどの行を指すか、だけである。

日付出来事member_keymember_profile_mini_key が指す行
6/14fct_page_view（求人閲覧）M001 版1(400_600, passive)
6/15属性変化変化なし（版は増えない）行は増えない（15 行のまま）
6/20S001 受信 → fct_scoutM001 版1(600_800, active)
6/23P001 応募 → fct_application_pipelineM001 版1(600_800, active)
8/1C001 入社 → current_company_id 変化M001 版2 を発行（Type 2 属性なので）(600_800, active) のまま

要点は変化の種類でディメンションが分かれることだ。8/1 の current_company_id は dim_member の Type2 属性なので新しい member_key が出る。6/15 の2属性はミニ側なので新しいキーは出ない。

M001 がもし年に4回意欲を切り替えても、dim_member は静止したままである。

ただし DT#127 の但し書きが効く。6/15 の変化は、6/20 の S001 というファクトが発生したからこそ記録に残った。もし 6/15 以降 M001 が何も起こさなければ、この変化はどのファクト行にも刻まれない。

「会員の意欲がいつ変わったか」自体を分析対象にするなら、ミニディメンションでは足りない。正典の dim_member_daily（日次スナップショット）かファクトレスファクト表が要る（05回）。

8. 参考: 手元の基盤ではどうか

  • dbt_logs_analysis の mart_url_performance_incremental は unique_key=['url_path', 'date']、つまり自然キーの複合をそのままキーにしている。履歴を持たないモデルなので、この回の基準では正しい判断（判断基準表の「Type 0/1 は自然キーをそのまま」）。ハッシュに置き換える理由は無い。
  • 同プロジェクトには dim_date に相当するものが無く、date が DATE 列のまま並んでいる。これは §2(b) そのものの形で、「営業日ベースのレスポンスタイム」や「年度別」の要件が来た瞬間に各モデルへ CASE が散る。
  • news_pipeline の summaries はスコアを上書きする Type 1。scoring_version があるので「どの採点版か」は追えるが、dbt_invocation_id / batch_id に相当する監査列は無い。/recalculate の途中でクレジット枯渇が起きたとき、どの実行がどこまで書いたかを SQL で切り分けられない。dim_audit の最小形はこの1点に効く。
  • 試せる種: raw_articles.collected_at から date_key INT64 を作り、-1 行を1行だけ持つ dim_date を置いて summaries（notified_at が NULL の行が大量にある）を結ぶ。未通知が -1 に落ち、COUNT(*) = notified + not_yet が成立するのを確かめる。これが §2(c) の再現になる。
