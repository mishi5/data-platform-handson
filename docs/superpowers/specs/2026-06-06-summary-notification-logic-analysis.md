# 要約保持・通知選定ロジックの整理（現状仕様と検討論点）

作成日: 2026-06-06
目的: 「サマリーを残しすぎていないか」「フィルタ精度を上げるべきか」「閾値以上溜まっていたら要約をスキップしたいか」を判断するため、現状の処理フローと選定ロジックを可視化する。これは**現状仕様の分析ドキュメント**であり、変更の設計はまだ確定していない。

---

## 全体処理フロー（`_run_pipeline`）

```
[1] RSS取得          fetch_articles(feeds)           … 全フィードの記事メタデータ（今回435件）
        │
[2] dedup           raw_articles の URL と突合        … 既出URLを除外（今回 新着59件）
        │
[3] 要約上限で絞る   new_articles[:max_summarize]     … settings general/max_summarize（現状30）
        │                                              ※ ここで「先頭N件」を機械的に取る（順序はRSS取得順）
[4] 本文取得        fetch_content(url)               … requests + trafilatura（403等は本文空で続行）
        │
[5] raw_articles保存 bq.insert_raw_articles           … 取得した全件を生データとして保存
        │
[6] 要約生成        summarize_article() ×N           … Claude Haiku で {summary, tags, importance_score}
        │                                              ※ ここが律速。1件2〜4秒 × N
[7] 重要度フィルタ   importance_score >= IMPORTANCE_THRESHOLD（既定0.5）
        │                                              … 閾値未満は summaries に残さず破棄
[8] summaries保存   article_id 重複を除外して insert   … 「残すサマリー」が確定する地点
        │
[9] 未通知取得      get_unnotified_summaries()        … notification_log に無い全サマリー（今回234件）
        │
[10] カテゴリ別通知  category ごとに importance降順 → max_notify件 → Slack送信
        │
[11] 通知済みマーク  notification_log へ和集合を記録
```

## 「サマリーとして残す」ロジック（=蓄積される条件）

サマリーが BigQuery `summaries` テーブルに残るかは、以下を**すべて**満たした記事だけ:

1. **新着である**（[2] raw_articles に URL が無い）
2. **要約バッチに入った**（[3] その実行回の新着の先頭 `max_summarize` 件に入った）
3. **重要度が閾値以上**（[7] `importance_score >= IMPORTANCE_THRESHOLD`、既定 0.5）
4. **summaries に未登録**（[8] 同一 article_id が無い）

### ここで起きている「残しすぎ」の構造

- **保持ゲートは [7] の重要度閾値ただ1つ**。閾値 0.5 は緩めで、データエンジニアリング関連ならほとんど通過しうる。
- **保持と通知が非対称**。残すのは「閾値以上の全件」だが、通知するのは「カテゴリ別に上位 max_notify 件」だけ。
  → 残る速度 > 捌ける速度 になりがちで、`summaries` の未通知分がバックログとして積み上がる（今回234件）。
- バックログは消えない。各実行でカテゴリ数 × max_notify 件ずつしか通知されず、古い低スコア記事が延々と未通知のまま残る。

---

## 「通知するニュースを選ぶ」ロジック（=出す条件）

通知は保持とは別のゲートで決まる（[9]〜[10]）:

1. **未通知である**（`notification_log` に article_id が無い）
2. **カテゴリに分類**（feeds の category、空欄は `other`）
3. **カテゴリ内で importance_score 降順**にソート
4. 各カテゴリ **上位 `max_notify` 件**（settings `<category>/max_notify`、既定5）だけ送信
5. 通知順はカテゴリ＝settings の group 出現順

### 通知選定の特徴と弱点

- **新着とは無関係**。その実行で新規要約が0件でも、バックログから毎回 max_notify 件が掘り出されて通知される。
- **古い記事が上位を占めうる**。importance_score だけでソートするため、鮮度（published_at / collected_at）は考慮されない。バックログが大きいと「数日前の高スコア記事」が「今日の中スコア記事」より優先される。
- **取りこぼしの可能性**（既知）。`send_slack_notification` は送信失敗を握りつぶすため、Slack に届かなくても notified 扱いになりうる。

---

## importance_score の決まり方（フィルタ精度の源泉）

- `summarizer.py` が Claude Haiku に **keywords シートの語**を判定基準として渡し、0.0〜1.0 を自己申告させている。
- プロンプト基準: 「キーワードに関連するほど高く」「複数該当でさらに高く」「全く無関係なら 0.1 以下」。
- 精度を左右する要素:
  - **keywords シートの内容**（広すぎると大半が高スコア、狭すぎると取りこぼし）
  - **本文取得の成否**（[4] が 403 等で空だと、タイトルのみでスコア判定 → 精度劣化）
  - **閾値 0.5 の妥当性**（緩い）
  - モデルのスコア較正（Haiku の自己申告スコアは絶対値の信頼性が低め）

## 検討論点（ユーザーが悩んでいる点の整理）

### A. サマリーを残しすぎる問題
- 現状の保持ゲートは閾値1つだけ。**残す基準と通知する基準が乖離**しているため未通知が溜まる。
- 取りうる方向:
  - (A1) 保持の閾値を上げる（残す母数を減らす）
  - (A2) 保持にも件数/鮮度の上限を設ける（古い未通知を期限切れにする）
  - (A3) 「残す＝通知候補」と割り切り、一定期間で未通知を失効させる

### B. フィルタ精度を上げる工夫
- (B1) keywords の見直し（粒度・ネガティブ語）
- (B2) 本文取得失敗時の扱い（タイトルのみ要約のスコアを割り引く／除外）
- (B3) スコアの較正（プロンプトで基準例を与える、相対ランク方式に変える）
- (B4) 閾値をカテゴリ別に設定可能にする（公式は緩め・個人は厳しめ等）

### C. 「閾値以上溜まっていたら要約をスキップ」（当初の要望）
- 目的: バックログが十分あるなら、コスト/時間のかかる [6] 要約を省いて、既存の未通知から通知だけ行う。
- 論点:
  - **判定する閾値は何の件数か**: 未通知サマリー総数（234のような全体）か、カテゴリ別未通知数か。
  - **スキップの範囲**: [3]〜[8]（取得・要約・保存）を丸ごと飛ばすのか、要約[6]だけ飛ばすのか。
  - **rss/dedup/raw 保存は続けるか**: 生データ収集は継続したいなら [1][2][4][5] は実行し [6][7][8] のみスキップ、という切り分けもある。
  - **設定キー案**: settings `general/skip_summarize_when_backlog`（未通知がこの数以上なら要約スキップ）。0/空で無効。
  - C は B（精度）や A（残す量）と独立して入れられるが、根本の「残す>捌ける」構造（A）を放置するとバックログは減らないため、**C は対症療法、A が根治**という関係。

## 次アクションの選択肢

この分析を踏まえ、どれを設計に進めるか:
- **C のみ**（当初要望: 閾値超過で要約スキップ）を最小実装する
- **A+C**（保持側にも上限/失効を入れてバックログ構造を是正しつつ、要約スキップも入れる）
- **B**（フィルタ精度の改善）を先にやる
- まずバックログ234件を一時的な max_notify 引き上げで消化し、運用しながら見極める

確定したらブレインストーミング→設計→実装に進む。
